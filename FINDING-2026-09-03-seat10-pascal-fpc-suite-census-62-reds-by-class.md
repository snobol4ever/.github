per-program FAIL lines. Bucketed the 61 by stderr signature first: 34 "Error 5 / Undefined function or

turned all 34 "Error 5" cases into an exact undefined-name-and-arity list in one pass. This diagnostic
addition is a permanent, zero-risk addition (env-gated, matches the existing convention exactly) — kept in

None of these builtins exist anywhere in `src/lower/lower_pascal.c` (grepped directly) — the mechanism that
DOES work for `ord`/`chr`/`pred`/`succ`/`trunc`/`abs`/`sqrt`/etc. lives in the PARSER, not the lowerer:
`pascal.y`'s `mk_call()` is a big if-chain matching literal function names at parse time, either rewriting to

etc. were simply never added to this list — confirmed by a minimal standalone repro (`round(3.7)` on a
freshly-written 5-line witness, same "Error 5" with zero suite machinery involved) before touching anything.

## CURED this session: `halt` and `round` (tied-largest classes, 6+3 witnesses)

Added `round`/`halt` to `pascal.y`'s `mk_call` (same pattern as `trunc`; `halt` handles both `halt;` and
`halt(n)`) and their handlers to `by_name_dispatch.c` (`round` → C's `round()` via libm; `halt` → `fflush(NULL);
exit(n)`). Regenerated the parser (`scripts/regenerate_parser_and_lexer_from_sources.sh pascal`).

**The BID registration mechanism is a one-way transform, not idempotent** — `gen_builtin_ids.py` converts
`!strcmp(fn,"NAME")` source forms into `(_bid==BID_NAME)` integer compares IN PLACE; today's
`by_name_dispatch.c` has already had every existing builtin transformed, so there is no `!strcmp` form left
for the generator to find (`sites_rewritten=0` if re-run). Adding a new builtin now means computing its hash
slot by hand against the existing 176-entry, 1024-slot open-addressed table (same djb2-style hash the
generator uses) and inserting the `#define BID_x N` + table entry directly — done here for `__pas_round`
(id 177, slot 558, zero probe) and `__pas_halt` (id 178, slot 15, zero probe), verified by re-parsing the
whole header afterward (178 defines, 178 occupied slots, consistent). **This is a real, load-bearing process
gap worth its own row**: the tool that was supposed to make adding a builtin mechanical no longer can, and
the fallback (hand-computing a hash slot) is exactly the kind of manual step the tool exists to avoid. Not
minted separately this session — flagged here for whoever next adds a builtin.

**Measured, isolated, before touching the suite:** `round(3.7)` → `4` (round-half-away-from-zero, correct).
`halt(1)` in a 4-line witness → prints the pre-halt output, process exits with code 1, no more "Undefined
function" error.

**Measured on the suite: `120 → 122` (m3_pass, m4_pass identical).** Only 2 of the 9 directly-touched
witnesses (`webtbs_tw23486`, `webtbs_tw35626`, both `round`) actually flipped to PASS. **Every one of the 6
`halt` witnesses and 1 of the 3 `round` witnesses (`webtbs_tw29930`) still fails — not because `halt`/`round`
are broken, but because fixing the "undefined function" error unmasked a SEPARATE, pre-existing correctness
bug each program was hiding behind it.** Same shape this fleet has already seen once this session (the
`pascal-m4-alpha-undefined-link` cure unmasked exactly one new residual, `arrparam.pas`) and once before that
(`pascal-restore-prezeta`'s history, repeatedly). Verified directly, not assumed — e.g. `tbs_tb0012` now
prints `1210` where the ref expects `1.2100000000000000e+003` (a formatting/type divergence, unrelated to
`halt`); `tbs_tb0598` prints a wrong large integer (`9223372036854` vs expected `10000000000`, overflow/
precision-shaped); `webtbs_tw3174` prints `0` where `A` is expected (unrelated value bug). These three
different mechanisms on three different programs is itself evidence this is a real unmasking, not one
shared residual cause. All 7 unmasked witnesses folded into the `wrong-answer-misc` row below rather than
re-counted under their old builtin names.

**Net effect measured plainly: this session's `main` is 2 programs better than where it started, and
