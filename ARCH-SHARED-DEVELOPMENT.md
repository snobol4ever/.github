# ARCH-SHARED-DEVELOPMENT — ONE SHARED, CO-OPERATIVE DEVELOPMENT SYSTEM FOR NINETEEN SEATS ON ONE BOX (the cto, Fable 5.1 xhigh, 2026-10-30 12:0x-12:5x CDT; CEO-2041; Lon in-chat to the ceo, verbatim: *"You need to fix the sharing and co-ordination between seats for the machine load problem."* · *"Actually, give that task to CTO."* · *"We want to design a shared and co-operative system that allows optimal development."*)
DESIGN-PLAN: shared-development

THE AIM, in the baton's words: the most useful development per hour across the fleet, not the lowest load number, with the testing officer's grading never starved. THE READING THAT DECIDES THE DESIGN: the box is oversubscribed about two to one (16 cores, load 27 to 35, cpu pressure some avg300 48 percent at 11:29), and what it lacks is not a limit on HOW MUCH runs but a say over WHOSE work the cores go to: the pools bound process counts and not shares, so one seat's `make -j8` holds every compile slot and one seat held a third of the box while the one grader everyone waits on held 0.39 cores and graded two programs in 392 s with 4,415 queued. The kernel already has the instrument and the lever: every session is its own cgroup scope with the cpu, memory and pids controllers delegated to this user, so a seat's exact CPU is one file read and a seat's fair share is one property write. THE THREE PRINCIPLES: (1) THE KERNEL DIVIDES TIME by class and by seat (work-conserving: an idle seat's share flows to the busy ones, nothing is ever reserved and wasted, nothing can deadlock), THE POOLS BOUND CONCURRENCY (how many compilers and runs exist at once, so memory and the caches are not thrashed) with a per-seat cap so no seat empties a pool, and the two are not the same job; (2) WORK IS DONE ONCE PER TREE: a build, a deterministic check, an oracle answer, a grading are pure functions of the tree hashes and are stored where every seat reads them; (3) THE GRADER IS A CLASS ABOVE THE SEATS, because every landing's verdict passes through it, and BATCH IS A CLASS BELOW THEM, because nobody is waiting on it this minute.

```
└─ user@1000.service / app.slice                                    cpu memory pids delegated
   ├─ app-org.gnome.Terminal.slice   CPUWeight 600, MemoryHigh 20G, MemoryMax 24G    THE SESSIONS (interactive)
   │    ├─ vte-spawn-….scope (one per seat)   CPUWeight 100, MemoryHigh 4G, MemoryMax 8G, MemorySwapMax 1G, TasksMax 2048   set by the seat's own SessionStart hook
   │    └─ vte-spawn-….scope (Lon's own tabs) CPUWeight 200 when the hook sees a non-seat root (class LON)
   ├─ s4e-grader.slice                CPUWeight 300, MemoryMax 10G     THE GRADER: loop8, tier1, their harness children and mem scopes
   ├─ s4e-batch.slice                 CPUWeight 100, MemoryMax 12G     BATCH: identity runs, censuses, sweeps, callgrind, boards, the DONE-WHEN sweep, cron
   │    └─ s4e-mem-….scope / run-….scope (one per job) MemoryMax 8G as today
   └─ app-gnome-*.scope, Chrome       weight 100 each, no cap         LON'S DESKTOP (class LON): protected by every fleet class having a MemoryMax
```

Under full contention the sessions' slice holds about 55 percent of the box, the grader 27, batch 9, the desktop 9; when the grader is idle its share flows to the sessions and when the seats are idle (evenings, a thin roster) batch inherits the box. Inside the sessions' slice every seat is an equal sibling: a seat's `make -j4` and another seat's single run each get the same share, and a seat's hand run that bypasses every pool can take no more than its own share. THE LEDGER is `/home/resources/progress/LOAD.tsv`, one line per seat and class every five minutes from the scopes' own counters (§ 2). THE CACHES are the build cache, the check cache and the oracle cache under `/home/resources` (§ 3), keyed by tree hashes, written by whoever is first, read by everyone.

## 2. THE ACCOUNTING: the cgroup scopes are the ledger (the baton's (1))

**2.1 What counts as a seat.** Four classes. SEAT: a Claude session whose root is `/home/claude_<seat>` (nineteen today: ceo, cto, cfo, coo, cao, cqo, hq_icon, hq_prolog, hq_pascal, hq_snocone, hq_snobol4, hq_raku, hq_templates, hq_runtime, hq_collector, hq_zetas, hq_packages, hq_dotnet, hq_jvm), identified by its session scope. LON: Lon's own Claude sessions and terminal tabs (a vte-spawn scope whose root is not a seat's) and the desktop scopes (`app-gnome-*`, Chrome, Sublime). CRON: the user crontab's jobs (the /tmp sweeper, the census), which run in cron's session scope at the `user-1000.slice` level, a sibling of the whole of `user@1000.service`, so a heavy cron job would take HALF the box; every cron line therefore re-homes itself with `systemd-run --user --scope --slice=s4e-batch.slice` (§ 5). SYSTEM: everything else under `user-1000.slice` (gnome-shell in `session.slice`, the agents), reported as one line, never acted on.

**2.2 The registration.** A seat's scope changes at every restart, so the map from scope to seat is written by the seat itself: the `SessionStart` hook (installed by Lon's one script, § 8 step 2) runs `s4e_session_start.sh`, which reads its own scope from `/proc/self/cgroup`, appends `seat, scope, pid, start` to `/home/resources/progress/SEATS.tsv` (one live line per seat, the older lines kept as history), and applies the seat's class properties to that scope (§ 4.2). The fallback for a scope with no line (a session started before the hook existed) is the cwd of the scope's first process, which is how the ceo and this page measured.

**2.3 The instrument: `util_seat_census.py` (new; it replaces the SEAT arm of `util_machine_health.py` and keeps its RUNAWAY arm word for word).** It walks every cgroup under `user-1000.slice`, samples `cpu.stat` twice ten seconds apart, reads `memory.current`, `memory.peak`, `memory.events` (oom_kill), `pids.current`, `cpu.pressure`, maps each scope to its seat by SEATS.tsv, sums per class, reads the pools (which seat holds which slot: the slot files gain a one-line sidecar `slot<i>.seat` written by the taker under the same flock) and the seats' /tmp (one `du` of `/tmp/claude-1000/-home-claude-<seat>` every fifteen minutes, cached), and APPENDS to `LOAD.tsv`: `utc, class, seat, cores, mem_mb, mem_peak_mb, oom_kills, pids, cc_slots, run_slots, tmp_mb` per seat and class, plus one BOX line (`cores_busy, load1, pressure_some_avg60, mem_available_mb, swap_used_mb, tmp_pct, cc_held, run_held, slice_held, builds_fetched, checks_hit, oracle_hit`). It runs from cron every five minutes inside the batch slice, and on demand (`util_seat_census.py now` prints the table; `--check` is step 1's DONE-WHEN: the newest run under ten minutes old, nineteen SEAT lines, the seats' cores summing to within ten percent of `app.slice`'s own delta). `s4e_msg.sh banner` prints ONE line from the newest LOAD.tsv, never sampling: `BOX busy 15.2/16 pressure 46 | you 0.8 cores 1.1G tmp 0.4G cc 0 run 1 | grader 2.3 | batch 1.0 | top hq_zetas 5.3`. `util_load_board.sh` prints the same table for Lon, newest first, and `--hours N` the history. A reading of this ledger is what every roll-out step below is measured by, and it is the only load number a telegram may quote (the load average says THAT, never WHO).

## 3. THE SHARING: work done once and reused by every seat on the same tree (the baton's (2))

**3.1 The principle.** A build, a deterministic check, an oracle answer and a grading are each a pure function of (the trees' hashes, the arguments). A cache keyed by those is correct by construction and needs no invalidation: a new landing is a new key. Every cache lives under `/home/resources` (the same partition as the roots, so hard links work), is written ATOMICALLY by whoever computes the value first (a temp dir renamed into place; the second writer finds the key and drops its copy), and is read by everyone. A root reads a cache only when its own trees are CLEAN (`git status --porcelain` empty in the repos the key covers) at the key's hashes; a dirty tree computes locally and stores nothing. Nothing in this section changes what a verdict means: a hit is the same computation, done once.

**3.2 THE BUILD CACHE (`/home/resources/builds/scrip/<key>/`).** The key is the SHA-256 of SCRIP's `HEAD^{tree}`, the harness tree hash (the three generated `.inc` files come from it), and the toolchain line (`gcc --version | head -1`, the ccache version). The entry holds `scrip`, `out/libscrip_rt.so`, `out/scrip-ipp`, `out/scrip0`, `out/libscrip_rt0.so`, the seven `out/libscrip_parser_<lang>.so`, `out/buildinfo` and the `rt_pic-<tag>` object set, about 150 MB. PRODUCER: `make` in ANY root (and the coo's tier-1 worktree, which builds origin/main within a minute of every landing, so it is the usual first) publishes after a successful build when its trees are clean. CONSUMER: `make` first computes the key; on a hit with clean trees it hard-links the artifacts into the root (`make` prints `FETCHED <key>`), touches them newer than every source, and the freshness guard (CEO-1040) reads the same tree hash in `buildinfo` it would have read from a local build. The objdir `/tmp/si_objs<root>` is then stale, which costs the next DIRTY build a full compile (ccache makes that about the link time) and nothing else. Retention: the newest 60 keys by access time (about 9 GB), pruned by the census. The measure: LOAD.tsv's `builds_fetched` against the landings per hour; the finish is one compile per tree per day at the fleet's scale, read from ccache's miss count and the pool's compile seconds.

**3.3 THE CHECK CACHE (`/home/resources/progress/checks/<name>/<key>`).** `util_check_cache.sh <name> -- <command>`: the key is `<name>` plus the SHA of the SCRIP, corpus, harness and .github tree hashes plus the command's arguments; a hit (the four trees clean at those hashes) replays the stored rc and output with a `CACHED <key> <utc>` first line; a miss runs the command, stores rc and output, and prints it. WHO USES IT: `s4e_msg.sh done` (the computed DONE-WHEN), the ceo's CEO-1386 sweep over every row's DONE-WHEN (its biggest consumer: the sweep runs hundreds of gates on one tree), the coo's blocking-set arms that are gates, and a lander's own gate. WHAT IS CACHEABLE: a `test_gate_*` the wiring (`util_gate_wiring.py`) classes as deterministic, which is every gate that reads only the trees and the binaries built from them; NOT cacheable, by name in `harness/scripts/checks_nocache.tsv`: a gate that reads the live box (load, /tmp, the postoffice, SEATS or LOAD), a clock-shaped gate, a board (a corpus population graded for a row; the progress store is its cache already), and anything run under `S4E_ONE_TEST_ADMIT` or an override. `--fresh` bypasses for one run and says so.

**3.4 THE ORACLE CACHE (`/home/resources/progress/oracle/<oracle>/<key>`).** Every live oracle run (sbl, icx, gpx, swx, fpx, rkx, the XSB and Trealla binaries) goes through `util_oracle.sh <oracle> [--stdin FILE] -- <args>`: it takes a run slot, runs under `timeout -k 5` (the swipl class that ignored SIGTERM for two hours, CEO-1796, dies at the kill), and caches rc, stdout and stderr by the SHA of the oracle binary, the program file, the argv and the stdin; `monitor_run.sh --oracle` and `util_ref_mint.sh` adopt it; the suite runners keep reading the stored refs in corpus, which are the oracles' answers already cut. A ref is still cut from the oracle, never from our output (CEO-1696's rule is untouched).

**3.5 THE PROGRESS STORE stays the one grading cache.** `results.tsv`, its rows written one test at a time by the coo's loop and by the computed `done`, read by every seat through `util_score_row.py from-progress`: KEPT as is; the ledger files sit beside it (LOAD.tsv, SEATS.tsv, SLICES.tsv, SMOKE.tsv, the sweeper's log). A seat never grades what the store already holds for the tree it stands on: `util_score_row.py` already answers from the store, and a TEST REQUEST (`s4e_test_request.sh`) is the way to ask for what it lacks.

**3.6 What stays per root.** The working trees (a seat's edits are its own), the objdir when the tree is dirty, the root's fetched or built artifacts, the session scratchpad under `/tmp/claude-1000/<root>/<session>`, and `settings.local.json` (whose `env` block names the seat). A detached control worktree (`.scrip-ctl-*`) is a root like any other and reads the build cache like any other.

## 4. THE CO-OPERATION: fair share, the grader's priority, admission, nesting (the baton's (3))

**4.1 Kernel or pools, or both: BOTH, each its own job.** THE KERNEL divides CPU TIME: `cpu.weight` among siblings is exact, work-conserving (an idle class's share goes to the busy ones, so no core ever waits for a reservation), instant (a property write), and deadlock-free (nothing waits on a weight). It cannot bound how many processes exist, how much memory they touch at once, or how the caches thrash, and that is THE POOLS' job: eight compilers and eight runs at once is what 16 cores and 30 GB bear without thrash; the pools stay, and gain a per-seat cap and a reservation. The memory controller bounds the damage of a runaway to its own class (§ 6). No `nice` anywhere: a nice value is relative within one cgroup and invisible across them; the six harness scripts that nice their work drop it in step 4.

**4.2 The weights and the caps (the numbers).** Set once by Lon's script (§ 8 step 2) on the slices and by every seat's SessionStart hook on its own scope, idempotently, so a restarted session is placed without anyone's hand: `app-org.gnome.Terminal.slice` CPUWeight 600, MemoryHigh 20G, MemoryMax 24G; each seat scope CPUWeight 100, MemoryHigh 4G, MemoryMax 8G, MemorySwapMax 1G, TasksMax 2048; a LON scope CPUWeight 200 and no cap; `s4e-grader.slice` CPUWeight 300, MemoryMax 10G; `s4e-batch.slice` CPUWeight 100, MemoryMax 12G; each batch job its own scope under it with MemoryMax 8G as util_mem_scope.py sets today. The caps are limits, not reservations: their sum may exceed the box because the OOM killer acts INSIDE the cgroup that hits its own `memory.max`, which is the whole point (§ 6). The hook uses `systemctl --user set-property --runtime <unit>` for a scope and `systemctl --user set-property` (persistent, under `~/.config/systemd/user.control/`) for the slices; the first write of a CPUWeight below `app.slice` enables the cpu controller there (measured: a transient scope with CPUWeight=50 flipped `app.slice/cgroup.subtree_control` to `cpu memory pids`, § 10), after which every child is weighted, so the slice properties are written BEFORE the first seat scope's.

**4.3 THE POOLS WITH A SEAT'S SHARE.** `util_cc_slot.sh` and `util_run_slot.sh` (and the harness's `_run_slot`, which must stay word for word the same rule) read their knobs from one new `lib_slots.sh`: the pool size (8 and 8 as today), the per-seat cap (`S4E_CC_SEAT_CAP` 4, `S4E_RUN_SEAT_CAP` 3), the grader's reservation (run slots 6 and 7 are taken only by `S4E_CLASS=grader`; the grader may also take 0 to 5), and the seat (from `S4E_SEAT`, else the root path). A taker first takes one of its SEAT files (`/tmp/s4e-cc-slots/seat/<seat>/<0..cap-1>`, flock, held for the process's life) and only then a pool slot; a seat at its cap waits on its own file, not on the pool, so another seat's single compile is never behind one seat's eight. The sidecar `slot<i>.seat` names the holder for the census. `make`'s default parallelism becomes the cap: the `env` block of every root's `settings.local.json` sets `MAKEFLAGS=--jobs=4` (a command-line `-j` still overrides), and the twenty harness scripts that pass `-j8`, `-j4` or `-j` pass `-j${S4E_SEAT_JOBS:-4}`; the SCRIP Makefile's own recursive makes inherit it. With the weights in place a seat that bypasses the pools hurts only itself, which is why the pools no longer need to be the whole defence.

**4.4 THE TESTING OFFICER'S PRIORITY.** The grader's work is everything loop8.sh and tier1.sh start: they are launched by the coo (swap40.sh, or by hand) as `systemd-run --user --scope --slice=s4e-grader.slice -p MemoryMax=8G -E S4E_CLASS=grader bash loop8.sh`, so every harness child, mem scope and compile of theirs lives in the grader slice at weight 300 and takes the reserved run slots. The loop's own ZSM census and ZD check are BATCH, not grading (they starved the round robin, COO-435): the loop starts them through `util_batch.sh` (§ 5), so they run under the batch weight and the grader's share is spent grading. `wait_wants` (the loop's tier-1 precedence) stays as the loop's own ordering; the loop never waits on another seat's process, and CEO-1805's one-test-at-a-time is the loop's own serialization, which stands. The grader's finish line is a RATE: the round robin's programs per hour read from results.tsv's `rr=1` rows, at load (step 5).

**4.5 ADMISSION FOR EVERY HEAVY RUN, not opt-in.** Three kinds of run exist. (a) A HARNESS RUN (a board, a smoke, a handful, a gate that runs programs, a test request's grading): admitted by the harness's `_run_slot` as today, inside the mem scope of its class when it is a board (`lib_one_runner.sh` passes `--slice=s4e-batch.slice`, or the grader's when `S4E_CLASS=grader`), inside the seat's own scope when it is a handful or a smoke (interactive by nature). (b) A BATCH JOB (an identity run, a census, a compile-all sweep, a callgrind, a placement-watch kick, a port HQ's board regrade, the ceo's DONE-WHEN sweep): started ONLY through `util_batch.sh <cmd>` (§ 5), which is `systemd-run --user --scope --slice=s4e-batch.slice -p MemoryMax=8G` plus a run slot, and refuses a second batch job of the same seat while one runs (one per seat: `/tmp/s4e-batch/<seat>.lock`); the scripts that are batch by nature call it themselves at their top (the way `lib_one_runner.sh` enters its mem scope), so a seat cannot start one outside the class. (c) A HAND RUN (`./scrip prog`, a two-tree diff, an oracle by hand): inside the seat's own scope, bounded by the seat's weight and memory cap; `util_run_slot.sh` is still the courtesy that keeps the pools honest, and `util_oracle.sh` is mandatory for an oracle (§ 3.4) because an oracle that ignores SIGTERM is a runaway class, not a load class. The port engines: `Directory.Build.rsp` (`-maxcpucount:1 -nodeReuse:false -p:UseSharedCompilation=false`) already keeps dotnet's build to one node and is kept; hq_dotnet's and hq_jvm's suite runners enter the harness's admission like every board (lib_one_runner already places `test_snoflake_suite.sh` in a mem scope) and their batch-sized regrades go through `util_batch.sh`.

**4.6 NESTING WITHOUT DEADLOCK, proven by the shape.** A holder of a pool never waits for the same pool: a compile slot is held by a compiler (a leaf: it starts nothing); a run slot is held once per tree of processes (`S4E_RUN_SLOT_HELD` makes every nested harness, hand run or batch wrapper take none); the seat files are taken BEFORE the pool slot and never after; the quiet slice takes everything under its own lock and REFUSES inside a held run slot (one line added: `S4E_RUN_SLOT_HELD` set means a slicer would wait on its own slot) as it already refuses inside a slice; a batch scope is a sibling, never a child, of the seat's scope (systemd nests scopes only under slices), so no cgroup limit waits on a parent that waits on it; the weights wait on nothing. The one ordering that must hold, slice lock then run slots then compile slots in `util_quiet_slice.sh`, is the only multi-pool take in the harness and stays the only one (a new script that needs two pools takes them in that order, which `test_gate_pools_cap_a_seat_and_reserve_the_grader.sh` reads from the text).

## 5. THE SCHEDULING: batch against interactive, the quiet slice, evenings (the baton's (4))

- THE RULE IS THE WEIGHT, NOT THE CLOCK. Heavy batch work (the coo's round robin is NOT batch, it is the grader; batch is the 274-program identity run, the ZSM and placement censuses, the compile-all sweeps, callgrind, the port HQs' board regrades, the ceo's DONE-WHEN sweep, the cron jobs) starts whenever its owner wants it, through `util_batch.sh`, and the kernel gives it what the seats and the grader leave: about nine percent of the box in the busy hours and the whole box when the seats are idle. Nobody schedules an evening: when Lon stands seats down (MODE's ROSTER) their share flows to batch by itself, and a batch job's wall is read from the ledger, never from a wristwatch.
- THE INTERACTIVE SEAT landing a fix gets its weight the moment it needs it: a `make -j4` and the handful (≤ 8 reps, both modes) run in the seat's own scope at the sessions' weight, ahead of every batch job and beside the grader. A seat waits for nothing but the pools' caps, and the caps are its own.
- THE QUIET SLICE (`util_quiet_slice.sh`) is KEPT for the one thing weights cannot give, a clock measurement (CEO-2035: a benchmark is an instruction count; a clock only inside a slice). It drains both pools as today and, with the weights in place, also runs its command in a scope of CPUWeight 10000 (the maximum), so the sessions it cannot drain yield to it; it refuses inside a held run slot (§ 4.6) and keeps its 600 s ceiling and its SLICES.tsv line. `BENCH_LOAD_GUARD_PER_CORE` (lib_perf_fmt.sh's per-core load threshold) is MERGED into it: a clock-shaped measurement is admitted by `S4E_IN_SLICE`, refused rc 2 outside one, and the load threshold is retired with the guard's text (the gate `test_gate_sweep_keeps_a_load_guard_refusal_and_retires_a_cannot_measure_one.sh` keeps its refusal shape on the new predicate). `util_instr_count.sh` is KEPT unchanged: it does not move with the load and runs at any time.
- THE CRON LINES re-home themselves: `*/5 * * * * XDG_RUNTIME_DIR=/run/user/1000 systemd-run --user --scope --slice=s4e-batch.slice -q flock -n ... bash util_tmp_sweep.sh ...` and the census line beside it, so cron's half-the-box session scope holds nothing but the one-second `systemd-run` call.
- THE ceo's SWEEP (CEO-1386, every row's DONE-WHEN) is batch and reads the check cache (§ 3.3): on an unchanged tree it costs nothing; on a new tree it costs one run per gate for the whole fleet.

## 6. MEMORY AND /tmp (the baton's (5))

- THE TWO SHAPES CLOSED. A runaway inside a capped cgroup is killed INSIDE it: the seat scope's `memory.max` 8G (a child of a session that reaches 8 GB dies and the session's node process, at 0.5 to 2.9 GB, does not), the batch and grader scopes' 8G, the slices' 24G, 10G and 12G, every one of them below the box, so the global OOM killer, the one that chose the desktop on 10-24, is never reached by fleet work; `MemorySwapMax` 1G per seat scope keeps a runaway from succeeding by swapping (util_mem_scope.py's measured rule, `MemorySwapMax=0` for a board scope stays); `memory.high` on the sessions' slice (20G) throttles before it kills, which is the right order for interactive work. `memory.events` of every scope is in the ledger, so an oom_kill is a line with a seat's name, never a mystery. The desktop (class LON) carries no cap: it is protected by everyone else's.
- /tmp. The 36 GB are the session scratchpads, one per session under `/tmp/claude-1000/<root>/<session>`, and Lon's rule stands: large outputs die in /tmp, never under a root. THREE MOVES: (1) every harness scratch maker sets `TMPDIR=/tmp/s4e/<seat>` (lib_one_runner.sh and corpus_suite_harness.py export it; mktemp follows), so a seat's harness debris is one directory the census measures and the sweeper names; (2) the ledger carries `tmp_mb` per seat and the banner prints the seat's own figure, so a seat sees its 7 GB before Lon does, and a seat over 4 GB is named in the census's BOX line; (3) `util_tmp_sweep.sh` is KEPT with its cron cadence and its age rules (48 h, dead sessions 6 h for a stood-down seat, mktemp debris 3 h), gains the per-seat directory and the ledger's names in its log, and is re-homed into the batch slice (§ 5); the objdirs stay untouched by it. The finish: /tmp under 60 percent for seven days with the fleet at nineteen.

## 9. What this page forbids

- A `nice`, `ionice` or `cpulimit` anywhere in the harness (invisible across cgroups; the weight is the mechanism). A `cpu.max` hard cap on any seat or class (it idles cores; the weights are work-conserving), except the 10000 weight the quiet slice takes, which is a share, not a cap.
- A pool whose size is read from the load average (a feedback loop with a 60 s lag that oscillates); the pools are fixed counts with per-seat caps and the kernel does the rest.
- A cache without a tree-hash key, a cache read from a dirty tree, a cache that stores a board's verdict (that is results.tsv's), a cache entry written in place (atomic rename only).
- A second ledger or sampler beside LOAD.tsv; a load number in a telegram that is not a LOAD.tsv reading; a `ps`-based per-seat figure (the undercount is measured).
- A ulimit on address space (the collector's PROT_NONE reserve), `MemorySwapMax` left unset on a seat or a board scope, a cap on class LON.
- A calendar: no evening window, no night batch queue; the ROSTER and the weights are the schedule.
- A batch job started outside `util_batch.sh`; a second batch job of one seat; a live oracle outside `util_oracle.sh`; a `make -j` above the seat cap in a script.
- Lon's settings changed by any hand but Lon's running the one script of step 2; a weighted scope or slice created by hand before step 2 has run (§ 10).

## 10. The disclosure of 11:5x CDT: the cpu controller is enabled on app.slice since the cto's measurement

To prove the lever of § 4.2 the cto ran a three-second transient scope with `CPUWeight=50`. systemd enabled the cpu controller on `app.slice` to honour it and left it enabled: `app.slice/cgroup.subtree_control` reads `cpu memory pids` since about 11:45 where it read `memory pids` at 11:29. While that stands and no weights are set, `app.slice`'s children are weighted siblings at 100 each: the one slice holding all nineteen sessions counts as ONE sibling beside every `s4e-mem-*` board scope (six were live at 11:29) and beside Lon's desktop scopes, so under full contention the sessions' interactive work shares about one seventh of the box and the board runs take the rest. The revert is one line, `echo -cpu` into that file; the cto's permission classifier refused the write as a shared-resource change, so it was telegrammed to the ceo at 11:5x and REVERTED by 12:0x (the file reads `memory pids` again, the ceo's word and the cto's read). Step 2 makes the enabled state deliberate with the weights of § 4.2 (the sessions' slice at 600 before any seat scope is weighted); until then nothing below app.slice is weighted, as before. The lesson is written into § 9: a weighted scope is never created by hand on this box outside step 2's script and util_batch.sh.
