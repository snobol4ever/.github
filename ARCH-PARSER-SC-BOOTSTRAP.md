**Standing law the design lives under** (RULES.md, restated in CLAUDE.md): the tree is the pruned parse tree built once by raw Shift/Reduce and the counter stack, and **only `tree_t` crosses to lower**; no global holds a stack (the machine stack is the stack; the CAS and the Prolog trail are the two r12 islands); the lifetime rule (stack for a construct's life, heap for what outlives it); LARGE CHUNKS (one small roll-out with its smoke, then everywhere in the lane, never a second small set); the order of work (suites to 100% first, then speed, then this); the 200-column hierarchy rule for any C written.

**What the rulings fix, in one paragraph.** The seven bootstrap parsers become native code linked into the SCRIP executable (the mode-4 `.s`, not an on-demand reader). Each is a MODULE: a source compiland with its own global namespace, Python's shape. SNOBOL4 keeps `INCLUDE` (one namespace across the includes); Snocone alone gains `IMPORT`. An imported library has no namespace of its own and binds into the namespace of the main parser that imports it. The GVA (the global variable array the emitted code reaches through one base register) is switched per module. The parser is a black box whose only output is the tree. Several parser modules are resident in one process at once (SCRIPtix). Everything else about a linked parser is ordinary slab code.

## 3. THE DESIGN

### 3.1 Vocabulary — pinned so the rest can be exact

- A **compiland** is one source file. A **module** is a compiland that owns a namespace. A **library** is a compiland that owns none: it binds into the namespace of the module that includes or imports it (CEO-1567). A **root** is the compiland the driver or the link step names; a root is always a module.
- A **namespace** is the set of things a name can denote inside one module: (a) the global variable cells (the GVA island and its name→slot table); (b) the procedures, labels and `DEFINE`d functions; (c) the datatype names and the accessor functions `DATA`/`struct` create; (d) `OPSYN`ed operators; (e) the names the by-name roads resolve at run time (`$`, `APPLY`, `CODE`/`EVAL` text, `TRACE`, `DUMP`, `CONVERT`, `DATATYPE`). **Not namespaced** — they are the runtime's, found in the base table by every module: built-in functions and patterns, the keywords (`&FULLSCAN`, `&ANCHOR`, `&TRIM`, `&CASE`, …), `OUTPUT`/`INPUT`/`TERMINAL` and the file units. This split is a **[DESIGN]** choice and the cto's mechanism row confirms it, because it decides hazard H1 and H2 in §3.7.
- Why (c) and (d) are in the list and not optional: `struct tree { t, v, n, c }` and `struct link { next, value }` define functions named `t`, `v`, `n`, `c`, `next`, `value`, and `semantic.sc` `OPSYN`s `~` and `&`. In the one process-wide table those would **replace the host program's own `n`, `value`, `~`** the first time a `CODE()` ran the SNOBOL4 parser. The namespace is a correctness need before it is a tidiness one.

### 3.2 INCLUDE and IMPORT

- **SNOBOL4 `INCLUDE`/`COPY`: unchanged.** A textual splice into the includer's compiland; one namespace across the includes.
- **Snocone `IMPORT`: a library import is a namespace-sharing, once-only, name-located include.** `import <name>;` (a Snocone statement, so it ends with `;`) names a compiland by its stem; it is located on the library path (`bootstrap/` for the parsers, then `corpus/library/`, the two chains `CLAUDE.md` lists), compiled **into the importing module's namespace**, and executed **once per module** however many times it is named (Python's rule). Grammar rule → tree by the pruned-parse-tree law: `import = "import" name ";"` builds exactly one node, `(TT_IMPORT "name")`, at the `;` that completes it, and **the lowerer resolves it** (A PARSER MOVES NOTHING; THE LOWERER PLACES IT): `lower_snocone.c` loads the named compiland through its own language's parser and splices the statements under the importer, as it already rewrites the Snocone tree for `lower_snobol4.c`. **[ASK Lon]** the surface syntax is hq_snocone's strawman — Lon said "IMPORT statements just like Python" and gave no spelling; hq_snocone assumes `import name;` until told otherwise.
- **Qualified access to another module's globals (`M.x`) is NOT part of stage 1.** Lon's analogy is Python, but CEO-1567 settles the library case (binds into the importer), and the parse stage needs no cross-module name reference at all: the C driver reaches a module's entry by a sealed cell (§3.4). `M.x` belongs to the SCRIPtix row; this page reserves the word and builds nothing for it. **[DESIGN]**
- Until `import` exists, stage 1 expresses the chain exactly as `scripts/run_scrip_parser.sh` already does — the library files concatenated ahead of the parser by the build, in the order `bootstrap/README.md` and `util_parser_sc_census.py` declare — and `import` lands as its own row, after the SNOBOL4 smoke has shown the module mechanism works. The chain order then moves from a script into the source. **[DESIGN]** This keeps the first landing free of a grammar change in two parsers (the C Snocone parser that is about to be deleted *and* `parser_snocone.sc`).

### 3.3 The GVA per module

The mechanism is the cto's (row `modules-each-linked-parser-module-has-its-own-gva-island-and-name-table-…`). What the parser stage needs from it, stated as requirements the gate can check, and one placement proposal:

- **R1 — One island per module, one base per module.** Module 0 is the program the user ran, **at `RT_GVA_VA` exactly as today**: no emitted constant, no mode-3 baked address and no `gc_heap.c` window changes for any existing program. Module `i ≥ 1` (a linked parser, a SCRIPtix section's module) takes a fixed stride inside the same reserved 1 GiB window — **[DESIGN]** proposal `RT_GVA_VA + i * 2^27` (8 M cells per module, eight modules: the user, the seven parsers); the cto sizes it (a larger window is a `MAP_NORESERVE` change, not a layout change).
- **R2 — The base is switched at the module boundary, in a frame.** Mode 4's code is already position-independent in `k` (`[r9 + 16k]`, F7), so a module's code needs no relocation: only r9 differs. The entry stub of module M saves the caller's r9 **in its own frame**, loads M's base into r9, **writes the one current-module cell** (`rtccb` slot 6, which the RTCC veneer reloads r9 from after every C call), and the return path restores both. A single "current X" cell is not a stack (NO GLOBAL HOLDS A STACK); a list of saved bases would be one, and is refused. Error exits must restore the cell: the catch sites that `setjmp` for `core_runtime_error` save it before and restore it after, as the Raku block-callback head cell did (CEO-1560). Mode 3 bakes `base_M + 16k` as a compile-time constant per module, so it needs the stub only for the cell.
- **R3 — Every module's island is a collector root.** `gc_heap.c:137` and `:2717` walk a **module table** (`{ base, ncells }[]`, program-lifetime, filled at module registration) instead of the one window. That table holds one entry per *module*, not one per live call, so it is not a second stack.
- **R4 — One name table per module, resolved in the current module.** `gva_register` becomes per module. The by-name roads (e) resolve against the **current module's** table first; a miss goes to the base table of runtime names and **nowhere else** (never into another module). `DEFINE`, `OPSYN` and `DATA` register in the current module's table, so §3.1's accessor and operator collisions cannot happen.
- **R5 — Procedure symbols are module-qualified.** F7 shows procedures leave the assembler as weak globals `Name_α`. Seven modules each carrying `Shift_α`, `Push_α`, `Append_α` would be merged by the linker **silently, into one copy that reads whichever r9 is current** — correct only if every module's library slots coincide, which nothing enforces. The module emitter qualifies every symbol it defines (`<module>$<Name>_α`). The cost is one copy of the library per importer (the library is about 600 of the SNOBOL4 chain's 1370 lines; the exact object growth is a number the first landing records). Sharing one copy of the library across modules by giving every module the same library slot prefix is a possible later optimisation, not a stage-1 design. **[DESIGN]**
- **R6 — The sealed entry cell.** The C driver reaches a module through a cell the module's registration fills (its entry address and base), not through a global name. The cell is the module's *interface*; nothing outside the module learns its internal names.

### 3.4 The module ABI: one entry, one exit, the tree

Each linked parser module M exposes exactly what the driver needs and nothing else:

```c
tree_t *M_parse(const char *src, size_t len, const char *path);   /* NULL on refusal; the diagnostics are §3.6 G2 */
```

- It returns the same root the corresponding `<lang>_compile` writes into `*out_ast` today (F1), so **the lowerer, the driver and the polyglot loader do not change** and `RECORD_SEG`/`MERGE_AST` see the same thing. `sno_parse_ast(FILE *)` becomes a read-the-file wrapper over it; `sno_parse_string_ast` and the `CODE`/`EVAL` road call it directly.
- **Lazy initialisation.** The module body (the pattern graph, F11: 10–20 ms, 4.6 MB) runs the first time `M_parse` is called, never at process start. A mode-4 program that never calls `CODE`/`EVAL`/`read_term` pays nothing; the `scrip` driver pays for exactly the languages it is asked to parse. **[DESIGN]**
- **Per-parse state is reset by the entry, not by the module body.** `InitCounter()`, `InitStack()`, `SnLblT = TABLE(256)`, `Src`, the case flags: the lines today in the driver tail (F5). Resident modules are re-entered many times (every `CODE`), so the reset is part of the entry.
- **Where the entry lives.** The driver tail of each `parser_<lang>.sc` (SNOBOL4: `363-414`) is the entry's body today, interleaved with its stdin/dump loop. **[ASK Lon]** `CLAUDE.md` forbids rewriting a `parser_*.sc` beyond "a few characters" without asking. The proposal: the per-parse setup and match move into one function `ParseOne(Src)` in each file (about 15 lines of the existing tail, moved not written), the standalone dump loop becomes a six-line caller of it, and the linked entry calls the same function — so the five test arms (`test_bootstrap_parsers.py --arm sbl|m3|m4|sc3|sc4`) and the linked build run **the same code** and cannot drift. The alternative that touches no parser file — a build script that slices each file at its first driver-tail line and re-writes the setup in an entry glue file — duplicates the per-language setup seven times and is the drift this paragraph exists to prevent. Until Lon answers, stage 1 assumes the function form and does it for SNOBOL4 only (the small roll-out); the other six wait for the answer, which costs nothing because they are the massive roll-out.
- **Keywords and I/O are saved and restored around the call** (§3.7 H1, H2).

### 3.5 The tree bridge — from the `.sc` `tree` record to `tree_t`

Lon: *"passes all information ONLY INSIDE the TREE"*; the ceo's reading of CEO-1375 adds that the bridge is the `tree()` datatype becoming `tree_t` rather than being printed and re-read. Two ways to get there; the first is the stage-1 bridge and the second is Lon's stated end state, reached by a row that already exists.

- **B1 — EXPORT (the stage-1 bridge).** The entry ends with one runtime builtin, `TreeExport(root)`: a **single recursive walk** over the `.sc` tree that allocates `tree_t` nodes in the compile-time arena (`ct_zalloc`, `ct_strdup`), mapping the name string to the enum through the existing `tt_e_name` table (a reverse hash built once), typing `v` by kind (`TT_ILIT` → `ival`, `TT_FLIT` → `dval`, text kinds → `sval` + `slen`), and filling `line` (§3.6 G1). It is not printed and not re-read: it is a copy of N nodes at the module's exit, the boundary the CEO-1375 text calls "the one bridge the drop-in needs beyond linking". **Zero lines of `tree.sc`, `ShiftReduce.sc`, `tdump.sc` or any grammar change.** Its cost appears on the parse clock the first landing records; the micro-benchmark in §5 M1 says whether it is the dominant cost for tiny `CODE()` strings.
- **B2 — NATIVE (the end state, under performance).** `tree(...)`, `Shift` and `Reduce` allocate `tree_t` directly in the arena and the value stack holds raw pointers (a foreign pointer type the collector does not trace — the tree's lifetime is the compile, which is the arena's). The walk disappears. This is the CEO-1561 row *"replacement, for the purpose of speed, of the counter stack and value stack. That is the PushCounter/PopCounter and the Shift/Reduce"* (Lon, 15:4x CDT): the native Shift/Reduce **is** B2, and the two ideas Lon named (stacks woven through the ζs, or two mmap'd regions) decide where the *stack* lives; the tree nodes' home is separate and is the arena. It changes the bootstrap library, so it is asked of Lon when that row is served, not here.
- **[ASK Lon]** whether B1 satisfies "BECOME `tree_t`" for the first landing. hq_snocone's reading: yes, because nothing crosses but `tree_t` and nothing is serialised; B2 then removes the copy for speed.

### 3.6 THE GAPS — what separates "100% on the parity gate" from "a drop-in that lowers the same"

Each gap names its evidence, its proposed cure, who decides and which gate closes it. **G1 and G2 are the two that would have been discovered only after the C parser had left.**

**G1 — Position bookkeeping (F4).** *Need:* SNOBOL4 and Snocone statements need `:line :lline :file :stno :src` (and `:incl`); Icon, Raku, Prolog and Pascal nodes need `line` on arbitrary nodes (130 reads in `src/lower`). *Why it is a design problem:* the pruned-parse-tree law forbids invented wrapper nodes, and these attributes are `TT_ATTR` children the C parser adds beside the grammar's own nodes. *Proposal [DESIGN]:* position is **node metadata, not children** — `tree_t.line` is already a member of the node — and the lowerer places what is derivable: `:stno` is the statement ordinal (the lowerer, or the exporter, counts it), `:file` is the path the entry was given, and `:line`/`:lline`/`:src` come from **two cursor offsets per statement** (`@` captures at the start and end of the statement rule, a few characters in the Statement rule) turned into lines by the exporter with one newline index of the source, and the source slice taken from the same offsets. For the other languages the same two offsets per command/clause/declaration cover the statement-level reads; node-level `line` reads in `lower_icon.c`/`lower_raku.c` get a per-language census first (`which node kinds' line does each lowerer actually read`), because 49 + 64 reads do not say how many kinds. *Sub-gap G1b:* the `.sc` SNOBOL4 parser expands `-INCLUDE` into one buffer (`pp_out`, F5), so offsets in the expanded text are not lines of the original files; the C path's `stmt_line_is_included` machinery has a line map that the `PP*` functions must also produce. *Decider:* the ceo for the shape (it touches the tree law's edge), hq_snocone for the build. *Gate:* the **IR-identity gate** below.

**G2 — Parse diagnostics.** The C parsers report a message and a line and count errors (`sno_nerrors`, `scrip: N parse error(s) in 'file' -- no code generated`); the `.sc` parsers print `Parse Error.` and nothing else (F5). Suites with expected-error output and `.wantrc` entries can depend on the text and the line. *Proposal:* the entry returns NULL plus the cursor after the last statement that parsed (the `ARBNO(*Command)` stops there), and the driver prints the same `scrip:` line the C path prints with the line derived by the same newline index as G1. Wording of per-token expectations is not promised. *Gate:* the area smoke over the refusal entries of each language's master (`ALL.excluded.txt` and the entries that want a non-zero rc).

**G3 — Process-wide state the module body mutates (§3.7 H1/H2).**

**G4 — Names (R1–R6).** The cto's mechanism row. *Gate:* `test_gate_linked_modules_have_their_own_namespace_and_a_library_binds_into_its_importer.sh` (the row's DONE-WHEN), plus the SCRIPtix witness of CEO-1568.

**G5 — The build cycle (§3.8).**

**G6 — The run-time callers (F2).** `runtime_eval.c:988` and `by_name_dispatch.c:5482` must call the module, so the module lives in `libscrip_rt.so`. `CODE`/`EVAL` in a loop is the hot path (§5 M1).

**G7 — Heap.** Today the C parsers allocate from the compile-time arena, outside the collected heap and outside `-d`. A resident module's pattern graph (F11: 4.6 MB) and a parse's garbage now live in the collected heap and count against the program's declared `heap_kb`. Programs that `EVAL` need a re-measured declaration (RULES.md clause 8 (g): a unit that runs out gets its measured need, two readings). *Gate:* the declared-sizes census after the landing, and §5 M2.

**G8 — Raku.** `parser_raku.sc` is frozen until hq_raku's C parser is stable (Lon 2026-09-27); Raku is last, and the Raku C parser leaves the binary only when `parser_raku.sc` matches it. Nothing in this page waits on it.

### 3.7 Hazards of a parser that lives inside the host program

- **H1 — The module body sets process-wide keywords.** `global.sc` assigns `&FULLSCAN = 1` and `&MAXLNGTH = 16777216`; `case.sc` and `semantic.sc` touch more. Run inside a user's `CODE()`, those would flip the **user's** `&FULLSCAN`, `&ANCHOR`, `&TRIM`, `&CASE` for the rest of the run. *Cure:* the entry saves the keywords it may touch in its own frame, runs the lazy init and the parse inside that bracket, and restores them on every exit including the error exits (the same catch-site discipline as R2). *Gate:* a program sets `&ANCHOR = 1`, `&TRIM = 1`, `&FULLSCAN = 0`, calls `CODE()`, and reads the three back unchanged — both modes.
- **H2 — Fixed I/O units.** The driver tail and `PPOpen` use units 9 and 10 (F5). A host program holding 9 or 10 open would have them closed or read from by `CODE` of a `-INCLUDE` source. *Cure:* the linked entry takes the source text, not a unit, and the include preprocessor reads through units the runtime allocates for the call (or reads the whole file with the runtime's slurp, as the C path does) and releases them. *Gate:* a host program with units 9 and 10 open runs `CODE` of an include-bearing source and its units are intact.
- **H3 — Re-entry.** Different modules re-enter freely (a SNOBOL4 section parsing Prolog text); the *same* module cannot be entered while it is mid-parse, and nothing in the grammars calls user code, so no path does. The entry detects it (a per-module busy flag in the island) and refuses with a runtime error instead of corrupting the counter stack.

### 3.8 Build and bootstrap — the cycle and its seed

- **The small roll-out has no cycle.** The SNOBOL4 chain is a Snocone program; the **C Snocone parser is still in the binary** when `parser_snobol4.sc` is compiled. The build order is: build `scrip` and the runtime without the SNOBOL4 C parser → `scrip --module snobol4 -o snobol4.s` over the chain → `gcc -c` → add the object to `libscrip_rt.so` → relink. That is the Makefile staging §3.10 L1 lands.
- **The massive roll-out hits the cycle exactly once, at Snocone.** `parser_snocone.sc` is compiled by a Snocone parser; when the C Snocone parser leaves, something must compile it. **[DESIGN]** the standard answer, GCC's: **a committed seed** — `SCRIP/bootstrap/seed/parser_snocone.s.xz` (about 0.5 MB, F7; a SHA-256 manifest beside it) assembled into a **stage-0** runtime that contains only the Snocone module. Stage 0 compiles all seven chains; stage 1 is the runtime with all seven modules; **the fixpoint gate** recompiles `parser_snocone.sc` with stage 1 and requires the `.s` byte-identical to the seed (a stale seed is a red with the fix named: `make seed`). Generated parsers are already tracked files with an in-sync gate and a regeneration script (`test_gate_parser_generated_files_in_sync.sh`, `regenerate_parser_and_lexer_from_sources.sh`); the seed is the same class of file. `.s` artifacts "live only beside benchmarks and demos, never as pinned goldens" (CLAUDE.md): a seed is **a build input, not a golden** — no test compares output to it — **[ASK ceo]** to confirm the class.
- **F12 sets the order inside a clean build:** stage 0 → compile `ipp.icn` and every other build-time `scrip` use with the stage the language's parser lives in. Until the Icon C parser leaves, `ipp.icn` is built by the C Icon parser as today; after, by the Icon module in stage 0 or 1 (stage 0 loads the Icon module too, so `ipp` builds before stage 1). The list of build-time uses is a measured census owed by the first Makefile landing (`grep` for `scrip --compile` in rules).
- **The fallback if the seed is refused:** keep `src/parsers/snocone/` as a build-only tool (`scrip-seed`, never shipped in `scrip` or the library). It keeps C parser source alive forever, which cuts against Lon's goal of replacing all the C-written parsers, so it is the fallback, not the plan.
- **The driver gains one flag:** `scrip --module NAME -o NAME.s src.sc` emits the module form of a chain — no `main:`, the qualified symbols of R5, a registration record `{ name, base, entry, names[], n }`, `M_init` (the module body, called lazily) and `M_parse`. It is a shared-node change (driver, emitter): landed with its control arm and named in the commit (RULES.md § SHARED-NODE VERDICT SCOPE). It uses the cto's registration API; the page of that API is the cto's reply to §4.

### 3.9 Where the CEO-1561 rows fit

The counter-stack and value-stack replacements ride under this row (CEO-1566). ## 5. MEASUREMENTS OWED BEFORE L1 LANDS (each is a number this page does not have)

- **M1 — `CODE`/`EVAL` in a loop.** SNOBOL4 programs that `EVAL` or `CODE` short strings a hundred thousand times are common in the benchmarks, and the C parser costs microseconds a call. The `.sc` module's per-call cost is the per-parse reset (F5), the match, and the export. A micro-benchmark of 100,000 `CODE('X = X + 1')` against the C parser, **before** the C parser is deleted, decides whether L1 needs a small-string fast path (cache by text, which `eval_string_transient` may already do) or B2. The 2.9x of F13 is a large-file ratio and is not evidence about tiny strings.
- **M2 — Resident cost and the heap cap.** Minimum `-d` at which each module's init succeeds, and the object growth of the library duplicated per module (R5): `size` of the seven objects after L2, against today's `libscrip_rt.so` of 41.3 MB. F7's 5.7 MB per object suggests 30–40 MB more at `-O0`; if that is wrong the page says so.
- **M3 — The node-kind census for G1:** which node kinds' `->line` each of `lower_icon.c`, `lower_raku.c`, `lower_prolog.c`, `lower_snocone.c` reads. Counting reads (130) does not say how many positions the parsers must stamp.
- **M4 — Build-time `scrip` uses** (F12): every Makefile rule that runs `./scrip` on a non-`.sc` source.
