The two stated hypotheses require runtime state (a global's value across two calls; whether a stub is reached at all) that an asm diff of the two call shapes cannot show — the baton's gdb-first instruction was correct and is why the actual mechanism, three layers deeper than either hypothesis, was findable at all.

Breakpointed the actual crash from the top with `break main` first (so the runtime `.so`'s symbols resolve before setting further breakpoints — a repeated procedural note from this same investigation, see below) and traced forward. Neither `rt_g_want_name` nor `rt_frame_prep` were ever touched on the failing path — mode-3's `APPLY('double', 21)` does not go through `_usercall_hook`/`rt_call_named_proc` at all (the path the original ADDENDUM traced); at current HEAD it goes through `by_name_dispatch.c:7027`'s `BID_APPLY` fast case straight into `rt_call_proc_descr`, a different, newer dispatch route. The old trace was accurate for the tree it was taken on; the tree had moved.

## Root cause, in the order it was actually uncovered

1. **`rt_call_proc_descr("double", ...)` finds a REAL `g_rt_gen_procs` entry for "double"** — not a bare `_func_buckets` alias (gap 2/3's territory). `lower_snobol4.c:2398`'s static-OPSYN-fold prescan (`sno_prescan_expr`, triggered when both `OPSYN` arguments are literal) clones "twice"'s `sno_def_t` under the alias name, preserving `entry`/`result_name` — so `double`'s clone gets its own `rt_proc_t`, same `dyn_scope=1`/`frame_bytes=48`/`jmp_entry=1` shape as `twice`, `result_name="twice"`, and its own tiny α-port stub (compiled via `bb_proc_entry`→`IR_GOTO_DEFERRED`→`bb_goto_deferred.cpp`'s DEFINE-FOLD arm) that correctly redirects, via the `body$twice` AB cell, into `LBL__twice` — the one real compiled body. This part works: entering `double`'s stub does land in `twice`'s real arithmetic, args read correctly.
2. **`double`'s "alpha$double" fast-path cell is never sealed.** `bb_ab_seal_entry_cells(pname, fnbase, alpha_face=1)` (`bb_define.cpp:38`) looks up a label literally named `"<pname>_α"` via `emit_label_lookup_offset` and silently no-ops if it's not found. That label is only ever emitted by `bb_call_proc_staged.cpp`'s "laz" signature machinery — which runs once, the first time a proc has a *compiled call site* (`bb_tiny_shim_ok` gates it, itself gated in part by `scc_taint_graph`'s **correct, intentional, whole-program** SCC decline the instant any 2-arg `OPSYN` appears, in `optimizer/proc_collect.c`). `double` is only ever invoked dynamically (`APPLY`) in this witness — it never gets a compiled call site, so its `_α` label — and by extension `twice`'s, once OPSYN is present anywhere in the program, confirmed independently below — never gets minted, regardless of SCC. `rt_dyn_alpha_fn_p` correctly reports this as unsealed (falsy) and `rt_call_proc_descr` correctly falls back.
3. **The fallback (`return rt_proc_enter(rt_dyn_alpha_fn_p(p, name, (void*)p->fn));`) is the actual bug.** `rt_proc_enter` (`rt.c`, hand-written asm) pushes 5 callee-saved registers + 2 continuations, jumps into `fn`, and its own `"2:"`/`"3:"` labels call the **plain** `rt_proc_call_epilogue_γ`/`_ω` (`DESCR_t frame0` / `void`) — no name, no g_name_save unwind. But `rt_proc_call_open` (called unconditionally just above, on **every** path through `rt_call_proc_descr`, not only the `!dyn_scope` arm) already ran `rt_proc_call_prologue`, which shadow-pushes the callee's own name (`"twice"`, via `p->result_name`) onto `g_name_save` for a fresh per-call `rcell` — SNOBOL4's `PROC = value` convention writing under that shadow, not under a global. Unwinding that shadow and reading the result back by name is **entirely** `rt_proc_call_epilogue_named_γ/_ω`'s job (`rt_proc_epilogue_named`, `rt.c:1292` — the same function gap 3 already made alias-aware) — work the plain epilogue never does. Confirmed against the working case: the compiled call site's own emission for `double(21)` (`bb_call_proc_staged.cpp`, direct syntax, `--compile`'d and read) does the identical push/jmp shape but calls the **named** forms.
4. **`rt_proc_enter`'s own `"2:"`/`"3:"` additionally do `addq $16, %rsp` before their five pops — this is itself only correct for a callee that jumps to `"2:"`/`"3:"` directly**, consuming nothing first. A dyn_scope body instead exits through the shared SNOBOL4 `":(RETURN)"` label, which does its own `pop rcx; add rsp,8; jmp rcx` *before* landing at the continuation — already consuming the two pushed slots. Copying `rt_proc_enter`'s `"2:"`/`"3:"` verbatim into a first attempt at a named variant reproduced this exact double-consumption: every subsequent pop read one slot stale (traced live — `rt_proc_call_epilogue_γ`'s own return address showed up as `0x44e270`, the literal address of the C string `"double"`, the alias name pointer that happened to be sitting where the corruption walked into). Removing the extra `addq $16` (verified against the exact push order, by hand and by re-deriving where RSP lands after `RETURN`'s own two-slot consumption) fixed it.
5. **Not every dyn_scope proc reached through this fallback exits through `":(RETURN)"`.** `pattern_match.c`'s embedded deferred-expression procs (`rt_defer_get_pat_dtp`/`rt_defer_probe_run`, compiler-synthesized names like `"EXPR$53"`) are *also* dyn_scope, *also* reach `rt_call_proc_descr`'s fallback (they have no compiled call site either, for an unrelated reason — see below), and their bodies exit through their own γ/ω port directly, not through the shared label — they need the **plain** `rt_proc_enter`, unchanged. Measured live: `demo_porter` regressed under an unconditional switch to the named form (`*EXPR$53` inside a pattern, SIGSEGV; `name` argument corrupted to `0x100000000` by the time it reached `rt_proc_epilogue_named`, a knock-on of the same wrong-consumption-count question applied to the wrong callee shape). The dispatch already carries a working convention for exactly this: `rt_call_named_proc`'s own pre-existing fast-path already declines to even attempt the alpha lookup when `strchr(name, '$')` — synthetic/internal names. Reused the same test to choose the epilogue.

## Fix

`src/runtime/rt/rt.c`:
- New hand-asm `rt_proc_enter_named(void *fn, const char *name)`, byte-identical to `rt_proc_enter` except: `name` (2nd arg) is stashed in one extra pushed slot ahead of the usual five registers (popped back into `rdi` at the continuation, before the two `!p->dyn_scope` `"2:"`/`"3:"` labels); the `addq $16, %rsp` is **not** present (see point 4); the continuations call `rt_proc_call_epilogue_named_γ/_ω` instead of the plain forms.
- `rt_call_proc_descr`, `rt_call_named_proc`, `rt_call_proc_direct` (the three call sites sharing the "dyn_scope, `rt_proc_call_prologue` already ran, then `rt_proc_enter(p->fn)`" shape): fallback now reads `(name && strchr(name, '$')) ? rt_proc_enter(p->fn) : rt_proc_enter_named(p->fn, name)` (`rt_call_proc_direct` has no `name` argument of its own; uses `p->name`).

Nothing about `rt_dyn_alpha_fn_p`/`rt_dyn_alpha_fn`/the fast path changed — the fast path's own behavior (and the deeper "why doesn't OPSYN's presence let *any* proc's `_α` label mint" emission-level question in point 2) is untouched, unexplained further, and is its own follow-up if HQ wants it — this row's DONE-WHEN is a correctness fix at the dispatch layer, not an optimization-restoration one.
