# PROPOSAL 2026-08-27 (seat05) — row `table-int-keys-and-nd-subscript` defect (3): a semantics argument for narrowing `.NAME`'s string representation, put to Lon per the brief's own "ask, do not decide"

This is the row's brief's own outstanding requirement for defect (3): *"whether `.NAME`'s string representation (descr.h slen==0 with `.s`) can be narrowed is a semantics question, not a perf question — measure its cost first, then put the proposal to Lon with the semantics argument written out."* The measurement is done (`FINDING-2026-08-27-seat05-nd2-subscript-narrowed-and-name-indirection-measured.md`: `$`-indirection costs ≈2.97x total Ir / ≈4.43x loop-body Ir vs. direct variable access). This is the semantics argument. **It is a proposal, not a decision — nothing below has been implemented.**

## The three representations, and one of them is dead code today

`descr.h`'s `DESCR_t` for `DT_N` (`.NAME`) has three shapes, distinguished by `.slen`:
- `slen==2` — `NAMETRAP`: `.p` is a pointer to a `VCELL_t` (table/array element references — the LVALUE nametrap mechanism, e.g. what `A[i,j]`'s assignment target resolves to). Heavily used throughout `pattern_match.c`.
- `slen==0` — `NAMEVAL`: `.s` is a C string. This is what `$expr` (indirect reference) always constructs — confirmed via `--dump-ir-verbose`, `$nm` lowers to `IR_CALL "SNO$NAME"` unconditionally, for *every* `$` use, not only the explicit `NAME()` builtin. Resolving it requires a hash lookup (`NV_GET_fn`/`_var_hash`/`_var_bucket_find`).
- `slen==1` — `NAMEPTR`: `.ptr` is meant to be a **direct pointer to an already-resolved `DESCR_t`**, per its macro (`core.h:24`) and its four consumers (`pattern_match.c:933,1060,1079,1141`, all `if (IS_NAMEPTR(val)) val = NAME_DEREF_PTR(val);`). **Grepping the entire runtime for anywhere this actually gets *constructed* (`NAMEPTR(`, or a literal `.slen = 1` on a `DT_N` value) returns zero matches.** The fast path is fully designed into the type system and its consumers — and has never been wired up by any producer. It is dead code today, not a hypothetical.

## Where the cost actually goes, and why that reframes the question

Session 2's profile decomposed the ≈2.97x total-Ir cost into two layers:
1. **≈42%, the larger share**: `try_call_builtin_by_name_bl` and its argument-marshaling (`rt_call_arr_impl`/`rt_call_arr_bl`) — `$`'s *own* dispatch, reaching its `SNO$NAME` implementation through the same generic "call a builtin by its string name" mechanism used for ordinary user-visible builtin/procedure calls. This is a **pure implementation/dispatch question, not a semantics one** — `$` already has fully-defined SNOBOL4 semantics regardless of how its own implementation is reached. hq_P has independently minted `perf-call-by-name-census-and-rank` to census this exact mechanism class (three sites found the same day, this row's being one). **That row owns this 42%; nothing here needs to relitigate it.**
2. **≈36%**: `rt_sno_indirect_name`/`bn_sno_name`/`NV_GET_fn`/`NV_SET_fn`/`_var_hash`/`_var_bucket_find` — the actual name-string-to-storage-location resolution. **This is the part the brief's semantics question is actually about**, and it's where `NAMEPTR`'s dead fast path is relevant.

## The semantics question, stated precisely

SNOBOL4's `$X` means "the variable named by X's *current* value, evaluated now." A naive "resolve once, cache forever" optimization is **unsafe**: `X = 'A'; $X = 1; X = 'B'; $X = 2` must resolve to two different variables, and any cache that doesn't account for X's value changing would silently produce wrong answers — this is exactly the kind of mistake `.NAME`'s current always-re-resolve design avoids by construction. So the question is not "can we cache" but **"can we cache correctly, at what granularity, and what does correctness require us to verify first."**

**The proposal:** per-call-site memoization, not global or program-lifetime caching — analogous in shape to the existing `_var_find_cached`/`SCRIP_NV_MEMO` mechanism (`core.c:2273`, measured the same day by `FINDING-2026-08-27-seat01-nv-set-fn-memo-payoff-confirmed-and-accounting-gap-characterized.md` as a decisive 1.51x native win for `NV_SET_fn`'s *own* by-name resolution — same disease, a precedent that a memo-shaped cure works here, though that memo does not currently cover `.NAME`'s indirection path, per session 2's profile still showing the full hash-chain cost). Each **static** `$`-indirection site in the compiled program would remember the last string it resolved and the `NAMEPTR` it resolved to; on the next evaluation, compare the current indirect-name string against the remembered one (cheap, and *correctness-preserving even if never true* — a miss just falls back to the existing full resolution) and reuse the cached pointer only on an exact match. This is strictly additive to the existing `NAMEVAL` path, not a replacement of it — `NAMEVAL` remains necessary whenever the indirect name genuinely varies (the case the cache can't help), and stays the semantically-correct fallback.

**What would need verifying before implementing this — explicitly not verified by this proposal, that's the "ask" part:**
1. **Storage stability.** The cached `NAMEPTR` is only safe across iterations if the resolved variable's storage address doesn't move (no compacting/relocating GC on the NV/GVA dictionary itself) for as long as the cache is held. This needs a direct check against the current GVA/NV dictionary implementation, not an assumption — the project's own `zeta_heap`/GC work has moved storage models before (`ARBLK_t`'s recent rewrite away from cell-pointer aliasing per `core.h`'s own comments is exactly this class of bug, cited there as a cautionary precedent for *table* cells; the analogous question hasn't been asked for the NV/GVA variable table).
2. **Cache granularity and lifetime.** Per-call-site (keyed on the specific `$`-expression's location in the compiled code) is the safe default — it never needs cross-site invalidation. Whether it should survive across procedure re-entries/recursion (a call site inside a recursive procedure resolving a *local* name would need the cache scoped per-activation, not per-static-site) is a real question this proposal does not resolve; the conservative starting scope is "top-level/global-name indirection only," which is also SNOBOL4's most common `$`-usage pattern in practice (dynamic dispatch tables, `$('ROW' i)`-style constructed names against globals).
3. **String comparison cost.** SNOBOL4 strings in this runtime aren't interned/pointer-comparable in general, so the cache-hit check is a `strcmp`-class comparison, not a pointer compare — cheaper than the full hash+bucket-search chain it replaces, but not free, and its cost should be measured against the *hit rate* in real programs before claiming a net win. No such measurement exists yet.

## What this proposal is not

Not a claim that this is worth doing — that's Lon's call, per the brief. Not an implementation — nothing in this row's fix (defect 2, landed the same session) touches any of this. Not a claim that 36% is the "right" number to chase first — `perf-call-by-name-census-and-rank`'s 42% arguably dominates it, and per that row's own framing, cures are scoped as child rows *after* its census, not decided ad hoc per-defect. If Lon wants this pursued, the natural next step is a child row under `perf-call-by-name-census-and-rank` (or a sibling to it) that first answers verification item 1 above (storage stability) before writing any cache code, since that's the one item that determines whether this is safe at all rather than merely a performance tradeoff.
