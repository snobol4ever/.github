# FINDING 2026-08-29 seat10 — the emergency optimizer bypass (SCRIP_OPT=0/SCRIP_ZD=0) exposes a LATENT, unenforced invariant in the compiler's shared call/return CONVENTION (not one function) that the default path only survives by coincidence of constant-folding. 176/1494 (11.8%) and 291/1494 (19.5%) of the graded SNOBOL4 corpus regresses under it; three crash sites traced, all the same root cause (a fixed byte count trusted to unwind a call, nothing verifies actual depth) at three different implementers of the convention: bb_define.cpp's floater, a per-function saved-continuation slot, and the rt_proc_enter runtime helper. ⭐⭐ **REFRAMING, added on hq_P's explicit request (they said this belongs first, and they are right): the "s64 RSP-ONLY: depth IS the anchor" invariant in `bb_define.cpp` is not actually enforced anywhere — it is only ever satisfied by coincidence of what the optimizer happens to fold away.** The default arm's witnesses PASS not because the floater is correct, but because the specific comparisons/expressions involved get constant-folded down to zero accumulated stack depth before the transfer. **`SCRIP_OPT=0` is not a broken path beside a working default — it is the same latent, unenforced invariant with the optimizer's coincidental cover removed.** hq_C, independently, reached the same conclusion from the code's own history: the comment `"depth IS the anchor"` states an invariant nothing checks, and "every successful run confirms the comment and none of them tests it." ## ROOT CAUSE FOUND FOR A REAL SLICE OF THE SCRIP_OPT=0 CLASS (added 2026-08-29, later same session)

Minimal witness (4 meaningful lines, ablated from `user_function_branch_6`, opt0-only in the census):
```snobol4
        DEFINE('failer(a)')                        :(main)
failer  EQ(a,1)                                     :F(FRETURN)
        failer = 'x'                                :(RETURN)
main    failer(2)
END
```
Default: PASS. `SCRIP_OPT=0`: SIGSEGV, in both mode-3 (`--run`) and mode-4 (`--compile` + real ELF, confirmed with a core dump) — this is a genuine codegen defect, not a JIT-only artifact.

**gdb, `rip=1` at the crash** (a jump to a literal small integer, not a code address) — the corrupted backtrace is full of small integers (1, 2, 3...) matching exactly the `mov r11, N` port-state tags visible in the `.s` output. Traced with breakpoints at the call site and at the `FRETURN` label:

| arm | rsp at call-entry | rsp at `FRETURN` | delta | `[rsp+8]` at `FRETURN` |
|---|---|---|---|---|
| default (works) | `0x7ffffffee070` | `0x7ffffffee070` | **0 bytes** | `0x40140f` = valid code addr (`n1_define_bx+472`) |
| `SCRIP_OPT=0` (crashes) | `0x7ffffffee0d0` | `0x7ffffffee030` | **160 bytes** | `0x1` = garbage |

**Exact mechanism, confirmed by reading `src/templates/bb/bb_define.cpp:562-580`:** `RETURN`/`FRETURN`/`NRETURN` are emitted as a shared "floater" trampoline, gated by `fnrbp()` (line 383: `static int fnrbp(void){... v = e?atoi(e):2; if(v==1)v=2; if(v<0||v>2)v=2; return v;}` — confirmed by hq_C's own prior sweep, `FINDING-2026-08-26-hq_C-fnrbp-clamp-dead-arms-the-class-has-one-member.md`, that this returns only 0 or 2, never 1). The default (`fnrbp()==2`) path is labeled in its own source comment **"s64 RSP-ONLY: depth IS the anchor"** — i.e. it assumes the `{gamma,omega}` continuation pair sits at a FIXED, PREDICTABLE offset from whatever `rsp` happens to be at the moment `RETURN`/`FRETURN` executes, with NO frame pointer or saved-depth record to correct for drift. The codebase's own alternate arm (`fnrbp()==0`, reachable via `SCRIP_FN_RBP=0`, never used by default) is explicitly a **"BOMB — coming-out frozen... UNKNOWN STACK DEPTH: the rsp-resident record cannot be found from here without a frame anchor"** — i.e. the original design already knew "depth IS the anchor" is an assumption that can fail, and built a deliberate loud-abort fallback for exactly that case. hq_C's 2026-08-26 sweep verified the *default build* is byte-identical before/after removing dead `==1` arms — it never exercised `SCRIP_OPT=0`/`SCRIP_ZD=0`, so it never tested whether the `==2` assumption itself holds under the bypass.

**Why default silently gets away with it:** `EQ(2,1)` is fully constant-foldable, so the optimizer eliminates essentially all the intermediate expression-evaluation temp allocations between the call and the `:F(FRETURN)` transfer — by the time `FRETURN` runs, accumulated stack depth is back to exactly what it was when the `{gamma,omega}` pair was arranged, so "depth IS the anchor" holds *by coincidence of what got folded away*, not by any enforced invariant. With `SCRIP_OPT=0`, nothing gets folded: the call site's own temp frame, the callee's function-entry frame, and the `EQ` comparison's argument-evaluation temps all stay separately stack-allocated, so 160 bytes of depth have accumulated by the time `FRETURN` fires — `FRETURN`'s fixed 16-byte unwind (`add rsp,8; pop rcx`) reads 144 bytes short of where the real continuation pair lives, pulls a leftover temp value (`0x1`, `0x3`) instead, and jumps to it.

**Scope of this specific mechanism:** confined to `bb_define.cpp` (grep for "depth IS the anchor"/"RSP-ONLY" across all of `src/templates/bb/` returns only this one file) — it explains `RETURN`/`FRETURN`/`NRETURN` transfers specifically, i.e. very plausibly most/all of the `user_function_*` family in the regression lists (both `SCRIP_OPT=0` and `SCRIP_ZD=0` examples included several), but almost certainly NOT the whole 176/291 — the two arms disable different amounts of optimization and the census's own overlap data (only 45 shared) already said this reads as more than one cause.

**NOT fixed, deliberately.** This is a documented architectural tradeoff (RSP-ONLY over a frame-pointer scheme), not a typo — a correct fix is either (a) make every box that can transfer control to `RETURN`/`FRETURN`/`NRETURN` first unwind its own accumulated temp depth (audit surface: any box implementing a goto-field transfer reachable from inside a `DEFINE`d body — plausibly larger than `bb_define.cpp` itself), or (b) give the floater a way to find the true anchor independent of accumulated depth (reopens the RSP-ONLY-vs-frame-pointer design decision this file's history suggests was made deliberately). Either is real design/implementation work, not a quick patch, which is directly relevant to the doctrine question (fix vs. delete) still open with ceo. Related: `GOAL-SNOBOL4-100.md` R-7 (`rung-fnrbp-clamp-dead-arms`, the owning rung for this function) — flagged to hq_C, who did the 2026-08-26 sweep and knows this code.

## SECOND MECHANISM FOUND, IN SCRIP_ZD=0 — SAME ARCHITECTURAL SHAPE, DIFFERENT SITE

Minimal witness, already this small in the corpus (`user_function_10`, zd0-only in the census, no ablation needed):
```snobol4
DEFINE('f()') :(fmain);f OUTPUT = 'in f' :(RETURN);fmain f(); OUTPUT = 'back' :(END);END;
```
Default prints `in f` / `back`. `SCRIP_ZD=0`: prints `in f`, then SIGSEGV (confirmed mode-3 and mode-4/real-ELF/core-dump, same as the first witness).

This time `rip` at the crash is a *valid* code address (`n1_define_bx+292`, inside the `f_γ` continuation) — not garbage. Disassembly at the fault: `mov rcx,[rsp+0x20]` then `mov rdx,(rcx)` — the second instruction faults because `rcx` holds `0x400000002` (a tagged inline SNOBOL4 scalar — type-tag/value pair — not a pointer), dereferenced as one anyway.

Traced why: `f_α` (function entry) saves the call site's own "what to jump to on success" pointer at a fixed offset, `[rsp+32]`, immediately after allocating its 48-byte frame. `f_γ` (the success continuation, reached via the shared `RETURN` floater once the function body completes) re-reads that same fixed offset, `[rsp+32]`, assuming it is still valid. Measured directly with gdb, breakpointing at `f_γ`'s entry in both arms:

| arm | rsp at `f_γ` entry | `[rsp+32]` | resolves to |
|---|---|---|---|
| default (works) | `0x7ffffffee0a0` | `0x4014b2` | `n8_call_bx+27` — a real code address (the call site's own continuation) |
| `SCRIP_ZD=0` (crashes) | `0x7ffffffee0b0` | `0x400000002` | garbage (tagged scalar, not an address) |

**This is the same architectural shape as the `SCRIP_OPT=0`/`FRETURN` mechanism above — a fixed offset relative to a function's frame-entry `rsp` is trusted to still hold cross-call saved state, with nothing tracking or correcting for whatever stack depth accumulates in between — but it is a DIFFERENT specific code path** (`RETURN`'s own continuation-pair pop succeeds here and correctly lands at `f_γ`; the corruption is one level further in, inside `f_γ`'s own re-read of its saved call-site pointer). This is consistent with, and gives a mechanism for, the census's own DIRECTION finding: `SCRIP_OPT=0` and `SCRIP_ZD=0` disable different specific optimizations, each of which happens to keep a DIFFERENT one of these fixed-offset assumptions satisfied by coincidence — so the two flags' regression sets are mostly disjoint (different assumptions broken on different programs), but both are instances of one underlying architectural pattern in `bb_define.cpp`'s function-call machinery, not two unrelated bug families.

⛔ **Not proven for the general population** — this is two rigorously-measured witnesses (one per flag), not an audit of all 176+291 entries. Treat "these two specific fixed-rsp-offset assumptions" as a strong, evidenced hypothesis for *a large plausible chunk* of both defect classes (anything shaped like `user_function_*`/`indirect_*`/`defer_*` in the regression lists), not a proof covering every entry — the 129 non-crash wrong-output entries in particular are a different symptom and remain unexamined.

Sampled 16 more crash witnesses (8 `SCRIP_OPT=0`-only, 8 `SCRIP_ZD=0`-only) with a cheap classifier (extract, compile, run under gdb, capture only the crash frame — not a full trace) to see whether they land in the same two already-found sites or somewhere new:

- **4/8** (`keyword_replace_branch_1`, `indirect_keyword_replace_branch_3/5`, `keyword_replace_branch_2`) could not be tested this way — they use `-INCLUDE`, which the bare-`extract`-then-compile path can't resolve (the same tooling gap already flagged to hq_B; not a new finding, just re-encountered).
- **4/8 additional `SCRIP_ZD=0` witnesses** (`user_function_11`, `user_function_apply_1`, `user_function_apply_2`, and `user_function_apply_3` at a nearby-but-distinct offset) crash at a VALID address in the `0x4013a3`-`0x4013ae` range of `n1_define_bx` — same signature as the `f_γ` mechanism above (the exact offsets cluster tightly because this is generic call/return glue, not user code).
- **A THIRD, DISTINCT lead, not root-caused**: `indirect_branch_2` and `len_indirect_1` (`$`-indirect-reference programs, one combining it with deferred `*` evaluation) both crash at the exact same address, `0x00007ffff484f511` — which is just PAST the end of `libscrip_rt.so`'s own mapped/symbol range (`ld-linux` reports the library's live range topping out at `0x...78adf2`; the crash is at `0x...84f511`). The bytes there disassemble as nonsense, confirming it's not a real code path — same general family as the other two (a computed jump target holding garbage instead of a real address) but a DIFFERENT specific site: this one is near the runtime library boundary, likely a deferred-evaluation dispatch mechanism rather than the `bb_define.cpp` call/return glue. `defer_branch_2` (deferred evaluation without indirection) crashes jumping to a stack address rather than a tiny integer — plausibly a variant of the same lead, also not traced.

**Net picture**: the two root-caused mechanisms above account for a real, substantial share of the tested crashes (8/16 sampled, all `user_function_*`-shaped). At least one more distinct mechanism exists (indirect/deferred-evaluation-shaped), evidenced but NOT traced to a specific line of source — that would need its own gdb session starting from wherever `*$(...)` or bare `$(...)` gets lowered/evaluated at match time (candidates by name: `bb_deref.cpp`, `bb_match_defer.cpp`, `bb_match_value.cpp`, `bb_indirect_assign_var.cpp` — not confirmed). ## THIRD LEAD TRACED — NOT A THIRD BUG, THE SAME ONE VIA A THIRD TRIGGER

Traced `len_indirect_1` (`N='V'; S='xyz'; S LEN(1) . *$N =; OUTPUT='[' V ']';`, `SCRIP_ZD=0` crash) to completion. The `*$N` (deferred indirect reference) compiles to a SYNTHESIZED helper function, `FN__EXPRNM$0`, emitted through `bb_define.cpp`'s ordinary function machinery (`n0_define_bx`, α/γ/ω ports — a compiler-generated function is still a function). It is invoked not via an inlined call site but via a hand-written runtime helper, `rt_proc_enter` (`src/runtime/rt/rt.c:1559-1602`), whose own comment states the mechanism explicitly: **"push omega/gamma continuations, jmp into fn — the compiled body pushes into `:(RETURN)`'s shared pop-and-jmp."** This is the identical push-two-then-jmp protocol as `bb_define.cpp`'s inline call sites (`failer_α`/`f_α` above) — `rt_proc_enter` is a second, C-callable implementation of the same convention, used for calls the compiler generates dynamically rather than inlines.

Measured: `EXPRNM$0`'s own local γ-jump (`jmp qword ptr [rsp]`, its shorthand for "go where I was told") correctly resolves to `rt_proc_enter`'s "2:" epilogue label in BOTH arms — that specific jump is not the fault. The corruption shows up one level further: single-stepping into `rt_proc_enter` under `SCRIP_ZD=0`, the backtrace already contains a small-integer garbage frame (`0x2`) below it, before `rt_proc_enter`'s own `addq $16,%rsp` epilogue even runs — meaning whatever depth `EXPRNM$0`'s own body (its `n1_lit_string`/`n2_call`/`n3_var`/`n4_assign` sequence) left on the stack was never accounted for, so `rt_proc_enter`'s epilogue (which, like the floater and like `f_γ`, assumes a FIXED byte count to unwind) discards the wrong bytes and corrupts the register/return state one level further up the chain.

**Conclusion: there are not three defects. There is one architectural weakness — a fixed byte count trusted to unwind a call, with nothing tracking or verifying actual accumulated depth — instantiated at (at least) three sites that all implement the same `:(RETURN)`/`:F(FRETURN)` convention**: the shared global floater (mechanism 1), a per-function saved-continuation slot (mechanism 2), and this runtime-helper epilogue (mechanism 3, reached whenever the compiler synthesizes a function rather than inlining a call — deferred evaluation is one trigger, there may be others, e.g. `bb_call_proc_staged.cpp` is name-checked in `rt_proc_enter_named`'s own comment as using the identical shape). A fix aimed only at `bb_define.cpp`'s inline call sites would leave this and any other `rt_proc_enter`-mediated call vulnerable — the fix needs to cover the CONVENTION, not one emitter of it.
