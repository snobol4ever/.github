# FINDING 2026-09-04 (seat11, FLEET-16) — the PAT suite's own SCORE.md write was silently REFUSED every run on a stray `;`

**CLAIM.** `scripts/test_pascal_pat_suite.sh` looked like a working, green-tail suite runner: it printed `PAT_SUITE_BOARD total=427 m3_pass=... m4_pass=...` and a reds list exactly as designed. It had nevertheless not written a single byte to `.github/SCORE.md` since (at least) the row's most recent prior measurement on 2026-09-03, because its own call into `util_score_row.py` was refused on every single invocation. A runner whose primary output looks correct is not evidence its side effect landed — this is the same failure shape as `FINDING-2026-09-04-ceo-crlf-came-back...`: the mechanism that should catch the defect (a parse check there, a glance at the printed board here) is exactly the thing that keeps passing while the real effect fails silently downstream of it.

**MEASURED.** Running `bash scripts/test_pascal_pat_suite.sh` on origin (SCRIP pre-fix, tree carrying commit `ae9ebfc2`) printed the full PAT_SUITE_BOARD as expected, then, several lines further down, past where a normal skim stops reading:
```
REFUSED(2) util_score_row: a ';' in the cell text is merge_clause's own clause delimiter and will silently fragment on the next write to this cell -- use '·' or ',' instead
```
`.github/SCORE.md`'s pascal-row PAT cell was confirmed stale against this measurement (still carrying the 2026-09-03 22:30 CDT hq_T reading) both before and after re-running the unmodified script twice.

**ROOT CAUSE.** `scripts/test_pascal_pat_suite.sh:101` (pre-fix) built the `--text` argument to `util_score_row.py write` as:
```
... 427 are REJECTION tests graded on whether scrip refuses them; `test_pascal_pat_suite.sh`
```
`util_score_row.py`'s `merge_clause` uses `;` as its own field delimiter when folding a new sentence into an existing multi-sentence cell, so a literal `;` inside the incoming text is indistinguishable from a delimiter and the writer refuses rather than risk silently corrupting the cell on its *next* write. The refusal is correct and working as designed — the defect is that a suite runner's own prose happened to contain the one character its downstream writer treats as structural, and nothing about the runner's primary printed output (the PAT_SUITE_BOARD line, the reds list) reflected that the write beneath it had failed.

**CURE (landed).** SCRIP `65346371`: `; \`test_pascal_pat_suite.sh\`` → `, per \`test_pascal_pat_suite.sh\`` — one line, no behavior change to the suite's own grading logic. Verified by rebuilding (`make`, incremental) and re-running the suite: the `REFUSED(2)` line is gone and `.github/SCORE.md` written cleanly. `.github` `dd8bff4b` carries the resulting pascal-row PAT cell refresh (m3 298/427 · m4 284/427, provenance `SCRIP db330110/65346371`, superseding the stale 09-03 reading). No gate exists yet that would catch a *different* runner making the same mistake — `util_score_row.py`'s refusal is the only line of defense today, and it only fires if a human (or a seat) reads past the primary board output to the writer's own tail.

**THE LESSON.** A test runner's success is usually judged by its headline output (did the board print, did the numbers look sane) — but a headline can be perfectly correct while a *side effect two calls deeper* silently fails, and the failure mode here (a refusal message printed and then ignored because the reader already got what they came for) requires no bug in the writer at all, only a reader who stops looking once the interesting number is on screen. Same family as the CRLF finding: the thing that should have made this loud (the writer's own REFUSED line) was in fact loud — it just was not load-bearing on anything that would stop a session from calling the run complete. Worth asking, for every suite runner in this fleet: does anything actually fail the run (non-zero exit, a gate) when its own leaderboard write is refused, or does the run print success and move on regardless?
