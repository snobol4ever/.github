## THE HEADLINE

**roman.sno's default build (`SCRIP_ONE_END` unset, i.e. `=1`, today's only configuration anyone measures) runs 372,771,572 Ir. The SAME source, SAME tree, compiled with the `SCRIP_ONE_END=0` killswitch, runs 360,195,414 Ir — 12,576,158 FEWER instructions, a clean 1.035x. Both report `check: 1102`; both are byte-for-byte the same answer.** This is not a new codegen idea — `SCRIP_ONE_END=0` is an EXISTING, gate-blessed fallback wired at commit `33b02920` (s119, "Killswitches SCRIP_ONE_DEFER/SCRIP_ONE_END=0 restore legacy byte-for-byte"). It has been sitting in the tree the whole time. Nobody has compared the two arms' Ir since s119, because s119 itself was graded on correctness only (md5 diffs + suite pass counts in the commit message, zero Ir number anywhere in it) — the perf axis was never checked.

## WHY: TWO SESSIONS, MONTHS APART, OPTIMIZED INCOMPATIBLE TARGETS AND NOBODY RECONCILED THEM

- **s119** (commit `33b02920`, "ONE-DEFER + ONE-END", predates the RTX ladder): folded MATCH_END's three-to-four separate emitted calls (`rt_dcap_end_ok_open` open, a step loop, `rt_dcap_end_ok_close`, `rt_match_ctx_restore`) into ONE emitted call, `rt_match_end_all(mark, top, subj, outer)` (`pattern_match.c:722`). Its C body is `c_rt_dcap_end_ok_open(mark,top,subj)` (the full, un-ported C prologue) + `g_dcf_top--` + `rt_match_ctx_restore(...)`. Motivation per the commit message was emitted-code simplicity and a `r8`-argument hazard fix, graded by md5 diff review and suite pass counts — **no Ir number was ever taken.** This became, and remains, the DEFAULT (`one_end()` in `bb_match_end.cpp` reads `SCRIP_ONE_END`, defaulting to 1 when unset).
- **RTX-8 SLICE 7/8** (`src/runtime/rtx/rtx_match.S:551-691`, sessions s220/s221, chronologically AFTER s119): hand-ported `rt_dcap_end_ok_open`'s ceremony (the dcf-frame push) and `rt_dcap_end_ok_close` (the pop) to ~15-instruction asm fast paths, gated by `RTX_GATE(match, ...)` (on by default), with the C bodies (`c_rt_dcap_end_ok_open`/`c_rt_dcap_end_ok_close`) kept only as cold-arm fallbacks (trace-on, lazy-init, overflow). The slice's own comment computes its ceiling as "~2%, BELOW the +-3% null floor" and explicitly declines to claim a wall-clock number for exactly that reason — **but never checks that its target symbol (`rt_dcap_end_ok_open`, the standalone asm entry) is reachable from the DEFAULT build.** It is not: by s220/s221, `SCRIP_ONE_END=1` had already been the default for many sessions, and under that default, generated code never calls `rt_dcap_end_ok_open` at all — it calls `rt_match_end_all`, whose C body calls `c_rt_dcap_end_ok_open` **by name, directly**, the exact cold/un-ported C function RTX-8 SLICE 8 built an asm alternative to avoid.

**Verified from emitted code, not inferred** (the discipline this row's own brief demanded): `nm`/`objdump` on `out/libscrip_rt.so` show `rt_dcap_end_ok_open` (asm, 0x74 bytes) and `c_rt_dcap_end_ok_open` (C, 0x190 bytes) as distinct, both-live symbols. `grep -n "call.*rt_match_end_all\|call.*rt_dcap_end_ok_open" roman_iter.s` under the default build shows only `call rt_match_end_all@PLT` (two sites, matching the program's two `MATCH ... .`-capture statements); under `SCRIP_ONE_END=0` the same two sites instead read `call rt_dcap_end_ok_open`. `grep -rn rt_match_end_all src/runtime/rtx/*.S` returns nothing — **`rt_match_end_all` itself has never been ported to asm**; it is 100% C, always was.

## WHAT THIS MEANS FOR THIS ROW (`perf-nv-set-capture-pump`) AND FOR EVERY ROMAN NUMBER ON RECORD

- STEP 1's own two questions, answered from emitted code:
  1. **Is the capture target's identity known at compile time?** YES, for the plain (non-`*`, non-NRETURN) case, confirmed directly from `bb_match_capture.cpp`'s COND-phase asm (lines 74-88): the varname is `lea rcx, [rip + <rodata-label>]` — a single RIP-relative load of a compile-time string literal baked per capture site, written into `rt_dcap_e.varname` by pure asm (r12 CAS pend-push, "ordinary, unchanged mechanism"). This is the SAME precondition the closed read-side row (`defer-nv-read-by-pointer-not-name`) relied on. **But** unlike the read side, `rt_dcap_pump` is ONE shared consumer loop with no compile-time "site id" threaded through `rt_dcap_e` (only `varname`/`saved_delta`/`len`, stride 24, no spare field) — a site-indexed cache the way `g_sno_defer_cells` does it would need either a 4th struct field (touches the asm push AND a corpus-wide `.s` regen) or a pointer-keyed cache instead of a site-keyed one (smaller blast radius: confined to `rt_dcap_pump`'s C body, no struct/asm change, no regen). Left open for whoever works the `NV_SET_fn`-cost half of this row — not attempted this pass (ROW FACTORY: measure and route).
  2. **Split `rt_dcap_pump`'s ceremony from its `NV_SET_fn` call:** see table above. Within `rt_dcap_pump` itself (unaffected by the ONE-END question — this is orthogonal): self 23,738,036 (6.37% of kernel) is materialize-and-loop ceremony (bounds check, `rt_str_alloc` 6,976,876/1.87% + `memcpy` 2,897,852/0.78% to build the captured substring, DESCR_t construction), and the `NV_SET_fn` call itself is 23,317,465 (6.26%) — roughly a 50/50 split between "make the substring" and "store it by name."
- **This row's own combined estimate ("NV_SET_fn(minus sxt_break)+capture-pump ≈ 18.5% of the kernel") undercounted**: add the now-quantified outer ceremony (4.78%) and the true total for "everything between a capture completing and its value landing in the variable" is closer to **~23% of the kernel** under the current default build.
- **Every existing roman.sno Ir figure on record — this row's own STEP 1 headline (372,771,601/0.419x), seat12's independent cross-check, the parent row `perf-roman-8x`'s entire LEDGER — was measured under the ONE-END default and is carrying this ~3.4% avoidable tax.** None of those numbers are WRONG (they correctly describe the current default build), but the 0.419x-vs-SPITBOL ratio would read closer to **0.434x** on the legacy arm alone, with zero code risk, because the code to do it already exists and is gate-proven back to s119.
