# FINDING 2026-09-12 cfo — a function DEFINEd with two prototypes bound the LAST TEXTUAL one for every call, so a re-DEFINE that renames a formal or drops a local ran the right body with the wrong names

**Seat** cfo · **Mode** TRIO (CEO-619) · **Row** `snobol4-gimpel-recursive-list-functions-overflow-the-call-stack-where-spitbol-completes` · **Ruling** CEO-626 (the prototype defect is this row) and CEO-630 (the route) · **Oracle** `sbl -bf`

## The claim, measured

Gate `test_gate_sno_define_prototype_follows_the_executed_define.sh`, two witnesses cut live from the oracle, RED in both modes before:

| witness | oracle | before (both modes) |
|---|---|---|
| w1 `DEFINE('rd(n)')` … first call … `DEFINE('rd(rd)','rd2')` | `first rd(3) = 6 · first rd(5) = 10 · after rd(4) = 24 · after rd(5) = 120` | `first rd(3) = 0 · first rd(5) = 0 …` |
| w2 Gimpel's COPYL idiom: `DEFINE('C(L)T')` whose body re-DEFINEs `C(L)` and sets T before recursing | `inner sees T<seen> = yes with L = x` | `ERROR 235 -- subscripted operand is not table or array` |

Three master entries (`user_function_26`, `user_function_replace_10`, `user_function_replace_branch_1`) fail the same way, and `gimpel-linked-list-functions` (snoflake) is COPYL in the wild.

## Where it was

The prototype -- formal names and the locals list -- was fixed at COMPILE time. `defs[]` keeps one definition per name and the last textual DEFINE overwrote the earlier one; the driver registered that prototype in the runtime registry; the compiled activation baked its save/bind slots from the registry (`bb_scc_probe` reading `rt_proc_pname`), and the scc call arm baked the callee's save slots at the SITE; `rt_define_site` received the registry's csv (`rt_define_query` at emit time), never the site's own, and never rewrote `p->pnames`. 0d54a825f had made the ENTRY follow the executed DEFINE; nothing made the prototype follow it.

## The route (CEO-630) and what it turned out to need

The ruling: one activation per distinct literal prototype selected by the DEFINE site, the site's own csv into `rt_define_site`, multi-prototype names marked at lowering so the scc site-side-save arm refuses, the non-literal (dynamic) DEFINE path kept and its minimal witness a control arm. Building it showed the runtime already owns a complete per-execution prototype mechanism -- the dynamic DEFINE path (`_DEFINE_` → `DEFINE_fn_entry`, the by-name call → `core_call_registered_fn` → the runtime prologue by names → the body label) -- and that it was BROKEN in two places, which is why the earlier dynamic-witness probes crashed. So the cure is: a multi-prototype name takes that path, and that path is fixed.

1. **Lowerer**: a per-name census of prototype encodings (`nformals|name,name,…`) fed by BOTH DEFINE positions (statement subject and expression, e.g. `DIFFER(DEFINE(...))`; the first draft counted only statements and missed the three master entries); a name with two distinct encodings is multi-prototype: its literal DEFINE sites lower as the runtime DEFINE call (the predicate at the static/dynamic fork answers dynamic; the expression-position fold and its fatal are skipped), it gets NO compiled proc, its bind nodes would carry the site prototype as a trailing `IR_LIT_STRING` operand (kept: single-prototype programs emit byte-identical code), and the proc graph is stamped `multi_proto`, a graph property, no global. ⛔ The first census compared `d.names[]` pointers and read every pair as equal: `sno_parse_define` hands back names that alias its own buffer, so a def kept from an earlier parse reads the latest parse. The encodings are captured at parse time.
2. **Call sites**: `bb_scc_probe` refuses when `rt_define_tiny_ok` is false (the callee is marked redefined), so neither the tiny nor the scc arm bakes slots for such a name; the driver marks the registry entry from the graph property.
3. **Runtime, the trampoline** (`rt_proc_enter_named`, the C → body-label entry the dynamic path uses): it pushed eight qwords from a C caller's rsp ≡ 8 mod 16 and entered the body at ≡ 8, where the compiled activation enters at ≡ 0; the body's first C call (the recursive `rd(rd-1)` → `rt_call_arr_bl` → `rt_entry_resolve` → `snprintf`) faulted on an aligned SSE store. **Every dynamic DEFINE with a recursive body dumped core in both modes.** An 8-byte pad before the pair push, removed on both return paths.
4. **Runtime, `DEFINE_fn`**: on an existing name it replaced spec, params and locals and KEPT `entry_label`, so `DEFINE('rd(n)')` executed after the driver's compile-time prescan had registered `'rd(rd)','rd2'` (in-process, mode 3 only -- the CFO-59 class again) ran the rd2 body with formal n: infinite recursion. A DEFINE without an entry binds the entry to the name -- **but only an entry a previous DEFINE set**: a blanket clear regressed `opsyn_binary_operator_reaches_a_code_built_function_1` in mode 3 (green on origin, red with the cure, found by the per-entry pre/post grade), because a CODE-built function's entry is bound by CODE, not by DEFINE, and lives in the same field. The block now carries `entry_by_define`; `DEFINE_fn_entry` sets it and `DEFINE_fn` clears the label only when it is set.
5. **`rt_define_site`** rewrites `p->pnames/nparams/nformals` when the csv differs, and the DEFINE-site template hands it the site's own prototype when the bind node carries one (dormant today: multi-prototype names have no compiled sites; kept for the activation-variant route should a measured need for it appear).

6. **`COPY` of a DATA record returned the record itself** (the identity test `IDENT(R, COPY(R))` succeeded where the oracle's fails, and a field assignment through the copy changed the original). That is why the linked-list fixture still differed by one line after the prototype cure: COPYL's `COPYL = COPY(L)` shared the tail. A shallow copy now: a fresh instance and id, the field array copied. Nothing to do with DEFINE; found because it was the last line between the fixture and its oracle.
7. **The emit chain was capped at 65536 IR nodes** (`enum CH_MAX`, three static arrays), and `[GZ-7] FATAL chain exceeds CH_MAX` aborted the compiler on any program past it in BOTH modes -- the whole `math_*` class of the SPITBOL x64 tests, twelve programs of fifteen thousand straight-line statements each, the widest single gap in any SNOBOL4 suite (Lon 2026-09-12: "So what is SNOBOL4's biggest challenge. Do that."). The arrays are sized from the graph's own node count now, never a constant; whether the arithmetic behind them is right is the next measurement, taken by the x64 board in this landing.

## ⛔ Withdrawn on Lon's word, and why it is recorded

Lon 2026-09-12 16:3x CDT, in chat: *"Just make sure not use a C caller. No C code."* The cure above routed a multi-prototype name's calls through the runtime DEFINE call and the C runtime prologue. It bound the prototype per execution and turned the gate green in both modes, and its two runtime repairs (the trampoline pad, the entry-label rule) were real cures of that path -- but that path is not where a compiled program's calls belong, and the pad proved it: the same trampoline is entered by assembly callers at the other parity, and the pad crashed 40 deferred-expression master entries (`defer_*`, `eval_defer_*`, `indirect_*`) in both modes -- found by the per-entry grade on the landing binary, bisected to the pad alone. A run-time alignment through rbx crashed the same entries differently (rbx is live for the entered body); a C-side call shim did not clear them either. Withdrawn whole. What lands is the C-free groundwork: the census, the site prototype on the bind node, the graph property, the scc refusal, COPY, the chain cap. The prototype cure proper is one emitted activation per prototype (`rd$k_α`), the DEFINE site's seal selecting it, in the emitted assembly -- exactly CEO-630's route, which I had shortened. The gate stays RED as a RULING and is the row's DONE-WHEN.

## Not done, named

The activation-variant half of the ruled route (`rd$k_α` per prototype, `alpha$fn` selecting) was not needed for correctness: a multi-prototype function runs on the runtime prologue, slower than a compiled activation. Multi-prototype functions are rare (three master entries, one Gimpel include) and the cost is measured in the boards. If a program with a multi-prototype function in a hot loop appears, the variants are the next step and the bind-node operand is already in place.
