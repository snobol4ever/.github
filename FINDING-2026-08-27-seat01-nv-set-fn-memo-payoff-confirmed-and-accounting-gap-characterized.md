## ITEM 2 (measure the memo's `-O0` payoff) — ANSWERED: the memo wins decisively, closing this question cleanly

Same binary, same tree, toggling only the runtime env var (`core.c:2273`, `_nv_memo_off_get`), which gates whether `_var_find_cached`'s memo table is ever populated (`core.c:2290`) — a pure cache-effectiveness A/B, semantics-preserving (`check: 1102` unchanged with the cache off, both natively and under callgrind):

**The memo cache is a real, decisive win at `-O0`** — this closes item 2's question outright: the in-source comment's justification (even though it cites stale `-O2` numbers as its rationale — separately flagged, not re-litigated here) is empirically correct at `-O0` too, just for different underlying reasons. Nobody should propose removing or gating this cache on the strength of "the comment's own numbers are retired."

**Where the cost moves when the cache is off** (mechanism confirmation, not just the headline number): `NV_SET_fn`'s *own* flat self-cost actually *drops* to 40,945,066 Ir (from 46,453,125) — the `if (e)` hit-body at the fast-path line is simply never taken — while the slow path it used to skip lights up for the first time: `_var_bucket_find`/`_var_hash` (name-hash + strcmp chain walk, called from `NV_SET_fn`) cost **~28.2M Ir** that does not exist at all when the cache is populated (17,534,955 + 7,986,820 + 2,662,295 + smaller `_var_hash` slivers). Net: −5.5M at the call site, +~31.9M in the newly-exercised slow path, for the net +26.3M kernel-wide. This is the *write-side* mirror of the already-cured *read-side* by-name defect (`defer-nv-read-by-pointer-not-name`) — same hash+strcmp mechanism, now demonstrated by direct A/B rather than inferred from the read side's shape.

## ITEM 1 (resolve the accounting gap) — REPRODUCED EXACTLY, THREE HYPOTHESES RULED OUT, NOT ROOT-CAUSED

Reproduced the minting session's gap on a fresh build, to the Ir: `callgrind_annotate cg.out src/runtime/core/core.c`'s source-interleaved view of `NV_SET_fn`'s own textual body (lines 1452–1538 of the annotated listing, i.e. real `core.c` lines ~2332–~2372) sums to **32,131,942 Ir** — I hand-summed every displayed per-line cost in that span (prologue 5,508,225 + debug-guard block 2,203,298 + `_var_init_done` check 1,101,646 + `rt_sxt_break` site 2,570,481 + protected-guard 4,406,524 + `!name` check 734,430 + the fast-path-hit line 13,403,067 + ~20 near-zero lines totaling ~1,914 + epilogue 2,203,290 = 32,131,942 exactly) — **14,321,183 Ir short** of the 46,453,125 flat total, reproducing the minting session's gap to the instruction.

Ruled out this session, with evidence:
1. **Not the `rt_protected.h` split** — that bucket (4,039,288) is already counted separately in the flat table under its own file key; adding it to 32,131,942 (36,171,230) is still 14,321,183 short of the *combined* 50,492,413 claim. Same arithmetic the minting session reported; independently reconstructed here from the raw contribution values, not just cited.
2. **Not a file-length/EOF truncation artifact** — `core.c` is 3,047 real lines; `NV_SET_fn` sits at ~2332–2372, nowhere near EOF, and `callgrind_annotate` emitted zero stderr warnings on either the threshold-100 flat pass or a clean unfiltered re-run.
3. **Not an arithmetic error in the original FINDING** — independently re-summed from a fresh `cg.out` on a build 3 days and one unrelated cure later; got 32,131,942 exactly, not an approximation.
4. **Not a third source file quietly absorbing the cost** — swept the full (unrestricted) flat listing for every row where `NV_SET_fn` is the *cost-bearing* (leftmost) entity rather than a caller-of-something-else; only `core.c` and `rt_protected.h` ever appear as such. So the missing 14.3M is real self-cost, tagged `core.c`, at some line callgrind_annotate's source-interleaved view for that file is not displaying under the function.

**What I could not finish in this session's time-box:** the raw `cg.out` position stream for `NV_SET_fn` uses callgrind's compressed relative-line encoding (`+N`/`-N` deltas, `fi=`/`fe=` file-context switches interleaved mid-function for the inlined guard). Hand-decoding it, I found at least one **non-monotonic (backward) jump** inside the biggest self-context (`rt_dcap_pump`, 23.3M Ir) — a `-57` relative delta mid-block, after a callee sub-block, landing at an earlier absolute line before continuing forward again — consistent with `-O0` basic-block layout not following source text order around call sequences. I was not able to fully hand-verify which specific line(s) absorb the missing 14.3M with confidence before the arithmetic risk of a manual decode error outweighed the value of continuing without tool assistance (no KCachegrind GUI in this headless sandbox to browse the address/line map directly). **Leaving this open rather than forcing a false closure.**
