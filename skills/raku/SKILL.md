# SCRIP Raku

The record is GOAL-RAKU-100.md (LIVE CURSOR on top); the design is `reference.md` § 8. Raku builds at rank 9 (CEO-1931) and climbs the cto's rung ladder, not the suites, until half the rungs are green (CEO-2070). Suite tables, file maps and receipts in full are in `reference.md` beside this file.

## 1. The oracle

- **rakudo 2026.05; the spec is the roast** (`/home/resources/roast-master`). The binary through `rakudo_bin()` in `harness/scripts/lib_oracle_flags.sh`; the `raku` on PATH (2022.12) is never the oracle. One dialect, no switch.
- A ref is cut from rakudo; a ref cut from our output is a SELF-PIN, not an oracle; no XFAIL. Refusal, crash or hang (`timeout -k 5`) is `NO_ORACLE_ANSWER` (CEO-1696); an implementation accident is no answer (CEO-1934). Gotchas: `OUTER` is a pseudo-package, a mid-line `}` needs `;`, EVAL of a string needs `MONKEY-SEE-NO-EVAL`.
- Interim (the re-design's layer (c), `reference.md` § 8): the program's own names win; a lib-path export does not beat the setting until F05's typed multi dispatch lands.
- Test is Rakudo's `src/parsers/raku/setting/Test.rakumod`, vendored as the setting's first file.

## 7. Rulings a landing must not break

- Every Raku value is ONE DESCR; a lexical's slot holds its value; `:=` in one scope is a compile-time alias; a run-time binding holds a REF to a heap Scalar, dereferenced in the box, never in C.
- One four-port pull protocol, Icon's generator pump; no second iterator machinery.
- The setting is Raku: a core method is written in Raku and its C body deleted in the same landing; no leaf that calls a box or loops over user code (CEO-1576).
- Never lower a construct to a C function by name, add an `IR_CALL <name>`, a `strcmp` chain or by-name table, or a desugar in `rk_tree.c`/`rk_syntax.c` (§ 10).
- The parser reaches 100% first; the recognizer is translated from Rakudo's grammar.
- A kernel box is born with its family's first rung; a Roast file is cured by its rung, never by its name; RakRungs and RakBench never fall below 100 at a landing.
- **A user class's own Bool and defined answer the truth tests** (the coo 2026-11-12 21:1x CST, an independent bug, not a prerequisite of the Failure cuts; officer_01 measured bd.raku: rakudo prints False False if-f tern-f False dor with-f False, while SCRIP prints True True if-t tern-t False D.new with-t True, because the C builtin __rk_bool never calls a user class's Bool or defined): in `so`, `?`, `if`, `??`, `//`, `with` and `.so`, lower emits a call to the class's own Bool or defined ONLY when the program declares one, a fact decided at lower, so a program that declares neither runs the builtin as today. Not the kernel truth box: that would put a dispatch on every truth test.
- **A container reaches a method the way it reaches a sub, by a fact decided at lower** (officer_04 2026-11-12 22:2x CST, on senior_02's rung-4 measurement of row raku-rungs-red-roast-causes-rc07-pairs-values-are-the-elements-containers: `method m($b is rw) { $b = 50 }` leaves the caller's `$y` at 2 in SCRIP, 50 in rakudo, because the per-call rw mask (`rk_param_is_rw`, `__rk_cell_of`) is built only for a callee lower can see, and a method dispatches at run time). (1) Lower collects, over the program and the setting, the set of (method name, position) pairs some method declares `is rw` (or `is raw`); at a call `E.m(...)` whose name is literal and in that set, a variable or element actual at such a position is passed as its cell, and a formal at that position that is not rw dereferences it on entry, so a program that declares no such method lowers exactly as today. A method named by a run-time string (`."$n"()`) passes values until a measured program needs more. (2) A method's own `is rw` trait rides on its declaration node in the pruned tree, as a parameter's trait does; an `is rw` method returns its container (a REF to the heap Scalar), never a copy. (3) `E.m = V` lowers to a call of m and a store through the REF it returns when the program declares an `is rw` method m (a fact decided at lower); otherwise it stays the field set it is today, so a public `has $.w is rw` attribute keeps its road. (4) An attribute that is the target of `:=` in some method of its class holds a REF in its object slot, and every read and write of that attribute dereferences it in the box (a per-class fact decided at lower). Landings in that order: (1) with (2) and (3), then (4), then Pair as a Raku class over (4) and Array or Hash `.pairs` over element cells, the C bodies deleted in the same landing.
- **Pair is a class of the setting; the C pair constructor allocates it** (officer_04 2026-11-12 23:5x CST, on senior_02's rung-5 measurement of row raku-rungs-red-roast-causes-rc07: a Pair is a two-element ARBLK tagged `rk_proto_pair`, built by `rk_mk_pair` from 22 callers in 8 runtime files, its key, value and kv C arms in `bn_03_sh.c`, and CORE.rakumod names no Pair). By the rule above (a core method is written in Raku and its C body deleted in the same landing) and the container bullet above: (3a) `class Pair` in CORE.rakumod (`has $.key; has $!value; method value is rw { $!value }`, key, kv, antipair, gist, Str, ACCEPTS, sort order), and `rk_mk_pair` keeps its signature and allocates an instance of that class with its two fields (data, no box entered), so its 22 callers and the `=>` operator and `Pair.new` are untouched, and the C arms for a pair's methods are deleted in the same landing; the raku master reads exactly as before (a no-behaviour landing). (3b) Array and Hash `.pairs` build the pair with `$!value` bound by `:=` to the element cell (the attribute REF of the container bullet), so `$p.value = 7` and `+= 100` write the element; a literal pair holds a value and assigning to it fails as rakudo does (Cannot modify an immutable Int).
- **An unfound dynamic variable reads a Failure** (the coo 2026-11-12 21:0x-21:2x CST, on officer_01's design and its correction for row raku-rungs-red-parser-print-stderr): rakudo answers an unfound `$*NAME` with a Failure, which throws only when it is used. SCRIP's Failure is the NATIVE runtime record Failure(exception, handled) (rk_failure_new, fail, DivideByZero), which already answers .defined, so, //, with and if as rakudo does (MEASURED, nf.raku). The cuts: (A) print, say and put sink an unhandled Failure through rk_failure_sink (one line in bta_rk_write; rc 1 and empty stdout as rakudo); (B) an unfound dynamic reads a Failure; (C) STDIN, STDOUT and STDERR leave the F class; (D) the census against rakudo's fixed 36 dynamics in core.c. MEASURED: only TZ, USAGE, SPEC, ARGFILES, SCHEDULER and REPO are missing, and they read Nil today.
- **`require` resolves at run time by path** (the coo 2026-11-12 21:1x CST, ruling officer_01's design on row raku-rungs-red-parser-coverage-stmt-ctrl-require): the recognizer builds the require statement node, and lower resolves the name by a path lookup, never a name table. A miss lowers to the die road at run time, as rakudo does (MEASURED: `say 1; require Nope::Mod` prints 1, then rc 1). It covers require alone: corpus has one, and every unknown use goes through use lib.
- S17 (concurrency) is OPEN: Lon released all holds (2026-11-12 12:4x CST, verbatim: "I release ALL holds. I do not remember making any holds. So there they go."), so an S17 entry (Supply, react, start, Promise; rung 942 kw_supply) is an ordinary red, and its design is the cto's. No global, side table, frame marker, second stack or fixed limit; the Raku smoke before every push (all eight for shared code).
- **An on-demand Supply is a gather the tap runs again** (CTO-644, the cto 2026-11-12 21:2x CST, row raku-rungs-red-parser-coverage-stmt-pfx-supply; MEASURED on rakudo 2026.05: `supply { say("emit") }` prints nothing; a supply's block runs afresh at each `.tap`, synchronously, its emits going to that tap's callback; `.list` is `(1 2)`, `.^name` Supply; `done` ends the tap and runs its `done` callback; `emit` from a called sub still reaches the tap). The one pull protocol carries it, so no second iterator: (A) `supply BLOCK` is its own tree node, as `gather` is (`rkb_sprefix_term`, rkt_04_sh.c), and `emit X` takes `take`'s construct in the tree builder (rkt_01_sh.c, TT_SUSPEND with ival 1, the user-definition check included); lower makes the node the setting's `Supply` holding one closure whose body is the block as a gather, so each tap or list runs it fresh; `class Supply` is Raku in CORE.rakumod (`tap(&cb, :&done)` loops over the closure's Seq calling cb, then done; `list` and `Seq` return it); the Supply's state is its object's attribute, never a global. LATER CUTS, each its own row once A lands: (B) `done` and `quit` inside a supply; (C) `whenever` over an on-demand supply in a supply or a `react`, a `for` over its Seq; (D) `Supply.from-list` and the live `Supplier`, whose taps are the Supplier object's own list; (E) `emit` and `take` from a called sub (SCRIP today: take without gather), one dynamic cure for both. `start`, `Promise`, `await` and `Channel` need a scheduler and are a design of their own, with Unicon's (CTO-503).
- **A proto with a body rides the interim `__multi_call`, and its `{*}` re-dispatches the arguments as they arrived** (CTO-647, the cto 2026-11-12 21:5x CST, on officer_02's ask, row raku-rungs-red-rewrite-rr08-dispatch cause A; MEASURED on rakudo 2026.05 against SCRIP 5999feb7a: `proto h($x) { "<" ~ {*} ~ ">" }` with Int and Str multis prints `<i>` and `<s>` (SCRIP: `i`, `s`); with `$x is copy` set to "a" before `{*}`, rakudo still prints `<i>`; with a named `:$k` it prints `<i5>` (SCRIP: `<>`); a body printing `pre` and `post` around `{*}` runs both). The interim is allowed because F05's `bb_rk_dispatch` has no live row, so waiting would leave the red open indefinitely. When F05 deletes `__multi_call`, it re-expresses this use too (a deletion carries its re-expression). The shape: when a multi base name has a user proto whose body is more than `{*}`, a call of the name is an ordinary call of the proto sub, through the user-sub road (no new C road, no IR_CALL by name). The proto's `{*}` lowers to the existing `__multi_call` over the call's own arguments as they arrived, the positionals in order and the nameds by name, never over the parameters' current values. An onlystar proto keeps today's road. The capture forwarding is CTO-648, below.
- **A `|` in an argument list spreads at run time over the staged medium** (CTO-648, the cto 2026-11-12 22:2x CST, on officer_02's follow-up, row raku-rungs-red-rewrite-rr08-dispatch-spread; MEASURED on SCRIP 5999feb7a: there is no spread at all. `sub g($a, $b) { "$a$b" }; my @x = 1, 2; say g(|@x)` prints `1 2` (rakudo `12`); a multi called through `|@x`, `|@a` of a `*@a` or `|c` of a `|c` finds no candidate (rakudo picks it); `sub f(|) { "ok" }` takes any count already). (1) A spread argument is a lowering fact on that argument, never a desugar in rk_tree. (2) A call holding one takes the staged road with a run-time argument count. The arguments before the spread are staged at their indices, the spread's elements one index each from there, and the arguments after it follow. `rt_arg_stage` grows the medium, so there is no fixed limit; the medium is heap, not spine, so the call's spine footprint stays constant and its box definite. (3) The elements are staged by an emitted iteration over the value (the one pull protocol), never by a C loop, because a lazy Seq runs user code as it reifies. A Capture spreads its positionals so and its nameds by name, and a Hash spreads as nameds. (4) `{*}` in a proto whose signature is `|`, `|c` or `*@` re-dispatches the spread of what it captured (CTO-647's "as they arrived" when the count is known only at run time). It reaches the candidates only, never the proto itself: SCRIP's named-argument road `__rk_named_call` enters the proto sub (measured by officer_02), so that road would loop. Witnesses: the four measured calls above, `proto h(|) { "<" ~ {*} ~ ">" }` with `say h(1)` (rakudo `<i>`), and CTO-647's named witness (rakudo `<i5>`). **THE BUILD** (CTO-650, the cto 2026-11-13 00:1x CST, on officer_02's shape question; officer_02 MEASURED that every open today takes a compile-time `CF_N()`, `rt_apply_open` included, and that the tree already marks `g(|@x)` as the argument node `__rk_arr_slip(@x)`). (a) The run-time count is a FACT on the existing call kinds, never a new kind per call form: the count is an IR operand produced by the staging construct, the prepare block copies the fact as it copies `op_raises` (CTO-558, skill runtime-calls), and the open takes `esi` from that operand under `IF(fact)`. So a user-sub call, `__multi_call` and a method call each keep one template, and the call's cell shape does not change. (b) The staging node is a NEW kind, `IR_ARG_STAGE`: a box that stores its operand at the medium's base plus its counter (growth through `rt_call_args_need`) and bumps the counter, a declared word of its cell (a `box_cell_shapes.tsv` row and `--write`). It is never an `IR_CALL_DIRECT` to `rt_arg_stage`, which section 7's "never lower a construct to a C function by name" forbids. (c) Once a call holds a spread, EVERY one of its arguments stages through `IR_ARG_STAGE` in order, because an argument after the spread lands at a run-time index; the spread's elements stage inside the iteration's body. Nameds take today's named road, counted the same way. (d) The planner places the staging cell on the spine before the call, and the call reads its count at a constant distance; the spine footprint is constant, so the box stays definite.
- **CLOSE { } is a statement prefix rakudo parses and never runs** (row raku-rungs-red-parser-coverage-stmt-pfx-close, 2026-11-13; measured on rakudo 2026.05: `CLOSE { say("c") }; say("b")` prints b alone at mainline, in a sub, in a loop and in an if): the recognizer marks it a phaser (`is_phaser_word`, rkt_04_sh.c) and the lowerer's `rk_ph_rank` drops it as it drops TEMP (lrk_10_rk.c), so its body never runs.
- **The RakDemo compiler object is a SCRIP feature, never an exclusion** (CTO-642, the cto 2026-11-12 18:3x CST, on junior_13's measurement relayed by the coo, row raku-demos-red-demos-raku-rakudo-compiler-rakudo-compiler-raku): Lon opened the suite for that one program (CEO-1607, 1616: "it will be the Raku compiler written in Raku"), so `nqp::getcomp('Raku')` returns SCRIP's own compiler object, whose `.parse` runs SCRIP's Raku recognizer and answers a Match tree named by Grammar.nqp's rules, `hash`, `list`, `from` and `Str` as the demo reads them. It is a design, not a junior's bug: the red row is the cto's until the plan is written; no other `nqp::` op is admitted by it.
