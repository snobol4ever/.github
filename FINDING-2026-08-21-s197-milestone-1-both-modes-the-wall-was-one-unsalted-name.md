## THE MECHANISM — PAT$ names collide in a fresh image; mode 3 worked by accident
`sno_pat_collect` (`lower_snobol4.c`) minted runtime stored-pattern names as bare `PAT$%d` while its sibling `sno_expr_collect` one screen up salts runtime mints (`EXPR$%dF%d`). A mode-4 image's static compile bakes `PAT$0..k` into the `.s` (fw witness: 8 names, 179 refs; beauty: 30 names, 524 refs). At runtime the image's own EVAL road (`eval_build_chain` → `lower_snobol4` → `sno_pat_thunks_build` → `rt_proc_set_fn(pname, jit_fn)`) re-mints from a fresh registry — `PAT$0` again — and the registration SHADOWS the image's static pattern of the same name. Every static defer slot that resolves through the name then fires the WRONG fragment. Measured on `fw_stmt_skeleton` (beauty's Stmt topology, checked in with a live-oracle ref): the two static `*PC()` slots fired the two runtime `*SH(...)` thunks — **static slot k = runtime mint k**, an index-for-index cross-wiring through the shared name space. Mode 3 never hit it because the single shared registry's counter CONTINUES past the static count — uniqueness by accident, not by construction.

## THE CURE — one line + killswitch (SCRIP `b5f5aad9`, +3/−1)
Salt runtime `PAT$` mints exactly as `EXPR$` already does: `PAT$<n>F<salt>` when `g_sno_expr_salt != 0` (compile-time mints are always salt-0 and keep their spelling — emitted `.s` byte-identical pre/post on fw AND beauty, proven before the corpus sweep predicted it). Killswitch `SCRIP_PATNAME_SALT=0` reverts to the colliding names — non-vacuous on both fw witnesses (red returns). All three `PAT$` name consumers are `strncmp("PAT$",4)` prefix checks (`zeta_storage.c:254`, `emit.cpp:1129`, `emit.cpp:3159`) — salt-transparent; none parses the index back.
