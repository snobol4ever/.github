## Bug A — FIXED: `lower_icon_resolve_call_kinds()` retags calls across the whole merged program, not just Icon's own

**Root cause, read directly at the source (not inferred): `src/lower/lower_icon.c:1423`'s `lower_icon_resolve_call_kinds()` iterates `g_stage2.bbp.table[]` — every graph in the ENTIRE merged polyglot program, across every language — not just graphs Icon's own lowering produced.** For every plain `IR_CALL` node it finds (regardless of which language lowered it), if the callee name matches *any* entry in the global `g_stage2.proc_table[]` (again, regardless of which language registered it), it unconditionally retags `nd->op = IR_CALL_PROC_STAGED`. This function is only ever invoked from `lower_icon_stage2()` (`lower_icon.c:1387`), i.e. **only when a polyglot compile contains an Icon segment** — which is exactly why every session on this row has seen the bug as "polyglot-triggered" without it depending on any actual name collision.

SNOBOL4's own call-construction site (`sx_call_named`, `lower_snobol4.c:229`) unconditionally builds `IR_CALL` via the dumb constructor `lc_build`/`IR_node_alloc` (both read directly this session — neither has any conditional logic on the op value, and node allocation is one fresh `calloc` per node, never pooled/reused). So `roman`'s four call sites are always constructed as plain `IR_CALL`. When SNOBOL4 lowers *before* an Icon segment in file order (true of every existing polyglot demo, SNOBOL4 fence always first), `roman`'s graph already exists in `g_stage2.bbp.table[]` by the time Icon's own `lower_icon_stage2()` runs its cross-program cleanup pass — which finds `roman` (a real, registered SNOBOL4 proc) and retags its calls, believing them to be Icon's own.

**Empirical proof, not just static reading:**
- `--dump-ir` on `roman.scrip`'s SNOBOL4 section standalone (`.sno`) vs. the same section plus trivial non-overlapping Icon (`procedure main(){write("icon-trivial")}`) + Prolog (`main :- write('prolog-trivial'), nl.`) sections (`.scrip`): all 4 `roman` self-call sites are `CALL` standalone, `CALL_PROC_STAGED` polyglot (reproducing seat01's finding exactly, on the current, freshly-pulled tree).
- **New, decisive test nobody on this row had run: SNOBOL4 + Prolog only, NO Icon section.** Same witness with the Icon block removed entirely — `roman`'s calls stay plain `CALL`. This directly falsifies "any polyglot merge" as the trigger and pins it specifically to Icon's presence, matching the mechanism above exactly.
- Traced the SECOND loop in the same function (`lower_icon.c:1442-1460`, retagging `IR_VAR` → `IR_PROC_VALUE` by the same global-scan pattern) — same root flaw, same fix.

**Fix (one line, `src/lower/lower_icon.c:1429`):**
```c
-        if (!g) continue;
+        if (!g || !g->icn_cells_graph) continue;
```
`icn_cells_graph` is already set on every Icon-lowered graph earlier in the same function (`lower_icon.c:1193`/`1266`, unconditionally under default config — only `SCRIP_ICN_LEGACY=1` without `SCRIP_ICN_CELLS=1` could produce an Icon graph with this flag unset; noted as a residual caveat, not fixed here, since it's an existing rare debug-only mode and every gate/test runs under default config). This scopes both loops to Icon's own graphs only, exactly matching the semantic intent ("resolve Icon's OWN call/var kinds") without touching what other languages already decided.

**Verification:**
- `--dump-ir` re-run post-fix: `roman`'s 4 self-calls are plain `IR_CALL` in the polyglot build too — divergence gone.
- Icon smoke (`test_smoke_icon.sh`): 14/14 both modes, unchanged, including `proc_recursion` and `proc_zeroarg` (the tests most likely to catch a regression in Icon's own call-kind resolution).
- `test_gate_polyglot_demos.sh`: **byte-identical** `m3 PASS=3 FAIL=7 / m4 PASS=3 FAIL=7`, demo-for-demo, with and without this fix (confirmed via `git stash`/rebuild/rerun on the identical tree) — the other 5 currently-crashing demos (02/04/05/09/10) are a **pre-existing, unrelated** state (not caused by this session, not cured by this fix either); do not attribute them to this row. `git diff --stat` at every checkpoint showed only this one line.

## Bug B — LOCALIZED, NOT FIXED: a NULL function-pointer jump surfaces once Bug A no longer masks it

With Bug A fixed, `roman.scrip` (demo03) and the minimal clean witness (SNOBOL4 + trivial Icon + trivial Prolog, no name overlap) **still SIGSEGV, in both modes.** This is a **different, still-open bug** — Bug A explained the IR-level mistag and the specific "rcx-as-scratch" crash mechanism seat13/seat07 pinned (that crash only happens via the code path a `CALL_PROC_STAGED`-tagged node takes); fixing the mistag removes that specific crash but exposes this one underneath.

**What's confirmed, via gdb (mode-3 AND mode-4 both dumped core, `ulimit`/core inspected directly):**
- Both modes crash identically: `rip=0x0`, `rcx=0x0` — a jump/call through a NULL pointer, not a wild address.
- **Mode-4's backtrace (real symbols, unlike mode-3's flat-wired slab) shows the recursion succeeding several levels before the fault**: `n57_call_bx` (x4, two alternating return addresses — consistent with `roman`'s own recursive self-call succeeding across more than one recursion depth) → `n52_call_bx` (x2) → `n47_call_bx` (x2) → NULL. **This rules out "the callee's entry cell/pointer is simply never populated"** (that would fault on the very first self-call, not several levels in) and points instead toward something that degrades or gets clobbered *during* execution — a fixed-capacity table exhausted by recursion depth, or a cell/slot that's live and correct for a while then overwritten.
- Ruled out as the (sole) cause at the classify/routing layer: instrumented `bb_call_route_classify()` and `bb_call_proc_staged_str()` directly (temporary prints, reverted, tree clean) — post-Bug-A-fix, `roman`'s calls show **identical** `k=IR_CALL`, `reg=1` (rt_proc_is_registered), `is_gen=0`, and `tiny_ok=1` (rt_define_tiny_ok) in both single-language and polyglot builds, at every one of the 4 call sites, in mode-3. Since these all agree, whatever's crashing at runtime is **not** a compile-time routing/eligibility difference visible at this layer — it's either downstream of it (the actual TINY/emitted-code path itself misbehaving specifically under polyglot despite an identical eligibility verdict) or in the runtime cell/table state the emitted code reads.
- Confirmed `rt_define_site` (the runtime call `bb_define.cpp` emits, firing when the `DEFINE` statement itself executes) fires exactly once for `roman` in both builds, with `existing_fn == incoming_fn` already on that first call and `p->redefined` never set — so `p->redefined` is NOT the mechanism (this was the next thing `rt_define_tiny_ok` checks; ruled out directly, not assumed).
- **Not yet reconciled**: a mode-4 `.s`-level diff (before this session's last diagnostic round) showed single-language taking a direct `lea rcx,[rip+.Lsig]; jmp [rip@cell+alpha$roman]` TINY-shim pattern while polyglot took a by-name-looking pattern (`.Lcall_α_*_0_s: .string "roman"` cells) for the same call sites — but the later, more precise `tiny_ok`/`is_gen` diagnostic (above) showed **identical** eligibility for both builds. These two observations are **not yet unified into one story** — flagging this explicitly so the next session doesn't have to re-derive either measurement, but starts from "these two facts currently look inconsistent, resolve that first."
