# FINDING: beauty's Read()/Write() never actually worked on EITHER live oracle — cured with an engine-conditional SETEXIT probe; also found a SCRIP name-passing gap and a broken, unused portability shim

Row: `beauty-library-readwrite-csnobol4-only`. Origin: hq_P's FINDING-2026-08-29-hq_P-a-program-passing-is-not-evidence-the-code-it-includes-passes.md (`.github` `90186d31`), which established that `corpus/include/ReadWrite.inc`'s `Read()` uses a CSNOBOL4-only bracket file-spec (`fileName '[-m10 -l131072]'`) that raises live SPITBOL `ERROR 116` — framed as "CSNOBOL4-only". Measured below: it was not CSNOBOL4-only. It was untested-on-either-engine.

## 1. The CSNOBOL4 half was also broken, just less visibly

`corpus/packages/snobol4/csnobol4_suite/openi.sno` and CSNOBOL4B 2.3.3's own `doc/snobol4io.1` are unambiguous: **filenames go in an optional FOURTH argument to INPUT()/OUTPUT(); the third argument is an options string only.** `INPUT(.rdInput, 8, fileName '[-m10 -l131072]')` — the ORIGINAL 3-argument call, with the name and brackets concatenated into one string — puts the entire `fileName[...]` blob into the *options* slot and supplies no filename at all. Measured directly: this exact call, run under real `csnobol4` (`/home/resources/csnobol4/snobol4 -f`) against a real, existing file, returns ordinary failure (`Read` → FRETURN) every time, plain filename or bracketed, absolute or relative path. ⭐ **The two beauty_suite driver tests that exercise `Read()`/`Write()` (`ReadWrite_driver.sno` tests 4–5) only ever call them on a deliberately bad path expecting FRETURN — so "FRETURNs" was indistinguishable from "opened correctly", and nobody had ever run the success path against a live engine.** Textbook instance of RULES.md's own "a correct procedure with a false explanation" class: the driver's PASS looked like evidence of portability and was actually silent about it.

## 2. The fix — try CSNOBOL4's shape, trap-and-fall-back to SPITBOL's

Neither engine accepts the other's call shape, and this is a hard incompatibility, not a style choice:
- **SPITBOL** (`x64/bin/sbl -bf` and `spitbol-bench-oracle`): exactly 3 arguments (`var, unit, name`); a 4th argument is a **FATAL** `ERROR 116`/`160` ("inappropriate file specification for input/output"), not an ordinary match failure — measured with a bare `SETEXIT`-free probe (execution aborts, `stmts executed 2`).
- **CSNOBOL4B 2.3.3**: filename **must** be the 4th argument; the 3-arg form never carries a name.

Cure (`corpus/include/ReadWrite.inc`, both `Read()` and `Write()`): `SETEXIT`+`&ERRLIMIT=1` around the CSNOBOL4-shape call (`INPUT(.rdInput, 8, , fileName)`); on ordinary failure, FRETURN immediately (real file trouble, not a shape problem); on a **trapped fatal error**, fall back to the SPITBOL-shape call (`INPUT(.rdInput, 8, fileName '[-l131072]')` — `Write`'s `OUTPUT` needs no bracket, see §3). Both branches save/restore the caller's own `SETEXIT`/`&ERRLIMIT` (via `rdPrevXit`/`rdPrevLim`) rather than clobbering it — verified empirically that an armed trap left dangling causes CSNOBOL4 to re-invoke the handler a second time on normal program exit (a real, measured side effect, not a hypothetical).

Verified **byte-identical output, rc=0, on all four cases (good file with a >1024-byte line, offset map correctness, bad-path Read, bad-path Write)** under `x64/bin/sbl -bf`, `csnobol4 -f`, **and** `./scrip` (bonus — not required by DONE-WHEN, but it's the actual product). New witness: `corpus/probe/beauty_readwrite_roundtrip.sno`/`.ref`.

⭐ **Side effect of the same cure:** `ReadWrite_driver.sno`'s pinned `.ref` — one of the three drivers `FINDING...beauty-suite-ref-provenance` flagged as "outrunning the live SPITBOL oracle" — is now reproduced by live `sbl -bf` directly (previously fatal at line 9 before reaching test 1). Re-verified 2026-08-29: both `sbl -bf` and `csnobol4 -f` match the existing pin exactly. `tree_driver`/`trace_driver` are unrelated, untouched, and still await Lon's disposition per that FINDING.

## 3. Measured SPITBOL specifics (why `-l131072` stays, `-m10` goes)

- SPITBOL's **default input line cap is 1024 bytes** (manual p.227, confirmed by direct measurement: a 300,000-byte line under a plain 3-arg call reads back exactly 1024 bytes, then the **remainder up to the real newline is silently discarded** — not returned on a later read). `-l131072` (documented, manual p.228: "`-ln` Line mode: maximum record length is n") raises that ceiling — also measured working alone. ⛔ **This is a ceiling, not true unlimited length: SPITBOL still silently truncates+discards past 131072, unlike CSNOBOL4 (unbounded text-mode input since 2.2, manual `doc/snobol4io.1`) and SCRIP (`getline`-based, unbounded, `src/runtime/core/core.c:3035`).** A single line ≥131072 bytes is a pre-existing latent risk on SPITBOL specifically, unchanged by this fix and out of this row's scope (would need abandoning line-mode for raw/binary reads with manual newline scanning — a materially bigger rewrite).
- `-m10` alone (Unix's own EOL-char default, redundant on paper) empirically **fatal-errors under live `sbl -bf`** the same as combined with `-l131072`; `-l131072` alone does not. Root mechanism not further diagnosed (not load-bearing for the fix — Unix's default EOL is already LF/code 10, so dropping the explicit option changes nothing behaviorally). Flagging the residual mystery rather than asserting a cause I didn't verify.
- Output needs no length option at all: SPITBOL's OUTPUT default is `&MAXLNGTH` (16,777,216 in this build), not 1024 — measured with a clean 3001-byte single-record write.
- OUTPUT's fatal error for the same 4-argument mistake is a **different code**, `ERROR 160` (`INPUT` is 116) — the fix doesn't need to inspect which; any trap means fall back.

## 4. A genuine SCRIP defect found and worked around, not fixed (out of this row's scope)

First attempt factored the SETEXIT dance into one shared helper (`rwOpenIn`/`rwOpenOut`) called from both `Read()` and `Write()`, passing the target variable by reference (`.rdInput`) as a function argument — standard, and verified working correctly under **both** live engines. **Under `./scrip` it silently breaks:** the helper's `INPUT()` call reports success, but the caller's variable is never actually bound to the channel — every subsequent read returns empty string, which reads as "success" forever rather than failing at EOF, so `Read()`'s own reconstruction loop **never terminates** (measured: `timeout 8` kill, not a crash — confirmed the ORIGINAL unmodified library has no such hang on the same input, isolating this to the new indirection). Root cause, read from source: `src/runtime/core/core.c`'s `_io_varname()`/`INPUT`'s first-argument handling appears not to preserve a NAME-type (`DT_N`) value passed *through* a user `DEFINE`'d function parameter, only one written directly as `.name` at the `INPUT()`/`OUTPUT()` call site itself. **Cure applied: no shared helper — the SETEXIT logic is inlined separately into `Read()` and `Write()`, each using `.rdInput`/`.wrOutput` directly at its own call sites** (the pattern already proven to work), at the cost of ~15 duplicated lines. This SCRIP gap is real, reproducible, and worth its own row for whoever owns `GOAL-SNOBOL4-100.md` compiler-side work — any corpus program passing a name through a helper into `INPUT()`/`OUTPUT()` will hang, not fail loudly, under `./scrip` today. Not fixed here: compiler-internal, outside a corpus-library row.

## 6. Two related, out-of-scope discoveries, flagged not fixed

- **`corpus/include/io.inc`** is an earlier, unfinished attempt at generic `INPUT`/`OUTPUT` dialect-bridging via `OPSYN` remapping, explicitly marked incomplete by its own header ("The recognition and interpretation of the options is incomplete"). Grep confirms **nothing in `corpus/{include,library,tests,demo,packages,benchmarks}` includes it** — dead code from the shipped library's point of view. Its engine-detection guard (skip remapping "when `FENCE` is a built-in pattern, i.e., running under SPITBOL", via `DATATYPE(FENCE)` vs `DATATYPE(LEN(1))`) is not just unused but **measured false**: both `sbl -bf` and `csnobol4 -f` report `DATATYPE(FENCE)=PATTERN`, identical to `DATATYPE(LEN(1))` — so the guard reads "skip remap" on *every* engine tested, never just SPITBOL. Worth a row of its own (repair using a proven detection method, or delete) — not touched here, out of scope for a corpus-library portability fix.
- **`corpus/library/ReadWrite.sc`** (Snocone) carries the byte-for-byte identical `fileName '[-m10 -l131072]'` construct — same defect, different toolchain/oracle (Snocone, not SNOBOL4). Not audited or fixed — outside `corpus/include/*.inc`'s scope and this task's DONE-WHEN, and Snocone's own engine semantics weren't verified here. Flagged for whoever owns Snocone library work.
- **`corpus/probe/fwctx/ReadWrite.inc`** — byte-identical to the pre-fix `ReadWrite.inc` — deliberately **left untouched**: it's a frozen defect-witness copy (`util_beauty_override.sh` calls it "LOAD-BEARING for this crash", an unrelated s178 conjunction/FULLSCAN repro) that never calls `Read()`/`Write()` at runtime (compile-only, same "umbrella" shape as `beauty.sno` itself). Editing it risks disturbing a different crash's reproduction fidelity for zero benefit — it exercises none of the code this row changed.
- **`corpus/programs/lon_cherryholmes/`** carries the same `[-mNN -lNNNN]` idiom pervasively (~20+ files, grep-confirmed) — explicitly out of scope per RULES.md ("all of `corpus/programs/` needs work and is not convertible to tests currently", Lon 2026-08-27) and per this row's DONE-WHEN, which scopes the sweep to `corpus/include/*.inc` only. Not audited here.
