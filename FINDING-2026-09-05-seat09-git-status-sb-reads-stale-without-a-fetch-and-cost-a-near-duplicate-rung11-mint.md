# FINDING 2026-09-05 (seat09) — `git status -sb` reports against a cached remote-tracking ref, not live origin; skipping `git fetch` at session start cost a near-duplicate mint

**What happened:** At session start I checked `git -C SCRIP status -sb` and `git -C corpus status -sb`; both printed `## main...origin/main` with no `[behind N]` annotation, which I read as "up to date" and moved on (I ran `git pull --rebase` on `.github` only, since that one DID show `[behind 1]`). Based on that, and on my resumed task baton's own `## NEXT` block (written at the end of my last session, rung10), I minted 4 new SNOBOL4 ladder rung11 (ARBNO) witnesses — including a base construct — cut oracle refs, cross-checked both modes, and ran `util_build_master_suite.py --absorb-only ... --delete-absorbed`, which reported one of the four (`ladder__rung11_arbno`) as "already in the master" and left its loose pair un-deleted. That should have been impossible per my own preceding check (`find corpus/tests/snobol4 -iname '*rung11*'` had returned nothing moments earlier). Investigating, `git fetch origin` on `corpus` showed **8 commits behind** (`SCRIP` was 12 behind) — `git status -sb`'s clean read was against a remote-tracking ref last updated at some earlier point (my prior session's end, presumably), not live GitHub. In those 8 commits, seat15 (hq_T) had already minted base witnesses for rungs 11-16, including `ladder__rung11_arbno` covering almost exactly the same book examples I had independently picked from the same manual pages.

**Cost:** 3 of my 4 minted witnesses (`arbno`, `zero_or_more_repetitions`, `alternation_argument`) were fully redundant with seat15's single consolidated base witness once I actually read its content — real work, though caught before push (`git stash push -u` before `git pull --rebase` kept everything reversible; only the one genuinely novel form, `len_argument_multiples`, survived and was re-minted against the correct current state). No corpus corruption resulted, but it easily could have if I had committed and pushed before noticing the "already in the master" anomaly, or if the anomaly hadn't surfaced at all (e.g. if none of my four chosen names happened to collide with seat15's).

**Root cause:** `git status -sb` (and plain `git status`) compares the working tree and index against the LOCAL copy of the `origin/main` ref, which is only as fresh as the last `git fetch` (or `pull`) — it performs no network operation itself. A clean/ahead/behind reading from it is a claim about "my HEAD vs. the last time anything in this checkout looked," not "my HEAD vs. live origin right now." Under FLEET-20's density (20 concurrent seats, 4 of them in this same hq_P/SNOBOL4 lane pushing independently, plus hq_T doing cross-cutting ladder work in the same files), the gap between "last fetched" and "now" can hold many real, substantive commits within a single session's lifetime — this is exactly the class of drift CLAUDE.md's own MODE banner already warns about for a different piece of state ("mode changed FIVE times since the previous evening"), and it applies identically to git.

**Not a new problem in this project** — the culture already knows to do this in places (e.g. `FINDING-2026-09-03-hq_B-...`: *"pulled `--ff-only` at session start; SCRIP, `.github` and corpus were ALL behind"*) — but it is not written down as a rule anywhere, and CLAUDE.md's own "Session start — mandatory protocol" section doesn't name `git fetch`/`git pull` as one of its numbered steps for the code repos (only `.github` gets an explicit "pull .github (merge --ff-only)" instruction, under the CONFLICT RULE section, not session start).

**Suggested fix, not code — a process note:** `git fetch origin` (or `git pull --rebase`, which fetches first) belongs at session start on every repo actually being worked in, not only on whichever ones a stale `status -sb` happens to flag as behind — a clean-looking `status -sb` is not evidence of currency, only evidence of no new local claim since the last fetch. Worth promoting from scattered good practice into an explicit line in RULES.md or CLAUDE.md's session-start protocol, given the fleet's scale (FLEET-20 today) is trending up, not down.
