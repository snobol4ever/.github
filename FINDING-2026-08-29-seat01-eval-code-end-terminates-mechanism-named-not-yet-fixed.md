## PART 3 — THE MECHANISM, TRACED FIVE LAYERS DEEP (ASM-DIFF-FIRST, then gdb)

**The witness set itself already isolates the ingredient precisely**: `ev_code_end_label_ctl` enters the fragment via an ORDINARY label goto (`:(INSIDE)`), not the direct code-object goto (`:<C>`) — and crashes identically to `ev_code_end_terminates`, which uses `:<C>`. This proves the direct-goto grammar (`goto-code-object-parse`) is not itself in the picture; the sole shared ingredient is **the fragment's own internal goto target is `END`**.

1. **`CODE()`'s fragment compilation is NOT special-cased from whole-program compilation.** `code()` (`src/runtime/runtime_eval.c:368`) parses the fragment's source text at runtime and calls `sno_lower_fragment_at(prog, k)` for each labeled (or first) statement, then `emit_chain(g->entry, NULL, "code_flat")` — a REAL, independent JIT compile happening live, mid-execution of the already-running outer program. Critically, **`lower_snobol4()` (the whole-program entry point) is itself just `sno_lower_fragment_at(prog, 0)`** (`src/lower/lower_snobol4.c:2792-2794`) — there is exactly one lowering path for both a whole program and a runtime fragment; they differ only in `entry_idx`.

2. **The `END` label registry is populated identically for both** (`src/lower/lower_snobol4.c:2078-2085`: `bb_label_registry_reset()` then `bb_label_registry_add("END", exitnd)`), so a fragment's own `:(END)` resolves to a REAL node (`exitnd`) in its OWN small graph — not a stale or missing entry. `rt_goto_resolve()` (`src/runtime/runtime_eval.c:336`) confirms this split further: `if (!strcmp(name, "END")) return NULL;` (line 350) is a **deliberate sentinel**, separate from the ordinary label-table lookup (`rt_label_get_fn`) that resolves a normal label like `DONE` or `INSIDE` to a real function pointer. Verified live via gdb: the first `rt_goto_resolve` call (name=`"<DGT$0"`, the direct-goto's operand) resolves fine to a real JIT address; **a second `rt_goto_resolve("END")` call is never observed** — the crash happens before or instead of reaching it, meaning the fragment's own internal `END` transition does not even go through this function.

3. **Two structurally different fragment-entry mechanisms exist, and only one sets up a stack-independent continuation.** `rt_chain_enter` (`runtime_eval.c:71-102`, hand-written asm) is the "intended" fragment-invocation path: it pushes callee-saved registers, then places a continuation address in `%rcx`/`%rdx` (via `leaq 1f(%rip),%rcx; movq %rcx,%rdx`) **before** `jmp *%rax` into the fragment — no `call`, so nothing is implicitly pushed for the fragment to `ret` through; the continuation is carried in registers instead. But the actual entry mechanism exercised by both crashing witnesses is `bb_goto_deferred.cpp`'s TAIL-TRANSFER arm (`src/templates/bb/bb_goto_deferred.cpp:26-40`, the default arm given `SCRIP_GOTO_TAIL` defaults on): `call rt_goto_resolve; test rax,rax; jz[..]; jmp rax` — a **bare tail-jump directly from the middle of the enclosing program's own flat-wired flow**, entered with none of `rt_chain_enter`'s register setup.

4. **The fragment's own top-level graph is a `flat_jmp_entry` graph, and that changes how reaching its own exit compiles.** `bb_glue_outer_γ()`/`bb_glue_outer_ω()` (`src/templates/bb/bb_glue_flat.cpp:28-46`) — the code that runs when a graph's outermost flow completes — branch on `g_emit.flat_jmp_entry`: a **non**-jmp-entry graph (an ordinary whole-program compile, entered via `call`/`rt_outer_call`) does `xor edi,edi; call exit` — a hard, safe process termination via libc, which can never crash regardless of stack/register state. A **jmp-entry** graph instead does `mov eax,DT_S; ret` — a bare return, which is only correct if something already pushed a valid return address onto the stack for it to pop.

5. **The gap: a `CODE()` fragment's own graph is (evidently) a jmp-entry graph, so its `END`-mapped exit compiles to the bare-`ret` arm — but the witnesses reach the fragment via the raw tail-jump from part 3, which never pushes anything for that `ret` to consume.** Measured directly, right at the crash: `rip=0x0`, `rcx=0x0` (the register `rt_chain_enter` would have populated with a valid continuation address, had that path been taken — it was not: a breakpoint on `rt_chain_enter` never fires for this witness). `rax`/`rdx` hold unrelated leftover values from the immediately-preceding `OUTPUT` statement's own runtime calls, not anything resembling a return address. This is consistent with, though not pinned to the single instruction of, a `ret` (or an equivalent indirect transfer) consuming a stack slot / register that was never populated by this entry path — attempted 40-step single-instruction tracing to catch the exact faulting instruction directly timed out (the flat-wired jmp-threaded architecture leaves no conventional call-stack for gdb to walk back through once past the tail-jump, and bounding the trace tightly enough to be both fast and certain to hit the fault needs more iteration than this sitting spent on it).

**⛔ NOT FULLY PINNED: the single exact instruction that reads/derives the address that becomes 0.** What IS established with high confidence, converging from both the static code-path evidence (parts 3-4) and the live register state (part 5): a `CODE()` fragment's `:(END)` transition is compiled assuming an entry convention (`rt_chain_enter`'s register-based continuation) that the ACTUAL entry path taken (`bb_goto_deferred.cpp`'s bare tail-jump, used identically for both the direct code-object goto and an ordinary label goto reaching into the fragment) does not honor.

## NOT ATTEMPTED — WHY, AND WHAT A FIX WOULD NEED TO DECIDE
No code fix was attempted this session — this is a genuine architectural gap between two calling conventions for the same graph-exit shape (`flat_jmp_entry` + reaching outer-γ), not a one-line bug, and per this project's own established practice, a change to `bb_goto_deferred.cpp` or `bb_glue_outer_γ`/`bb_glue_outer_ω` is SHARED-NODE machinery reached by every language, not SNOBOL4-specific — any fix needs the same corpus-wide blast-radius verification this project's culture demands for shared templates, which is a bigger unit of work than one investigation sitting. Two directions worth naming for whoever picks this up, neither decided here:
- **(a)** Make `bb_goto_deferred.cpp`'s tail-transfer arm detect "the resolved target is a jmp-entry graph's own outer exit" and set up the same register/stack contract `rt_chain_enter` would have, before the `jmp rax`.
- **(b)** Make a fragment's own `END` transition NOT depend on the entry convention at all — e.g., route it through something unconditionally safe regardless of how the fragment was entered (the non-jmp-entry `call exit()` arm already IS unconditionally safe; the question is why a `CODE()` fragment's own top-level graph is a jmp-entry graph in the first place, and whether that classification itself is what needs to change for this specific graph shape, versus the two exit arms).
