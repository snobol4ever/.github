# FINDING 2026-08-27 (seat06, later session) — `opsyn_rebind_twice` / plain-alias m4 failure: real root cause found, a fix attempted and REVERTED (introduces a SIGSEGV via a second, separate by-name dispatch path). Continuation of row `conform-opsyn-operator-rebind-gz5-fatal` (claim held by seat06, not released — see task file). The grammar fix from earlier today (closing 17/19 R-8 witnesses) is unaffected and still correct; this FINDING is about the remaining two red witnesses (`opsyn_rebind_twice`, and by extension `f14_opsyn.sno`'s m4 blocker) only.

## Retraction: no nondeterminism

The earlier FINDING claimed mode-4 for OPSYN aliases behaved nondeterministically across rebuilds. Re-verified cleanly this session, mode-3 and mode-4 run and captured separately (not combined in one shell block): **it is 100% deterministic. A plain `OPSYN('newname','oldname')` alias NEVER works in mode-4, on any build.** The earlier "sometimes correct" observations were mode-3's (always-correct) stdout misattributed to a mode-4 run in a combined command block.

## Real root cause, named exactly

`rt_proc_call_open`/`rt_proc_find` (`src/runtime/rt/rt.c`) — the by-name dispatch every mode-4 `CALL name(args)` compiles to (`call rt_proc_call_open@PLT; test rax,rax; je fail; ...; jmp rax`) — search ONLY `g_rt_gen_procs[]`, populated ONLY by `rt_proc_register()` at compile-time-driven module-init for **statically DEFINE'd procs**. `opsyn()` (`src/runtime/pattern_match.c:440`) calls `register_fn_alias(nm, old)` (`src/runtime/core/core.c:2766`), which writes into `_func_buckets[]`/`FNCBLK_t` — a **completely separate table `rt_proc_call_open` never looks at**. So `rt_proc_find("newname")` always returns NULL for any OPSYN-established name, and the by-name call always fails.

Worse: `register_fn_alias` itself is incomplete for this exact case. It tries to copy the old proc's info by searching `_func_buckets` for `oldname` — but a *statically compiled* proc (e.g. `twice`, `cat`) was never written into `_func_buckets` either (only `g_rt_gen_procs`). So `old_entry` is never found, and the fallback branch fires: `fe->spec = strdup(newname); fe->fn = NULL; fe->entry_label = fe->name;` — a **useless self-referential placeholder** with no working pointer to the real target at all.

Operator-syntax OPSYN calls (`3 @ 4`) mostly dodge this: `lower_snobol4.c`'s `sno_t4_scan`/`sno_t4_target` (a compile-time table, `lower_snobol4.c:1122-1162`) watches every literal-arg `OPSYN(op, target, kind)` call in the whole program and, when a single operator symbol maps unambiguously to one target (`kind` 1 or 2, never reassigned to a different target/arity — reassignment POISONS the entry), the compiler folds the call site to invoke `target` directly (verified in the emitted `.s`: `lea rax,[rip+sum2_α]; jmp rax`, no by-name dispatch at all). Two things defeat this fold, both landing back on the same broken by-name path: (a) **plain-identifier aliases never enter the table at all** — `sno_t4_scan` explicitly only admits operator-shaped first characters (`sno_t4_opchar`), a bare `return;` for anything else; (b) **rebinding the same operator symbol to a second target POISONS the fold**, by design (correctly — SPITBOL's own LAW says the binding must be re-resolved every time, R-8, `.github/GOAL-SNOBOL4-100.md`). `opsyn_rebind_twice.sno` hits (b); `f14_opsyn.sno`'s `double`+`!` both targeting `twice` hits (a) for `double` specifically.

## Attempted fix (written, verified, then REVERTED — do not re-apply as-is)

Added `rt_proc_register_alias(newname, oldname)` in `rt.c`, called from `opsyn()` right after `register_fn_alias`. Looks up `oldname` via `rt_proc_find`, copies its `rt_proc_t` **by value** (immediately, before any call that could `realloc()` `g_rt_gen_procs` and dangle the pointer — `rt_gen_proc_grow()` does exactly that), resets `pcells`/`rcell`/`cells_done` to fresh/unset (these are `oldname`'s own lazily-initialized per-invocation cell cache; copying them verbatim would alias two names' live call state), then either creates a fresh `g_rt_gen_procs` entry for `newname` (via `rt_proc_register`, `newname` first `rt_ws_strdup`'d — `rt_proc_register` stores the pointer verbatim, and `VARVAL_fn`'s return is not guaranteed to outlive the call, same hazard `register_fn_alias` already works around) or overwrites an existing one in place (so repeated rebinding — R-8's "runtime, repeatedly" requirement — keeps working, each `OPSYN(...)` re-copies the CURRENT state of `oldname`).

**This measurably fixed the intended thing**: `rt_proc_call_open("&", ...)` (and `"double"`) now finds a real entry and dispatches correctly for the *first* rebind. But `opsyn_rebind_twice.sno`'s **second** `OPSYN('&','rev',2)` — same op, new target — now **SIGSEGVs mode-3** (`--run`) at the first call through the rebound `&`, jumping to `0x200000000`. `f14_opsyn.sno` did not crash but also did not reach `m4=PASS` (still `42\n7`, unchanged) — the fix only touched the `rt_proc_call_open` path, and per the paragraph below at least one other call site for `f14_opsyn.sno`'s shapes apparently doesn't take that path either.

**Root cause of the crash, per valgrind (`--error-exitcode=99`, full trace kept in scratch, key frames below):**
```
Jump to the invalid address stated on the next line
   at 0x200000000: ???
   by _usercall_hook (driver_hooks.c:72)
   by APPLY_fn (core.c:2818)
   by rt_call_arr_impl (by_name_dispatch.c:4713)
   by rt_call_arr_bl (by_name_dispatch.c:4646)
```
**There is a SECOND, entirely separate by-name call-dispatch path** (`rt_call_arr_bl` → `rt_call_arr_impl` → `APPLY_fn` → falls to `_usercall_hook` when `APPLY_fn`'s own `_func_buckets` lookup finds an entry with `fn==NULL` → `_usercall_hook`'s own fallback, `driver_hooks.c:71`, `if (FNCEX_fn(name)) { rt_call_named_proc(name, ...); ... }`). This path is what mode-3 actually used for the `&` call site in this witness (a breakpoint on `rt_proc_call_open` never fired before the crash). It still walks through the SAME broken `_func_buckets` placeholder (`fn=NULL`, `entry_label="&"` self-reference) `register_fn_alias` created — my fix never touched `_func_buckets` at all, only `g_rt_gen_procs` — and something in that walk (`FNCEX_fn`/`rt_call_named_proc`, not yet traced to the exact line) computes a garbage jump target instead of failing cleanly.

**Why this was reverted rather than chased further:** two independent by-name dispatch mechanisms exist in this runtime (confirmed, not hypothesized), and it is not yet established which call SHAPES route through which, in which mode, or whether they are meant to ever both see the same name. A fix that makes one succeed while the other still holds broken placeholder state is worse than the pre-existing honest failure (wrong-but-silent output) — it trades a `DIFF` for a `SIGSEGV`, and RULES.md's own severity ranking puts a crash below a silent wrong answer only in the sense that at least a wrong answer isn't a crash; this is neither better. Continuing safely needs mapping ALL the by-name-call entry points (`rt_proc_call_open`, `rt_call_arr_bl`/`rt_call_arr_impl`/`APPLY_fn`/`_usercall_hook`/`FNCEX_fn`/`rt_call_named_proc`, and possibly more) and either (a) making `register_fn_alias` populate something the SECOND path can use correctly too (mirroring the `g_rt_gen_procs`-copy approach, but for whatever `FNCEX_fn`/`rt_call_named_proc` actually needs), or (b) unifying the two paths so OPSYN-established names are resolved once, consistently, regardless of which dispatch route a given call site takes.

**Reverted cleanly** — `git checkout` on the three touched files (`rt.c`, `rt.h`, `pattern_match.c`), confirmed zero diff, confirmed `grep -c rt_proc_register_alias` is 0 in all three. Rebuilt pristine, full corpus regression re-confirmed 365/365 both modes, `opsyn_rebind_twice.sno` back to its pre-existing (non-crashing) `m3=PASS m4=DIFF` red state. **The tree today, net of this whole session, carries only the grammar fix from the earlier FINDING — nothing from this investigation is landed.**
