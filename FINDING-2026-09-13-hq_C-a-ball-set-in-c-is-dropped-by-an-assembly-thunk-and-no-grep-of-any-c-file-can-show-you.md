# FINDING 2026-09-13 (hq_C) — a ball set in C is dropped by an assembly thunk, and no grep of any C file can show you why

**Claim.** `succ/2` and `plus/3` fail silently where ISO requires `instantiation_error`, `type_error(integer,_)`, `domain_error(not_less_than_zero,_)` and `evaluation_error(int_overflow)` — 14 cases across `succ_2` and `plus_3` in `corpus/packages/prolog/logtalk_iso`. The C helper behind both, `rt_pl_succ_plus_cell` in `src/runtime/unification.c`, was cured to set `cx->ball` on every one of those paths (SCRIP `edd0275ef`). **Nothing observable changed, in either mode**, and the cases stay red. The reason is not in any C file.

**Cause.** `src/runtime/rtx/rtx_plunify.s` carries two thunk macros a few lines apart:

```
#define PL_CTX_LEAF(nm)            … mov rdx, rsp; call rt_pl_dop_##nm##_c; … ret
#define PL_CTX_LEAF_BALL(nm,modop) … mov qword ptr [rsp + CTX_BALL], 0; mov rdx, rsp; call rt_pl_dop_##nm##_c;
                                     … mov rcx, [rsp + CTX_BALL]; test rcx, rcx; jz 99f; mov r15, rcx; … 99: ret
```

Only the second zeroes `CTX_BALL` before the call and reads it back afterwards to raise. `succ` and `plus` are registered with the plain `PL_CTX_LEAF`, so a ball written by the C helper goes into a stack slot that is **never initialised and never read**. Two consequences, and the second is nastier than the first: the ball is lost, *and* the helper's own `if (!cx->ball)` do-not-overwrite guard is reading uninitialised memory, so whether it even writes is undefined.

**Why it survives review from either side.** The C is complete and correct — every error path sets a ball, and a reviewer reading `unification.c` has no reason to look further. The assembly is complete and correct too — `PL_CTX_LEAF` does exactly what it says, and nothing in it mentions `succ`. **The defect exists only in the pairing**, and the pairing is expressed as a macro name in a `.s` file that no C tooling reads. ⭐ This is the same shape CLAUDE.md records for `g_zeta_mode` — *a global read only by EMITTED code is invisible to every grep of the compiler's own sources* — with the direction reversed: there, deleting a symbol the C could not see broke emitted code; here, a contract the C cannot see silently discards what the C produces. **The general form: when a value crosses a language boundary, correctness on both sides is not correctness.** The cheap check is to ask which side *initialises* the slot — an out-parameter nobody zeroes is an out-parameter nobody reads.

**How it presented, and why the obvious reading was wrong.** After the cure, `succ(a,_)`, `succ(-1,_)`, `plus(a,1,_)` and nine siblings all still printed `failed`. The natural conclusion from "I fixed it and nothing changed" is *the diagnosis was wrong* — and that conclusion is available, plausible, and would have sent the next hour into re-reading the ISO clauses. What ruled it out was cheaper: the C helper's behaviour on the *success* paths had also changed (overflow checks added) and those still worked, so the function was certainly being executed. **A cure that changes nothing is not evidence against the diagnosis until you have proven the edited code runs** — `a-cure-in-one-of-two-duplicate-spellings-changes-nothing`, one layer lower.

**Scope, which is the part that needs a ruling.** `rtx_plunify.s` registers **thirty-odd** names with `PL_CTX_LEAF`. Any one of them whose C helper can set `cx->ball` today is silently failing instead of throwing, and that is invisible from either side alone — it cannot be found by reading the C (which looks right) or the assembly (which also looks right), only by *joining the two lists*. `sort`, `msort`, `char_type`, `term_string`, `atom_length`, `atom_concat`, `atom_chars`, `atom_codes`, `atom_number`, `atom_string`, `upcase_atom`, `downcase_atom`, `string_concat`, `string_length`, `string_lower` are all on the plain macro. Asked to the cto as one row — *sweep every `PL_CTX_LEAF` whose helper can raise* — rather than two names, because a per-name fix leaves a class that reads as cured. Same argument the cto made to hq_R about the sibling stream sinks, arrived at from the other end.

**Landed anyway, and labelled.** The `unification.c` half is on origin at `edd0275ef` with a commit that says in as many words that it is **inert until the thunk row lands**, and the row's baton says the same in its `## NEXT`. Holding it back would have been worse: it is the behaviour the thunk will carry, and the alternative is a later seat re-deriving the same ISO error table from scratch. But an unlabelled inert cure is how `succ/plus` would come to read as done — the shape `a-red-criterion-on-an-open-row-is-invisible` warns about, with the criterion replaced by the cure itself.
