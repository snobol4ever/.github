## ⛔⭐⭐ STANDING LAW OF THIS LANE — THE DEFINING DOCUMENT IS NOT AUTOMATICALLY THE SPEC (hq_snocone 2026-09-16, minted after it nearly cost a lexer change)

`corpus/tests/snocone/report.md` is Andrew Koenig's original Snocone paper, and `SCORE.md` makes it this language's standard *for the score* — where no public conformance suite exists, the ladder to the top of the defining document's census IS the score. ⛔ **That does NOT make it the syntax spec.** SCRIP's Snocone emulates **C surface syntax over SPITBOL semantics**, and where the paper and that design disagree on SYNTAX, the C reading plus the SNOBOL4 operator set wins.

**The ruling that settled it** (Lon 2026-09-16, in-chat, verbatim): *"The '#' is an operator, if it is an operator in SNOBOL4. Snocone emulates C, so /* ... */ and // ... are the comments."* The condition was verified rather than assumed: `ARCH-LANGUAGES.md` lists `#` as an undefined **binary** operator available for `OPSYN` (left, pri 7), and the SPITBOL manual (lines 5204–5206) lists it among the unused unary *and* binary operators, with the worked example `OPSYN('#','DIFFER',2)`.

**How close this came to landing backwards.** The paper says, flatly, *"Comments begin with a # character and end at the end of the line."* A census had already shown that across 168 `.sc` files the only bare `#` outside a string or comment was the failing test itself — so curing the lexer would have broken nothing measurable, passed every gate, and been wrong. **A change that breaks no test is not thereby correct.**

| the paper says | SCRIP's Snocone is | disposition |
|---|---|---|
| `#` begins a comment | `#` is an OPSYN operator; comments are `//` and `/* */` | test deleted, recorded in `ALL.excluded.txt` with a do-not-re-mint note |
| `a[i,j]` — Algol-like subscripts | same — brackets, **not** SNOBOL4's `a<i>` | two tests repaired from `arr<i>` to `arr[i]` |
| alternation is `\|`, concatenation is `&&` | same | five tests repaired from `(a, b)` to `(a \| b)` |

⭐ Note the table cuts **both ways** — the paper was RIGHT about subscripts and alternation and wrong only where SCRIP's C emulation overrides it. So the rule is not "distrust the paper"; it is **name which authority governs the question you are asking** — the paper for what the language *is* and for the score's census, `ARCH-LANGUAGES.md` plus the SPITBOL operator set for how SCRIP *spells* it.

## ⛔⭐⭐ STANDING LAW OF THIS LANE — SNOCONE SPELLS THINGS TWICE, SO A CENSUS OF ONE SPELLING REPORTS THE OTHER AS ABSENT (hq_snocone 2026-09-16, written at hq_snobol4's request after it caught us BOTH in one day)

Snocone is C-syntax SNOBOL4, and the C syntax did not replace the SNOBOL4 spelling — **it sits beside it**. So this language has construct pairs where two different surface forms produce the same runtime object, and **a grep for one of them answers, truthfully, about half the population.** Measured instances, both inside twelve hours:

| the question asked | the spelling grepped | the spelling MISSED | what the miss cost |
|---|---|---|---|
| how many functions does the corpus declare? | `function` | **`procedure`** | 8 declarations, including `Fib`, `QSort`, `Reverse`, `IsPalindrome`, `SplitWords`, `Double`, `MayFail`, `NullFn` |
| how many DATA registrations are in the rungs? | `DATA(` | **`struct`** | 10 of 13 — I reported "three" to another HQ and was wrong by a factor of four |

⛔ **`struct point { x, y }` IS A RUNTIME RECORD REGISTRATION.** It is the Snocone spelling of `DATA('point(x,y)')` and creates a constructor plus one accessor per field at runtime, declared statically nowhere — identical to the `DATA` form in everything except how it is typed. A resolver, a census or a blast-radius read that keys on `DATA` sees three entries where twelve exist.

**THE RULE:** before quoting any population count for this lane, name BOTH spellings of the construct or state that you checked there is only one. ⭐ And the general form, which is why this is law and not a note: **a narrow true answer is indistinguishable from a broad one at the point of reading.** The grep did not fail, the shell did not warn, and nothing was wrong except the question. This is the same class as the instrument traps in root `CLAUDE.md` (`command -v` answering *is it on PATH*, `$?` after a pipeline answering about the pager) — except that here there is no instrument to blame: the narrowing was in the fingers, so no refusal, default or gate can catch it.

## ⛔⭐⭐⭐ THE ONE DEFECT UNDER ALL SEVEN PARSERS — A USER FUNCTION CALLED INSIDE A DEFERRED CAPTURE TARGET FAILS THE MATCH, SNOCONE ONLY (hq_snocone 2026-09-16, three-line witness)

**THE WITNESS, and it contains no parser:**

```snocone
function INNER(x) { INNER = .dummy; nreturn; }
function OUTER(t) { INNER('v'); OUTER = .dummy; nreturn; }
if ('' ? epsilon . *OUTER('P')) OUTPUT = 'MATCH'; else OUTPUT = 'FAIL';
```

| arm | answer |
|---|---|
| `sbl -bf` on the SNOBOL4 twin | **MATCH** |
| `scrip` on the SNOBOL4 twin | **MATCH** |
| `scrip` on the Snocone source above | **FAIL** |

**The class:** a **user-defined** function call nested *inside* a deferred conditional-assignment target (`… . *F()`) makes the match fail. Remove the nested call and it matches. Call a **builtin** instead (`SIZE`) and it matches. It is the nesting of a *user* call that breaks it.

⛔ **THIS IS WHY ALL SEVEN PARSERS SCORE ZERO, AND IT IS ONE BUG, NOT SEVEN.** Every `parser_*.sc` is built on `Shift` and `Reduce` from `bootstrap/ShiftReduce.sc`, and both are invoked exactly this way — `p . thx . *Shift(t, thx)` and `epsilon . *Reduce(tag, n)` — while their bodies call `Push`, `Pop` and `tree`, all user functions. So every reduction in every grammar silently fails the match, and the failure surfaces at the top as a bare `Parse Error`. The parsers are not (only) stale: **the language they are written in cannot run them today.**

**The ablation, in the order it actually went, because the wrong turns are the useful part:**

| probe | result | what it killed |
|---|---|---|
| `epsilon . dummy` (plain variable target) | MATCH | not conditional assignment itself |
| `LEN(1) . *F()` standalone | MATCH | not deferred targets as such |
| same, with the 14-file library chain prepended | MATCH | not the library, not the `OPSYN` of `~`/`&` |
| 6-parameter function called with 2 args | MATCH | not arity |
| `nreturn` from inside an `if` block | MATCH | not nreturn placement |
| a statement that FAILS inside the body (`GT(xTrace,4)…`) | MATCH | not statement failure |
| full hand-clone of `Push` as the direct target | MATCH | not `Push`'s body |
| a wrapper calling that same clone **nested** | **FAIL** | ⭐ the nesting |
| a wrapper calling the builtin `SIZE` nested | MATCH | user functions only |

⭐ **TWO WRONG ROOT CAUSES I PUBLISHED TO MYSELF AND KILLED BY CHECKING.** (1) `ShiftReduce.sc` calls `tree(` lowercase while `tree.sc` defines `Tree` — a real-looking case mismatch in a case-sensitive language. It is NOT a bug: `tree.sc:1` declares `struct tree { t, v, n, c }`, so `tree(…)` is the **runtime record constructor**, invisible to any static census. Exactly the DATA-registration trap this lane already has a law about. (2) I read `DIFFER(p)` returning the null string as "p is null" and concluded `reduce()` returned nothing; DIFFER returns null **on success**, so it had been returning a valid pattern all along. Both were caught by running one more probe instead of writing the fix.

⛔ **DO NOT "FIX" `ShiftReduce.sc`, `semantic.sc` OR `counter.sc` FOR THIS.** They are correct SPITBOL and they run correctly under `sbl -bf` and under our own SNOBOL4 frontend. The defect is in the Snocone frontend's lowering of a deferred capture target, and that is where the cure belongs. `FoldOp` (referenced at `semantic.sc:66`, defined nowhere) is a separate real gap and does not cause this.

## ⭐⭐⭐ THE MODEL — HOW SNOCONE FITS THE SHARED PIPELINE

Snocone is **C-syntax SNOBOL4**: same semantics, same runtime, same IR (`LANG_SNO`), different surface syntax (braces/semicolons instead of column-position statements, `if`/`while`/`for`/`function` instead of `:S()`/`:F()`/`DEFINE`). It is not a separate machine the way Icon (generators) or Prolog (backtracking/unification) are — it rides SNOBOL4's Byrd-box pipeline directly, which is why so much of its history is "port this SNOBOL4 program to Snocone syntax" and "fix this shared-pipeline bug that happens to surface through Snocone first."

```
.sc → snocone lex/parse (src/frontend/snocone/: snocone_lex.c, snocone_parse.y, snocone_driver.c)
    → lowering (historically snocone_lower.c/snocone_cf.c; unified into the shared src/lower/
      lower_snobol4.c by 2026-07-21 per IR-BB's own newest entries — see staleness hazard #3)
    → the same optimizer_run → emitter → templates → x86-64 pipeline every language shares
    → mode-3 (--run, BINARY) / mode-4 (--compile, TEXT) — see staleness hazard #1 on stale mode counts
```

Pattern match: `subject ? pattern` lowers to a STMT_t with subject+pattern fields, routed through the exact same broker/BB path as SNOBOL4's `subject 'pattern' = replacement`. Control flow (`if`/`while`/`for`/`return`/`freturn`/`nreturn`/`procedure`) lowers to the SNOBOL4 statement model's goto/label STMT_t sequences — Snocone's frontend does the C-syntax → goto/label translation once, at parse/lower time; nothing downstream needs to know it started as `if`/`while` rather than `:S()`/`:F()`.

**Snocone → SNOBOL4 translation table** (for writing Snocone tests by eye from working SNOBOL4 programs — from `GOAL-LANG-SNOCONE.md`):

| SNOBOL4 | Snocone |
|---------|---------|
| `X = "hello"` | `x = "hello";` |
| `OUTPUT = X` | `OUTPUT = x;` |
| `X Y :S(L)` | `if (x ? y) { goto L; }` |
| `X 'pat' = 'repl'` | `x ?= pat <- repl;` (or `subject ? pattern` scan form) |
| `DEFINE('F(A,B)')` | `procedure F(a, b) { ... }` |
| `:S(L) :F(M)` | `if (...) { goto L; } else { goto M; }` |
| `IDENT(A,B)` / `INTEGER(X)` / `DIFFER(A,B)` | same builtin names, lowercase args |

**The self-host bootstrap library** — the shared `.sc` runtime that six languages' self-hosted parsers (`parser_{icon,prolog,raku,rebus,snobol4,snocone}.sc`) and Snocone's own self-hosted lower/interp effort build on — lives at **`SCRIP/bootstrap/`** today (moved from the eleven files' `corpus/SCRIP/`; see staleness hazard #2, including the unresolved `lower.sc`/`lower_driver.sc` question).

## ⛔ LAWS THAT BIND EVERY RUNG (RULES.md is the parent; compact, deduplicated from all eleven files)

- **NEVER patch corpus `.sc`/`.sno` source to work around a runtime bug.** Fix the runtime. Repeated as an explicit Lon directive at least three separate times across the absorbed files (sessions #73, 2026-06-24, and others) because it kept almost happening — a bug found via a `.sc` port is real evidence about the shared runtime, and papering over it in the port hides that evidence.
- **⭐ THE BODY-PART-CORRESPONDENCE PRINCIPLE (Lon, 2026-05-02, the standing translation law for every `.sno`/`.inc` → `.sc` port):** mentally erase `:F(LBL)`/`:S(LBL)`/`:(LBL)` plumbing and goto-label targets from the source — what remains is a stream of **body parts** (assignments, expressions, pattern matches, calls). Those body parts go into the `.sc` port **unchanged in name and content.** Then wrap them with structured control (`if`/`else`/`while`/`for`/`break`/`return`/`freturn`/`nreturn`). It is a one-to-one body-part correspondence — the control envelope is new, the bodies are identical. Forbidden moves: renaming identifiers (except function-name-shadow collisions), inventing intermediates not in the source, adding branches not in the source, dropping comments or `OPSYN` calls, reasoning about *when* the source statement would have failed and reimplementing that logic instead of porting it. Expression-IR should end up byte-identical between `.sc` and `.sno`/`.inc`; only control-flow IR differs.
- **No automated mass-transforms on `.sc` code.** A scripted "strip braces from single-statement bodies" sweep landed broken code (`else Shift = .dummy; nreturn;` with no guarding `if`) and had to be reverted. Every `.sc` transform is hand-verified per file.
- **No dead-code pruning when porting.** *"The code is turned on by settings"* (Lon) — every construct in the canonical `.sno`/`.inc` gets ported regardless of whether it appears reachable at default settings.
- **Case sensitivity is a frontend concern, not a flag the user should need.** Since SCRIP `5535b229`, every non-SNOBOL4 frontend (`snocone_cf_compile`, and the Icon/Raku/Prolog/Rebus equivalents) calls `sno_set_case_sensitive(1)` itself at compile entry — `--case-sensitive` should never be required on the command line for a `.sc`/`.icn`/`.pl`/`.raku`/`.reb` file.
- **Pattern globals convention:** `&ANCHOR = 0` always (never 1), `&FULLSCAN = 1` always, set at program start.
- **`&&` in this history is Snocone's original explicit concatenation operator**, juxtaposition is whitespace-implicit concat in later ports — see the unresolved Koenig-pivot conflict above before assuming either is currently "the" rule.
- One-authority naming: `E_*` IR tags, `x86(...)` sole binary/text producer, TEMPLATE-ONLY, BOTH-MEDIUM — all inherited unchanged from the shared cross-language laws in root `CLAUDE.md`; not re-derived per-language here.

Final: **PASS=67 FAIL=0, `beauty.sc` 1148/1148 statements byte-identical to the oracle.**

**Worth preserving: two real scrip pattern-engine bugs found and fixed along the way**, since they're the kind of subtle engine-level defect likely to recur elsewhere:
- **The `$'  ' = *White` alias regression.** A whitespace alias assigned via `*White` (deferred value-context evaluation) stores a frozen-`EXPR_t` (`DT_E`) descriptor; when later referenced in PATTERN context via `E_INDIRECT`, both the SM path (`SM_PAT_DEREF`, `sm_interp.c`) and the IR tree-walk path (`interp_eval_pat`, `eval_pat.c`) had no `DT_E` case and fell through to a degenerate empty-name pattern reference, breaking recursive grammar rules built on the alias. Fixed on both paths by adding a `DT_E` branch that thaws the frozen expression via `PATVAL_fn`/`EVAL_fn`, mirroring the existing `case E_VAR` handling.
- **The Compiland off-by-one / stranded-first-statement bug.** `(E_Parse & 'nTop()')` embeds `nTop()` as a string inside an `EVAL`'d deferred pattern, called at match time by `Reduce(t, n)`. On large, structurally complex input (full `beauty.sc`, 1148 statements) this returned a count one short, stranding the FIRST-pushed (oldest) statement on the tree stack while popping everything above it. Root cause of the miscount was never fully pinned down; the fix sidesteps it entirely — `reduce_prim(E_Parse)` calls `TopCounter()` as its literal first operation inside the match-time action, before any stack pops, eliminating the binding-time ambiguity. A companion, harder bug (heap corruption / SIGSEGV at intermediate input sizes) turned out to be unrelated: `cache_get_fresh` shallow-copied `arbno_t`'s heap-allocated `stack` pointer, so a `realloc()` inside one cached copy's growth left a sibling copy's pointer dangling — fixed with a deep copy, plus unifying two previously-inconsistent local `arbno_t`/`arbno_frame_t` definitions into one canonical `bb_box.h` version.
