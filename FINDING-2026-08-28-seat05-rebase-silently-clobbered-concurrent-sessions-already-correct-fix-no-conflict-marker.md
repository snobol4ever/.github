# FINDING 2026-08-28 seat05 — a clean `git pull --rebase` silently reverted a concurrent session's already-correct, already-tested fix, with no conflict marker

**Date:** 2026-08-28 · **Seat:** seat05 (row `scrip-polyglot-demo-icon-semicolon-5-files`) · **Tree:** SCRIP, `main`, two ordinary rebases in the same session, neither reported a conflict.

## Headline

Two sessions independently found and fixed the **same stale-path bug in the same gate script** within about a minute of each other, fixing it in **opposite historical directions** because the ground truth moved between when each session started reading. My `git pull --rebase` replayed my (by-then-outdated) one-line patch cleanly on top of the other session's already-pushed, already-verified fix — and because a rebase is a context-line patch-apply, not a semantic merge, git found **no conflict at all**: the base's current text matched exactly what my patch expected to find-and-replace, so it silently flipped their correct fix back to wrong. This was caught by luck of discipline, not by git: I re-ran the row's own gate immediately after the rebase (HQ-27 / rebase-baseline corollary), and it failed in a way that didn't match my mental model, which is what sent me digging into `git log` instead of trusting the "Successfully rebased" message.

**The generalizable lesson: a rebase reporting no conflicts is not evidence the result is correct — only that it applied. Two sessions can independently fix the same bug in opposite directions when the underlying ground truth changes between them, and a clean rebase has no mechanism to notice this, because it operates on text, not on "was this line already correct before I touched it." Re-running the gate after every rebase is not a formality; it is the only check in the whole workflow that would have caught this.**

## What this means

Not a compiler defect — a **process/tooling hazard specific to a highly concurrent, shared-identity fleet** (every seat commits as the same `LCherryholmes <lcherryh@yahoo.com>` identity per the ONE-IDENTITY LAW, so `git blame` alone cannot even tell you two different sessions were involved). The failure mode is silent by construction: a 3-way patch-apply rebase only conflicts when it **can't** figure out where to put a hunk; it has no concept of "the target line used to say something else before another author fixed it," so two authors independently patching the same line in opposite directions is invisible to it as long as the second patch's context still matches.

**Mitigation that actually worked, in order:** (1) HQ-27's "gate verdicts require `make pristine` first" forced an actual re-run rather than trusting the rebase message; (2) noticing the re-run's *specific* failure text didn't match my own mental model (I expected either full pass or the row's known remaining defects, not "witness not found") is what triggered suspicion; (3) reading the actual commits (`git show <hash> -- <path>`) rather than guessing settled it in under a minute once suspected.

**Generalizable takeaway for anyone in a rebase-heavy concurrent-fleet workflow:** if your own commit touches a file that a fast-moving shared area (paths, config, anything subject to an in-flight reorg) also plausibly touched, do not just check "did the rebase report a conflict" — re-run whatever check proves your change is *currently* correct, immediately after every rebase, every time, even the second one in the same session. This is the same discipline HQ-27 already mandates for gate verdicts; this incident is a concrete instance of it catching something real, not a hypothetical.
