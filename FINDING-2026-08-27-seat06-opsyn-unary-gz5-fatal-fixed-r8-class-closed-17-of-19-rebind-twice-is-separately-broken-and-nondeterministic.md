## Root cause, named exactly (NOT in lowering)

The row's brief pointed at `lower_snobol4.c`'s GZ#5 dispatch, matching the sibling row's precedent (`comment.sno`, a missing `TT_INDIRECT` pattern arm). **This one is a different mechanism.** `f14_opsyn.sno`'s FATAL (`binary operator with missing operand`) bisects to exactly one of its three OPSYN forms: `OUTPUT = !21` (the *unary* operator-rebind call). `--dump-ast` shows why: `!21` parses to `(TT_POW (TT_ILIT 21))` — a **one-child `TT_POW` node** — while the working binary form `3 @ 4` correctly parses to `(TT_OPSYN @ (TT_ILIT 3) (TT_ILIT 4))`. `lower_snobol4.c:385`'s `TT_ADD/TT_SUB/TT_MUL/TT_DIV/TT_POW/TT_SEQ/TT_CAT` case requires `t->n >= 2` and fatals otherwise — correctly, for a genuine binary op. The bug is that `!` (unary position) was never wired to build a `TT_OPSYN` node at all.

`src/frontend/snobol4/snobol4.y:173`: `T_1BANG expr14 { $$=expr_unary(TT_POW, $2); }` — the grammar itself hardwires unary `!` to `TT_POW`. This is **exactly** the defect R-8 already named and left as its one remaining open item as of s192 (`.github/GOAL-SNOBOL4-100.md` line ~742, and the original s105 LAW at line ~1566): SPITBOL splits operators into USED (static arithmetic identity, cannot be OPSYN'd — manual pp.115-116) and UNUSED (`& @ # % ~` binary, `! % / # = |` unary — OPSYN-able, zero static identity, oracle-verified). The grammar had 7 remaining hardwired arms, all in `expr7`/`expr10`/`expr14`, all discovered by grepping the six arms R-8's own text names plus one more (`T_2POUND`/binary `#`, `T_2PERCENT`/binary `%`, `T_1BANG`/unary `!`, `T_1PERCENT`/unary `%`, `T_1SLASH`/unary `/`, `T_1POUND`/unary `#`, `T_1EQUAL`/unary `=`) — `&`/`@`(binary)/`~`/`&`(unary)/`|` were already correctly wired to `TT_OPSYN` (visibly, as the sibling lines right next to the broken ones).

## The fix — same mechanism as the already-correct siblings, all 7 arms

`src/frontend/snobol4/snobol4.y`, 7 one-line changes (pattern identical to the pre-existing correct `&`/`@`/`~`/`|` lines):
```c
-expr7      : expr7 T_2POUND      expr8   { $$=expr_binary(TT_MUL, $1,$3); }
+expr7      : expr7 T_2POUND      expr8   { tree_t*_e=expr_binary(TT_OPSYN,$1,$3); _e->v.sval=strdup("#"); $$=_e; }
 (same shape for T_2PERCENT/"%", T_1BANG/"!", T_1PERCENT/"%", T_1SLASH/"/", T_1POUND/"#", T_1EQUAL/"=")
```
**`snobol4.tab.c` (the actually-compiled parser — no bison in this environment, `.tab.c` is hand-synced, not regenerated) was edited identically at the corresponding 7 `case N:` blocks**, verified one-to-one against the `.y` source via the embedded `#line "snobol4.y"` directives (monotonically increasing, no reordering) plus the bison rule-comment (`/* expr7: expr7 T_2POUND expr8 */`) on each case — not by position alone, to avoid silently corrupting a *real* arithmetic operator (`*`/`/`/`**` each also route through `TT_MUL`/`TT_DIV`/`TT_POW`, appearing as look-alike duplicate action text next to the ones that needed fixing).

## Two witnesses still red — NOT this row's fix, and NOT new regressions (both were already-red in the s105 census, before any of this session's or s192's work)

**`opsyn_rebind_twice.sno`** (m3 PASS, m4 empty output/DIFF) — SAME operator symbol (`&`) rebound twice at runtime to two different targets (`cat` then `rev`); oracle requires the *second* binding to take effect on the second call, i.e. no call-site caching of OPSYN meaning is legal. This is `f14_opsyn.sno`'s own m4 blocker too: `f14_opsyn.sno` OPSYN's `double`→`twice` (plain alias) *and* `!`→`twice` (unary, same target) — same defect family — m4 gets `42\n7`, silently dropping the `!21` line. **Root cause not fully found.** Localized as far as: `rt_proc_call_open("double"/"negate"/...)` returns 0/fail even in cases whose overall program output is correct, so the real dispatch for a plain OPSYN-established name in mode-4 does not go through the path I could find by static reading (`register_fn_alias`/`_func_buckets`, used by `APPLY_fn`, is NOT consulted by `rt_proc_call_open`/`rt_proc_find`, which only ever look at `g_rt_gen_procs` — so the working cases are succeeding through some other, uncharacterized mechanism). ⛔ **New data point beyond what R-8 recorded: this looks layout/memory-sensitive, not a clean deterministic bug.** Measured live this session: a minimal single-alias witness (`OPSYN('double','twice')` + `OUTPUT=double(21)`) printed the *correct* `42`/`198` (checked with two different inputs, so not a coincidental match) under an **incremental** build, then printed **nothing** for the identical `.sno` against a **freshly `make pristine`-rebuilt** tree with *no source change in between* — and separately, adding one `fprintf(stderr,...)` debug line inside `rt_proc_call_open` (later reverted) also flipped the same witness from correct-output to empty-output. Three different rebuilds of byte-identical logic, three different outcomes, on the same input. This smells like uninitialized memory or a dangling/stale pointer somewhere in the OPSYN-established-name call path, not a logic error visible from the source alone — gdb breakpoints on `rt_proc_call_open`/`NV_SET_fn` gave results that did not add up (`rt_proc_call_open` returning 0/fail even on runs that printed the correct answer), which is consistent with a real UB bug moving gdb's own observation around. **Recommend whoever picks this up next uses valgrind/ASan from the start rather than gdb breakpoints** — RULES.md's ASM-DIFF-FIRST order assumes a deterministic divergence, which this may not be.
