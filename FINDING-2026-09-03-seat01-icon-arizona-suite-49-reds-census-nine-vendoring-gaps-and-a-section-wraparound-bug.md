### Layer 1 — CURED (corpus-only): `link` name collision between IPL library modules and same-named Arizona/JCON standalone tests
`core.icn` (vendored last session) itself does `link io; link lists; link random; link scan; link sets;`; `factors.icn` does `link io`; `strings.icn` does `link lists`. SCRIP's `icn_resolve_links` (`src/parsers/icon/icon_driver.c:26-45`) resolves every `link` by exact `<invoking-file's-dir>/<name>.icn` lookup — one directory, no library search path. Because this Arizona `general/` directory *also* independently ships standalone JCON-sourced tests literally named `io.icn`/`lists.icn`/`random.icn`/`scan.icn`/`sets.icn` (each with its own `procedure main()`), those five `link` statements silently resolve to the **wrong** file — not the real upstream library at `/home/resources/icon-master/ipl/procs/{io,lists,random,scan,sets}.icn`, which last session's vendoring census never flagged as missing (a file of that name already existed; the census only detects *absence*, per the "non-empty is not alive" false-signal class). Confirmed byte-for-byte: our `general/lists.icn` diffs identical (module semicolons aside) to upstream `icon-master/tests/general/lists.icn`, the JCON *test*; upstream `ipl/procs/lists.icn`, the real *library*, has zero `procedure main`.

`icn_resolve_links`'s `ast_push` merges a linked file's entire top-level AST into the program with **zero duplicate-symbol detection** (read directly, not inferred) — so when `core`'s closure pulls in five extra `procedure main` definitions alongside `ilib`'s own, whichever gets registered last in the (unguarded) symbol table silently wins as *the* program. For `ilib`'s specific link order this was never `ilib`'s own main — explaining the **zero-stdout, immediate `Error 5` symptom** exactly (nothing of `ilib`'s real body ever ran). For `mega`'s different link order (reaches the same five names via `numbers`→`factors`/`strings`, not via `core` directly), a different duplicate apparently won, one that happened to produce clean-looking output with just the reported pad defect — coincidence of link order, not evidence mega was actually close to passing.

**Cure** (corpus only): vendored the real `ipl/procs/{io,lists,random,scan,sets}.icn`, semicolonized identically to the original 17, under **non-colliding names** `{io,lists,random,scan,sets}_lib.icn`; also vendored `equiv.icn`/`indices.icn` (transitively needed by the real `lists.icn`/`io.icn`, no local collision, plain names kept). Repointed the five colliding `link` sites (`core.icn` ×5, `factors.icn`, `strings.icn`) plus one further transitive hit inside the newly-vendored `io_lib.icn` itself (`link random` → `link random_lib`) to the new names. One more fix needed to reach a clean parse: `io_lib.icn`'s `components()` has genuine upstream Icon `return case ... of {...} ||| expr` with the operator un-parenthesized after the case's closing brace — SCRIP's `parse_expr` (`src/parsers/icon/icon_parse.c` ~572-676) dispatches `case`/`if`/`every`/`while`/`until`/`repeat`/`create`/`suspend` as early-return branches directly in the outermost expression-grammar function rather than at `parse_primary`/unary level, so none of these keyword-led constructs can feed a trailing binary operator unless parenthesized — **a real, general SCRIP parser limitation, confirmed by reading the grammar, not fixed** (only worked around locally: added explicit parens around the `case` in our vendored copy, semantically inert, same spirit as the semicolon-insertion already used for these files). Not minted separately since it has exactly one live witness and the workaround is trivial and permanent; noted here for anyone hitting the same shape elsewhere.

Verified via full suite, **zero regression**: `ARIZONA_SUITE_BOARD total=89 m3_pass=44 m3_reject=0 m3_fail=45 m4_pass=45 m4_reject=0 m4_fail=44` — byte-identical fail list to the pre-session-2 baseline (`techo`/`lists`/`substring` from classes 1/2 still PASS; nothing else moved).
