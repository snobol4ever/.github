## 1. THE EXACT BUG, CONFIRMED (not seat06's "somewhere in the chase-loop" — this is the precise defect)

`src/driver/scrip.c`, the mode-4 dentry-resolution block (~line 1470-1486), for a `DEFINE` statement node `_c` (n_operands==0, e.g. `roman`'s `DEFINE('roman(n)t')` in `demo03`):

```c
for (int _q = 0; _q < s2->proc_count; _q++) { ProcEntry *_pr = &s2->proc_table[_q]; if (!_pr->name || strcmp(_pr->name, IR_LIT(_c).sval)) continue;
    IR_t *_sn = bb_proc_entry(_pr); if (!_sn) continue; int _sg = 0; while (_sn && (_sn->op == IR_SUCCEED || _sn->op == IR_FAIL || _sn->op == IR_GOTO) && _sn->γ.node && _sg++ < 64) _sn = _sn->γ.node;
```

**`_pr` (found by an EXACT name match against `IR_LIT(_c).sval`, i.e. `"roman"`) is `proc_table["roman"]` — the `sno_build_call_stub` STUB, role 4. Its entry node `_sn`/`_gd` is `sno_build_call_stub`'s own `IR_GOTO_DEFERRED` node (`.sval` also `"roman"`).** For every plain `DEFINE` without a separately-tracked body (the classic Gimpel inline idiom — a labeled statement inline in the main statement list, guarded by a `:(label)` skip on the `DEFINE` line itself — `demo03`'s `roman` is exactly this shape, and it is the ONLY shape `def_body[di]==NULL` produces), `_gd->op` is **always** `IR_GOTO_DEFERRED`, so the buggy branch fires unconditionally for this whole class, never the correct one below it.

The buggy branch does a **second, independent** lookup: search `proc_table[]` for `"LBL__roman"` (a *different* entry, populated at lowering time — `src/lower/lower_snobol4.c:2679-2703` — by `bb_label_landing("roman")`, i.e. the RAW label-anchor for the literal statement labeled `roman` in the merged main graph), then chase ITS entry through the same `SUCCEED/FAIL/GOTO` skip-loop. **Measured via a temporary γ-chain dump (methodology in §2): this anchor's γ-chain is `IR_GOTO → IR_STATEMENT_BEGIN → IR_VAR (the parameter `n`) → IR_MATCH_BEGIN (roman's real body, `roman`'s emitted `n855_match_begin_α`) → ...`.** The skip-loop's allowlist (`SUCCEED`/`FAIL`/`GOTO` only) stops at the first non-allowlisted op — `IR_STATEMENT_BEGIN` (hop 1) — landing on `n853_statement_begin_α`, a bookkeeping marker, not real content. This is **exactly** what seat06 measured by hand (and what their `IR_STATEMENT_BEGIN`/`END`-widening attempt advanced by one more hop, to `n854_var_α`, still short).

**The correct value was sitting in the SAME loop's own fallback branch, three lines down, unreached:** any `_pr` found by exact name match is **unconditionally** emitted with label `"<fname>_α"` by the named-proc emission pass, regardless of what its entry node's own op happens to be — the second lookup is not needed at all for this shape. `roman_α`'s own compiled body (verified in the `.s`, see §2) already does the stub's real job: recursion-safe parameter save/restore into a fresh 80-byte frame, **then itself jumps to `n853_statement_begin_α`** — i.e. `roman_α` is precisely what `rt_define_site`'s `fn` should be; `n853` is only valid to enter *after* `roman_α`'s own prologue has already run, which is exactly what the SIGSEGV is: `roman()` gets called (especially the recursive `REPLACE(roman(n), ...)` at line 11), jumps straight to `n853`, and the parameter-binding/frame-swap that recursion depends on never happens.

## 3. Three fix attempts, each measured, each reverted — read before trying a fourth

**Attempt 1 — in scrip.c, remove the buggy branch entirely (always use the `"<fname>_α"` fallback), clearing `dentry_entry` to NULL (matching the fallback's existing convention exactly).**
Measured: `rt_define_site`'s `fn` correctly became `roman_α` — **but `roman_α`'s own body silently disappeared from the `.s` entirely** (label referenced, never defined). Runtime result: `Error 22 Undefined function called` instead of SIGSEGV — different failure, still wrong.
**Why:** `dentry_entry`'s non-NULL-ness is read a second time, independently, at `emit.cpp:1219` (`_realstub = g_emit_cfg->dentry_entry[_dq] ? 1 : 0`), which gates a *separate* inline emission (`g_emit.op_define_role = 5`) that turns out to be what actually produces the stub's compiled body. Clearing `dentry_entry` to signal "no further lookup needed" also silently signalled "this stub doesn't need a body."
Reverted (this specific hunk only; not yet a full revert).

**Attempt 2 — same branch removal, but keep `dentry_entry = _sn` (non-NULL, preserving the `_realstub` signal) while also setting `dentry_name` directly to `"<fname>_α"` up front (bypassing the need for `emit.cpp:2982`'s retroactive fill, which can never fire here anyway since `_sn` lives in the stub's own separate graph, never part of the flat main-chain `nodes[]` the retroactive fill scans).**
Measured: `roman_α`'s body came back, `rt_define_site`'s `fn` was correctly `roman_α` — **but `roman_α`'s own body now ended with `jmp roman_α` (a self-jump)**, confirmed by a temporary trace inside `bb_define_sr()` (`src/templates/bb/bb_define.cpp`, the `role==4` branch, `en4`/`_.lbl_t0`): the exact same `g_emit.lbl_t0` value my fix set for `rt_define_site`'s benefit is **also** read by this second, unrelated consumer — `bb_define_sr()`'s role-5 firing (`inl5=1`, triggered inline by `emit.cpp:1219`'s `_realstub`-gated block, `g_emit.op_ival=5` temporarily) — to compute where the stub's OWN body should jump to *after* its parameter-binding prologue completes. In the original bug, both consumers coincidentally received the same (wrong) value, which happened to be *correct for the second consumer's purpose* (n853 really is where the prologue should jump to) while wrong for the first. Fixing the shared field's value for consumer 1 broke consumer 2.
Reverted entirely (`git diff --stat src/driver/scrip.c` confirmed empty).

**Attempt 3 — leave scrip.c completely untouched (attempt 1+2 fully reverted); instead fix ONLY `bb_define_bind()` (role 6, the actual `rt_define_site` caller, `src/templates/bb/bb_define.cpp`) to compute its OWN `blbl` (the `fn` argument) as `fname + "_α"` directly, bypassing `_.lbl_t0`'s VALUE for this one consumer while still gating on `_.lbl_t0`'s truthiness (preserving the existing `rt_ab_undef_fn_stub` fallback for whatever legitimate case that protects) — architecturally the correct separation: role 6 and role 5 stop sharing one field's value for two different meanings.**
Measured via a byte-level `.s` diff against the pristine (unmodified) build: **exactly one line differs anywhere in `n851_define_bx`'s emitted body** — the intended `lea r9, [rip+roman_α]` in place of `lea r9, [rip+n853_statement_begin_α]`. `roman_α`'s own tail is confirmed unchanged (`jmp n853_statement_begin_α`, matching the pristine build exactly) — the architectural separation worked as designed. **Yet this still SIGSEGVs**, with a *different* crash: `gdb` shows the fault inside (or very near) `n851_define_bx`, at `mov (%rdi),%rax` where `rdi` is computed from `mov 0x18(%rcx),%edi; add r8,rdi` — `rcx` holds `0x40e4bf`, which looks like a raw code address (not an obviously valid data-structure pointer) being dereferenced with a field offset. **Not root-caused.** This instruction sequence does not correspond to anything visible in `bb_define_bind()`'s own source (read in full, lines 267-305) — it is most likely inside `x86_pair_loop()` or `x86_ro_seal_str()` (called at the tail of `bb_define_bind()`, neither read this session) or is a `gdb` nearest-symbol misattribution of an address that is actually inside `bb_ab_seal_alpha`'s or `rt_define_site`'s own C implementation (both read this session, both look simple/safe on inspection, which argues against them but doesn't rule them out — e.g. lazy PLT resolution behavior wasn't specifically checked).
