## Part A — the two real bugs, and why session 2's own narrowing led away from them

Session 2 had narrowed defect (2) to "the static ζ-storage slot offsets `bb_subscript2()` reads via `FRQ()` don't match what the operand-producing boxes actually wrote." That framing was **half right and half a red herring**, discovered by reproducing the original bug faithfully (same design, same reapplied diff) with additional instrumentation:

1. **The real bug wasn't in the `FRQ`/static-offset arithmetic at all.** Instrumenting `emit_drive`'s 3-operand branch and the template's own entry point showed the static offsets flowing through *unchanged and internally consistent* end to end. The actual discrepancy: `bb_subscript()` (the existing, working 2-operand box) has **two addressing branches** — an `_.op_zres` branch using `ZOPQ()`/cell-relative addressing, and a fallback using `FRQ()`/frame-relative addressing directly off the static offset. Under this build's *default* ζ-storage selector, ordinary SNOBOL4 subscript nodes take the `op_zres` branch (confirmed: `zd_wl_kind(IR_SUBSCRIPT)` already returned 1 for the 2-operand case *before* any of this row's changes — it is normal, not a rare mode). `bb_subscript2()` never implemented that branch at all — it only had the `FRQ` fallback, unconditionally. That fallback's raw static offsets are correct as *offsets*, but they're not the address family this build's default configuration actually reads through at that program point, which is what produced the "off-by-a-net-shift" symptom session 2 was chasing. Confirmed by grepping `src/lower/lower_icon.c` (the other, pre-existing 3-operand `IR_SUBSCRIPT` consumer, Icon's `s[i:j]` section syntax, `bb_section()`) — its `op_zres` value and `ZOPQ`-branch addressing are the direct precedent this box was missing.

   **Fix:** added an `op_zres` branch to `bb_subscript2()`, structurally identical to `bb_subscript()`'s existing one, extended from 2 to 3 operands (`ZOPQ(0..2, 0/8)`). The pre-existing `zd_nops`/`zd_wl_kind` changes from session 1 (which session 2 had flagged as an unrelated "red herring," touching a mechanism the template never consulted) turned out to be **necessary but not sufficient** — they're what makes `op_zread[2]` populate at all for a 3-operand `IR_SUBSCRIPT`; the missing piece was consuming that population in the template. Both were required together.

2. **A second, independent, more consequential bug**, found only after the first fix still failed the differential battery's out-of-bounds case (`corpus/crosscheck/rung11/1112_array_multi.sno`, confirmed via a true `git stash` baseline to regress cleanly against origin/main — not a pre-existing failure). The new combined-dispatch runtime functions (`c_rt_subscript_var2`/`_lv` in `pattern_match.c`) fall back, outside the narrow in-bounds-array guard, to the exact pre-existing two-hop chain — but as a **single monolithic C function calling both hops unconditionally**, whereas the *old* lowering built that same two-hop chain as **two separate `IR_SUBSCRIPT` boxes**, each with its own `cmp al, DT_FAIL` / `x86_omega("je")` wiring. A first-hop **failure** (e.g. an out-of-bounds index — a normal, expected SNOBOL4 pattern-match failure, not an error) would short-circuit straight to the whole expression's failure port in the old lowering. The new single-function fallback had no such short-circuit: it fed the first hop's `FAILDESCR` result straight into the second hop as its *base*, and `c_rt_subscript_var_container_only`'s type guard (`if (b.v != DT_A && b.v != DT_T)`) turned that into a **hard runtime error** (`kwb_error(235)`) instead of a graceful pattern-match failure. Separately (and needed regardless, though not sufficient alone): the fallback was calling the `c_`-prefixed pure-C entry points (`c_rt_subscript_var_container_only`) rather than the ASM-exported ones the old lowering's emitted code actually calls (`rt_subscript_var_container_only`/`rt_subscript_var`) — switched to match, on the reasoning that the exported names are the ones proven-correct by every existing call site.

   **Fix:** check the first hop's result for `DT_FAIL` and return `FAILDESCR` immediately rather than attempting the second hop.

Neither bug is what session 2's narrowing pointed at. The static-offset arithmetic that session 2 spent most of its time on was correct throughout; tracing it that far was not wasted (it definitively ruled out several other hypotheses with evidence, which is why this session didn't have to re-derive them), but the actual fix came from comparing against the *other* working precedent (`bb_section`) rather than from further arithmetic on the failing case alone.
