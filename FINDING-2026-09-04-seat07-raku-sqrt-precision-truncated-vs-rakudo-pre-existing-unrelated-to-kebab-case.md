# FINDING: Raku `say sqrt(2)` prints truncated precision vs. real Rakudo — pre-existing, NOT caused by the kebab-case lexer fix

Surfaced while verifying `raku-roast-100-percent-compile` pass (kebab-case identifier lexing, SCRIP this session). The master regression (`corpus_suite_harness.py run ../corpus/tests/raku/ALL.raku ../corpus/tests/raku/ALL.ref --lang raku --by-modes-column --modes m3,m4`) showed `FAIL m3 simple_program_37: output mismatch` / `FAIL m4 simple_program_37: output mismatch`, one entry worse than SCORE.md's cited baseline (`FAIL=0/859 both modes`, cross-confirmed at SCRIP `2db0e0421`).

**Not a regression from this session's change:** the entry is `say sqrt(2);` — no `$`/`@`/`%` token, no hyphen, nothing the kebab-case lexer edit (`raku.l` lines defining `VAR_SCALAR`/`VAR_ARRAY`/`VAR_HASH`) can touch. Structurally impossible for that edit to affect this program's tokenization.

**The actual mismatch:** `./scrip` prints `1.414213562` (9 digits after the decimal); real `/usr/bin/raku` prints `1.4142135623730951` (full double precision, matches `ALL.ref`). Pre-existing precision truncation in the double-to-string path, exposed now only because this session ran a full regression with a freshly (cold-cache) rebuilt binary — worth checking whether the SCORE.md `FAIL=0` cross-check at `2db0e0421` ran against a fully fresh build or an incremental one.

**Not root-caused — flagging, not fixing (out of this row's lane):** a plausible but UNCONFIRMED lead: `src/runtime/core/argval.c:28` formats a double with a bare `snprintf(buf, sizeof buf, "%g", d.r)` (C default 6 significant digits) — but the observed output has 9 decimal-place digits, not 6 significant digits, so this may not be the exact call site `say`/`rk_write` uses for a `Num` result. Whoever owns Raku runtime float formatting should locate the real site (search for the actual stringify path a `LIT_FLOAT`/builtin-`sqrt` result takes to `rk_write`) and decide the right fix (likely: shortest round-trip / full double precision, matching what other languages' real/float `say`-equivalents already need to get right — see the sibling `FINDING-2026-09-03-seat01-icon-real-toby-generator-prints-trailing-decimal-oracle-does-not.md`, a related but distinct float-formatting gap in Icon).

**Scope note:** left `simple_program_37` as a genuine (not new) FAIL; did not touch runtime float formatting. This session's row is the kebab-case lexer fix only — see the task baton ledger for that.
