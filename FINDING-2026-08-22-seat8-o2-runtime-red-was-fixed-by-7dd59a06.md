## ⭐⭐ (2) WHY THIS COMMIT, MECHANICALLY — A PLAUSIBLE ROUTE FROM A PERF BUG TO A CORRECTNESS BUG
`7dd59a06`'s own commit message frames it as PURE PERFORMANCE: `getenv()` was being called on every function/variable-access call because a `-2` "trace is OFF" sentinel failed a `< 0` cache guard (`-2 < 0` is true, so the guard never latches). It was measured and merged at `RT_OPT=-O0`, and its own text makes no `-O2` correctness claim — the author had no reason to suspect one.

But the four sites it touches (`rt_call_arr`, `rt_call_arr_impl` in `by_name_dispatch.c`; `NV_SET_fn`, `NV_PTR_fn` in `core.c`) sit on **every SNOBOL4 function call and every variable set/lookup** — among the hottest, most-inlined functions in the runtime.

⭐ **MEASURED SIDE EFFECT, this session:** the buggy (`< 0` guard) `-O2` runtime library is **310,396,624 bytes**; the fixed (`== -1` guard) `-O2` library is **33,460,704 bytes** — a **~9.3x size difference** from four one-character guard changes, both built from the identical `rm -rf out/rt_pic` clean-objdir state. Before the fix, the "check environment" branch is taken on *every* call (the sentinel is always `< 0`), so the optimizer cannot prove it cold/unlikely and it appears to be inlined at every hot call site instead of collapsing to nothing after the first call, the way the fixed version does. That is exactly the kind of inlining/code-shape explosion that can newly expose a latent miscompilation elsewhere (register allocation pressure under drastically larger inlined bodies, code layout shifting in ways that interact with hand-tuned RTX assembly's ABI/offset assumptions, etc.).

This FINDING does **not** claim to have traced the exact miscompiled instruction inside that ~277MB of extra inlined code — the revert-and-retest already gives unambiguous causal attribution at the commit level, and tracing the instruction-level mechanism inside a 310MB pathological build was judged not worth the further wall-clock this session.
