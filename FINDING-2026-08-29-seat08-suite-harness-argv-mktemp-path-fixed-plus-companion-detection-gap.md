## Headline
The mint's own diagnosis was correct as far as it went (argv carries a full `mktemp`-path, and the two-sided cure — bare basename in argv, matching name at capture time — is the right shape), but it named only two of the actual sites, and reading the code surfaced a **third, independent bug** in the same neighborhood that blocks one of the four named witnesses from converting at all.

## Fix 1 — argv is the bare basename everywhere `scrip`/the oracle gets invoked for grading
Three call sites passed a full (and, under `convert_one`, `mktemp`-varying) path as argv, where cwd was already correctly the source's own directory (or, for one site, not set at all):
- `run_m3` (`corpus_suite_harness.py:254`) — argv used `str(sno_path)`; cwd was already correct.
- `compile_m4`/`run_m4` (`:271`) — same, and **this subprocess.run call had no `cwd=` at all**, running from the harness's own inherited directory and only "working" because argv happened to carry a full path.
- `run_oracle` (`:179`) — same shape as `compile_m4`: full-path argv, no `cwd`.
All three now pass `Path(sno_path).name` and an explicit `cwd=str(Path(sno_path).parent)`. Verified directly (not just "should work"): a synthetic witness (`OUTPUT = &FILE`) run through the fixed `run_m3` from three different fresh `mktemp` directories produces byte-identical output every time; the same test against the fixed `run_oracle` is likewise stable.

## Fix 2 — capture and conversion must use the SAME canonical name, not a `"cand.sno"` placeholder
The mint's own citation (`corpus_suite_harness.py:512,525`) was `convert_one`'s two candidate-verification sites, both hardcoding `Path(td) / "cand.sno"`. **What the mint didn't have visibility into**: `run_suite_entry` — the function that grades an *already-converted* suite every single time from now on (`cmd_run`, `test_corpus_snobol4.sh`, every board script) — already used `Path(td) / f"{entry.name}{ext}"`, the witness's own real name, not a placeholder. So even after Fix 1, `convert_one`'s one-time verification would have echoed `"cand.sno"` while every future regrade echoes the witness's real name (e.g. `"ord_unimplemented.sno"`) — two different stable strings, still disagreeing. Changed both `convert_one` sites to `f"{name}.sno"`, matching `run_suite_entry`'s pre-existing, already-correct convention (the newer code should match the established one, not the reverse).

## Fix 3 — found while implementing, not in the mint: `convert_one` never copied companion files at all
`run_suite_entry` has always copied companion files (`_companion_files()`, an include/`open()` regex scan) into its temp dir via a `companion_dir` parameter — its own comment already said conversion-time *should* do the same, but `convert_one` never actually received or used one. This is invisible for companion-free witnesses, but **`probe/csnobol4_triage/input_eof_hang.sno` needs its empty `.dat` companion present to reproduce its documented (now-clean) behavior at all** — measured directly: with the companion present, `INPUT()` on it fails cleanly (rc=0, empty output); **without it, the identical program HANGS** (the original, pre-reclassification defect, in full). `convert_one`'s candidate ran in a companion-less temp dir, so its own conversion-verification step would have hit the hang, not the documented behavior — a silent trap for exactly this witness, unrelated to the argv/path bug but blocking the same DONE-WHEN. Factored the existing copy logic out of `run_suite_entry` into a shared `_copy_companions(text, companion_dir, dst_dir)` and called it from both of `convert_one`'s candidate sites.

## Fix 4 — also found while implementing: `_companion_files()`'s regex list never covered SNOBOL4's own `INPUT(...)`/`OUTPUT(...)` syntax
All three existing patterns cover directive-style companion references (`$include "X"`, `-INCLUDE 'X'`, Icon `open("X")`). SNOBOL4's `INPUT(.holder, 10, , "name.dat")` names its companion as a plain quoted **argument**, a shape none of the three patterns match — confirmed directly (`_companion_files()` returned `[]` against `input_eof_hang.sno`'s real source before this fix). Added `re.compile(r'\b(?:INPUT|OUTPUT)\s*\([^)]*["\']([^"\']+)["\']')`. Fix 3 alone was not sufficient without this — the companion-copy call had nothing to copy until this pattern existed.
