## Method note: the previous investigation's own root-cause paragraph was itself wrong

Before touching any code, re-traced both witnesses with gdb (`break` on `rt_proc_call_open`/`rt_call_arr_bl`/`_usercall_hook`/`NV_SET_fn` etc., `finish`/`continue` in breakpoint `commands` blocks — after two false starts: an implicit unnumbered `commands` block silently reattaches to the wrong breakpoint when an earlier `break` failed to resolve pre-`run`, and `finish` inside a `commands` block silently truncates the rest of the script if the frame it's finishing hits another breakpoint first; both avoided by using explicit `commands N` and by breaking at `main` first so the runtime `.so`'s symbols are resolvable). This directly disproved two assumptions carried in from the prior FINDING:

- `f14_opsyn.sno`'s m4 failure (`42\n7`, one line short of oracle) was recorded as "silently dropping the `!21` line." **It is actually `double(21)` that fails** — `!21` and `3 @ 4` both resolve their operator to a literal target-name string at COMPILE TIME (verified in the `.s`: `rt_proc_call_open` is called with the string `"twice"`, not `"!"`) and always worked. Both readings produce the same 2-line stdout (`double`→42 and `!21`→42 are numerically identical), so the wrong attribution was invisible from output alone — it took tracing `rt_proc_call_open`'s actual argument to see which call site really failed.
- The prior FINDING named `rt_proc_call_open`/`g_rt_gen_procs` as what "every mode-4 `CALL name(args)` compiles to" and separately named `rt_call_arr_bl`→`APPLY_fn`→`_usercall_hook` as the mechanism `opsyn_rebind_twice.sno` uses. Both are correct, but the FINDING never established *why* a plain-identifier alias (`double`) and a once-only-bound operator alias (`!`, `@`) both fold to a literal name and go through `rt_proc_call_open`, while a **rebound** operator (`&`, bound twice) cannot fold and goes through `rt_call_arr_bl` instead — confirmed this session by compiling each witness and reading the actual `.s` (`&`'s call sites carry no `rt_proc_call_open` reference at all; gdb confirms zero hits) and by reading `lower_snobol4.c`'s `sno_t4_scan`/`sno_t4_target` (rebinding the same operator symbol to a second target POISONS the compile-time fold, forcing dynamic by-name dispatch for every use of that symbol).

## Gap 1 — `g_user_call_hook` is never installed in a standalone mode-4 binary

`APPLY_fn` (`core.c:2809`) falls back to `g_user_call_hook` whenever a `_func_buckets` entry has `fn == NULL` (true for every OPSYN alias and every runtime `DEFINE(name)` with no C function — i.e. every ordinary SNOBOL4 procedure). The only assignment to this global, anywhere in the tree, is `scrip.c:1054` (`g_user_call_hook = _usercall_hook;`), inside `scrip.c`'s own driver `main()` — the code path for `./scrip prog.sno` (mode-3) and for `--compile` itself, **never linked into or executed by the standalone binary `--compile` produces.** A mode-4 program's own generated `main:` calls `core_lib_init()` (shared, `.so`-resident) and nothing else that touches this pointer.

Measured directly (gdb, `opsyn_rebind_twice.bin`, breaking at `main` then printing `g_user_call_hook`): `$1 = (DESCR_t (*)(const char *, DESCR_t *, int)) 0x0` at start and `0x0` again after the program exits. `_usercall_hook` itself IS linked and resolvable (it lives in `libscrip_rt.so`, same as `core_lib_init`) — it is simply never pointed to. So `APPLY_fn`'s fallback silently returns `NULVCL` (or, when the loop doesn't even find the name, falls through further and can raise error 5) instead of ever reaching `_usercall_hook`'s own alias-retry logic, IDENT/DIFFER/DATA dispatch, or Prolog resolve-table lookup — for mode-4 only. (Those builtins pass corpus regression because the compiler recognizes them and emits a direct call to `_builtin_IDENT` etc. at compile time in the common case; this gap only bites the by-name/indirect path.)

**Fix:** `core_lib_init()` (`core.c`) now wires the hook itself, guarded so it never overrides scrip.c's own explicit assignment:
```c
if (!g_user_call_hook) { extern DESCR_t _usercall_hook(const char *name, DESCR_t *args, int nargs); g_user_call_hook = _usercall_hook; }
```
This alone was sufficient to fix `opsyn_rebind_twice.sno` completely (both statements, both the pre- and post-rebind target).

## Gap 2 — `rt_proc_call_open`/`rt_proc_fn`/`rt_proc_jmp_entry` disagree about alias names, and they must not

For a call site whose target name folds to a literal string at compile time but isn't itself in `g_rt_gen_procs` (e.g. `double(21)`, alias only in `_func_buckets`), `bb_call_proc_staged.cpp` always emits **two** separate runtime calls keyed on that same name string: `rt_proc_call_open(name, nargs)` (validate + stage the call) and, only if that succeeds, `rt_proc_fn(name)` (fetch the actual function pointer to `jmp` into). `rt_proc_jmp_entry(name)` is a third member of the same family, read together with the other two per a `by_name_dispatch.c` comment on a different call shape.

Fixing only `rt_proc_call_open` (see below) made `double(21)` "succeed" (nonzero return) while `rt_proc_fn("double")` still returned `NULL` — the emitted code unconditionally does `jmp rax` on the success path, so this produced a clean SIGSEGV (measured: `f14_opsyn` m4 went from `rc=139` DIFF-turned-crash the moment the first-half fix landed, confirming the two functions must resolve identically or the caller's own control flow breaks).

**Fix:** factored one `static rt_proc_t *rt_proc_find_alias(const char *name)` helper (`rt.c`, placed once, before all three consumers) that redirects through `_func_buckets`' `entry_label` exactly like `_usercall_hook` already does (`FNCEX_fn` gate, `FUNC_ENTRY_fn` redirect, `rt_proc_find` on the resolved name) — and called it, consistently, as a fallback in all three: `rt_proc_call_open`, `rt_proc_fn`, `rt_proc_jmp_entry`. One helper, one place the logic can be read and reasoned about, so a fourth consumer added later has an obvious thing to call rather than an obvious thing to reinvent slightly differently.

## Gap 3 — the name-based RETURN convention re-resolves the alias name a second time, again unredirected

SNOBOL4 procedures return by convention: the callee assigns to a variable with its own name (`twice = x + x`), and the caller reads that variable back after the call. The compiled epilogue for this (`rt_proc_call_epilogue_named_γ`/`_ω` → `rt_proc_epilogue_named(name, failed)`, `rt.c`) is called with the **original call-site name** ("double"), and did its own bare `rt_proc_find(name)` — which fails for the same reason as gap 2, except here the consequence isn't a crash: the function returns `NULVCL` early, before ever reading `rname = p->name`. Fixing gaps 1+2 alone therefore dispatched `double(21)` to the *correct* function (`twice`'s real code, which correctly computed and stored 42 into the variable `twice`) but then read back the value from a variable named `double`, which nothing had ever set — an empty string, not a crash, not a `NULVCL`-vs-`FAILDESCR` distinction visible as anything but silently wrong output (`m4` regressed from "statement produces nothing" to "statement produces a blank line," measured, before this gap was found and fixed).

**Fix:** same `rt_proc_find_alias` fallback in `rt_proc_epilogue_named`. Once `p` correctly resolves to `twice`'s `rt_proc_t`, `rname = p->result_name ? p->result_name : p->name` is `"twice"` — the callee's OWN name, which is what SNOBOL4's return convention actually requires reading back regardless of what alias the caller used to reach it.

## Gap 4 (latent, not load-bearing for either witness, fixed anyway) — `register_fn_alias`'s fallback entry_label was self-referential

`register_fn_alias(newname, oldname)` (`core.c:2766`) looks up `oldname` in `_func_buckets` first; when found (true for both witnesses here, since `twice`/`cat`/`rev` are all also runtime-`DEFINE()`'d at the source level, which independently inserts them into `_func_buckets`), it correctly copies `entry_label` from that entry. When NOT found — `oldname` is a procedure that was only ever statically compiled, never separately `DEFINE()`'d at the source level — the old fallback set `fe->entry_label = fe->name`, i.e. the ALIAS's own name, not the target's. Since `_usercall_hook`'s (and now `rt_proc_find_alias`'s) whole retry mechanism is "if `entry_label != name`, retry with `entry_label`," a self-referential entry_label silently made that retry a permanent no-op for exactly the case it exists to handle. Neither witness this session exercises this branch (both aliased proc targets happen to have their own explicit `DEFINE()`), so this was found by reading the function while fixing the other three gaps, not by a failing witness — but it is the same subsystem, the same code path family, and a one-line, clearly-correct fix (`fe->entry_label = on;`, `on` being the already-`rt_ws_strdup`'d `oldname`), so it is fixed rather than left as a known landmine for the next OPSYN witness that happens to alias a purely-static target.

## Why this design, and not the previous session's reverted one

The prior attempt (see the FINDING it superseded) made `register_fn_alias` also populate a NEW `g_rt_gen_procs` entry for the alias name, copied by value from the target. That created a second, independent piece of state that had to be kept in sync with `_func_buckets`, and the SIGSEGV it produced was exactly a symptom of the two disagreeing (one path's fix visible, the other path's placeholder state untouched). Nothing in this session's fix creates new state anywhere: `g_rt_gen_procs` never gains an entry for an alias name; every consumer that needs to resolve an alias redirects, at read time, through the one table `register_fn_alias` already writes (`_func_buckets`) via the one field it already carries for exactly this purpose (`entry_label`). There is one source of truth for "what does this alias currently point at," and every consumer (`_usercall_hook`, and now `rt_proc_call_open`/`rt_proc_fn`/`rt_proc_jmp_entry`/`rt_proc_epilogue_named`) reads it the same way, so none of them can disagree with another about a rebound operator's current target.
