## Not SCRIP defects (read this before minting cure rows against SCRIP)

**#1 lowercase keyword (14 programs: `8bit2 breakline conv2 diag1 diag2 func2 hide k noexec space space2 setexit setexit5 setexit6`).** All 14 end in lowercase `end` (verified by direct inspection, not sampled). SCRIP reports "missing END statement" because it never recognizes the keyword — by design (RULES.md: SCRIP is case-sensitive, uppercase-only). **`lowercase_keyword.sno` run under `sbl -bf` ALSO fails identically** ("No END statement found in source file(s)."). Our own project-mandated correctness oracle enforces the same uppercase convention SCRIP does — this is a corpus-authoring-dialect mismatch (csnobol4_suite was written for a case-folding host), not a compiler bug. **The cure tool already exists and is unused here:** `scripts/util_uppercase_keywords.py` — built specifically to normalize a source file's keywords to uppercase without touching string/comment/user-identifier content, evidently applied to other suites already but not to this one. A cure row should be "run it against `corpus/packages/snobol4/csnobol4_suite/`, verify `scrip`+`sbl -bf` parity per file, commit" — not a SCRIP change.

**#2 missing corpus include target (10 programs: `base float2 include2 include3 include4 json1 ndbm random sleep time`).** Every `-INCLUDE` target (`basename.sno`, `host.sno`, `aa.sno`, `bb.sno`(×2), `../modules/ndbm/ndbm.sno`, `../modules/random/random.sno`, `../modules/time/time.sno`(×2), `json.sno`) is confirmed absent from the whole corpus tree by direct `find` — except `json1.sno`'s target, which exists at `corpus/demo/snobol4/json/json.sno` and `corpus/benchmarks/snobol4/demo/json.sno` but is unreachable because this suite's search path is `SELFDIR`-only (`scorecard_snobol4.sh`'s SUITES table). **`missing_include_target.sno` under `sbl -bf` fails identically** (`ERROR 285 -- include file cannot be opened`). This is the same class of defect RULES.md already documents for `corpus/programs/lon_cherryholmes/` (24 `-INCLUDE` files "nowhere in corpus") — a second, independent instance of the same corpus-completeness gap, this time in csnobol4_suite. Not a SCRIP bug; a corpus-fixture gap (9 files genuinely missing) plus one search-path gap (`json1.sno`, cheaply fixable by adding `demo/snobol4/json` to this suite's lib spec, or copying the file in).

**#5 RC1/RC1, representative `ord.sno` (calls the builtin `ORD`, character→ordinal, inverse of `CHAR`).** Isolated to a 2-line reproduction: SCRIP refuses at parse time ("Error 5 — Undefined function or operation", no output, rc=1). **`sbl -bf` also refuses it** — runtime `ERROR 022 -- undefined function called` — though SPITBOL degrades softer (continues to a final stats dump, rc=0) rather than refusing outright. Neither SCRIP's stated design target (SPITBOL semantics, per RULES.md) nor the correctness oracle implements `ORD`; it is very likely a CSNOBOL4-only extension outside SCRIP's declared scope, same family as the already-documented `popen`/`openi`/`setexit2` list, just not previously enumerated. **This bucket is NOT verified uniform** — only `ord.sno` was traced end-to-end; `labelcode.sno` and `maxint.sno` (2 of the other 7 RC1 members) are already on the known-CSNOBOL4-extension list independently, `rewind1.sno` is a stdin-routing case (see next section), but `file.sno intval.sno keytrace.sno update.sno` were not individually checked this pass and may be genuine SCRIP gaps — a cure-scoping pass should check each before assuming the whole bucket is out-of-scope.

## Confirmed SCRIP defects

**#4 representative, `content_after_end.sno` (4 lines): SCRIP does not stop scanning at a valid `END` statement.** Two identical trailing lines after `END` produce a spurious "duplicate label" parse error; `sbl -bf` prints its one line of real output and exits 0, ignoring the trailing text entirely as standard SNOBOL4 requires. Root cause, confirmed by line numbers, for `sudoku.sno`: `END` is at line 128, but line 205's "duplicate label" error names `5---649--`, a puzzle-grid data row that is **not** unique in the trailing data — the identical string also appears at line 194. **This is very likely also the true cause of `atn.sno`, `crlf.sno`, `trim0.sno`, `trim1.sno`, `uneval2.sno`** — all five, like `sudoku.sno`, are named in `test_csnobol4_budne_suite.sh`'s `STDIN_TESTS` list (programs whose file continues past `END` with data meant to be piped as stdin, per Budne's own harness convention), and all five show the same "syntax error + missing END" signature — **but this pass only individually traced `sudoku.sno`; the other four are a plausible, not confirmed, extension of the same root cause.**

⛔ **Separate, compounding harness gap, also worth flagging (no SCRIP fix required for this half):** `scorecard_snobol4.sh`'s `stdin_for()` has no knowledge of the Budne `STDIN_TESTS` split-at-`END` convention (`atn crlf longrec rewind1 sudoku trim0 trim1 uneval2`) — it only checks for a sibling `.input`/`.in` file, and none exists for these 8. So even after SCRIP is fixed to stop at `END`, these 8 programs would still receive `/dev/null` on stdin instead of their real test data under the scorecard, and would likely shift from COMPILE_FAIL to DIFF/TIMEOUT/RC\<n\> rather than PASS. Both fixes are independently necessary.

**#4 (DIFF) representative, `dump_unimplemented.sno` (3 lines): `&DUMP = 1` is silently a no-op.** SCRIP accepts the assignment (rc=0) but never emits a termination dump; `sbl -bf` prints the real "dump of natural/unprotected keywords" report `a.sno`'s `.ref` expects. Unlike `ORD`, `&DUMP` **is** implemented by the oracle SCRIP targets — a genuine, confirmed gap. **Bucket not verified uniform**: only `a.sno` was traced; the other 15 DIFF members include at least 3 (`popen.sno popen2.sno loaderr.sno`) already on the known-CSNOBOL4-extension list, so the bucket is likely a similar (defect + out-of-scope-extension) mix to classes #3/#4/#5, not fixable as one patch.

**#6 TIMEOUT, representative `input_eof_hang.sno` (uses the real `openo2.sno` shape: `INPUT()` on an exhausted/empty file, `OUTPUT = holder :S(loop)`): SCRIP's file `INPUT()` never signals read failure at EOF — the success branch fires forever.** Bounded at 3s, the witness wrote 777,813 lines to stdout before being killed; the real `openo2.sno` under the scorecard's 20s budget presumably writes tens of millions. `sbl -bf` on the identical construct fails fast instead (`ERROR 116 -- inappropriate file specification for input`, rc=0, no hang). This is the most severe class found this pass — an ordinary EOF condition causing unbounded output/CPU rather than a bounded, well-defined failure — worth prioritizing over the cosmetic classes above regardless of its small (2-program) membership.

**#7 `-INCLUDE` trailing space, representative `include_trailing_space.sno`: the quoted `-INCLUDE` argument is taken byte-for-byte, including a trailing space inside the closing quote, instead of trimmed.** Confirmed present in the **upstream, unmodified** suite source: `line.sno` line 8 literally reads `-INCLUDE "line2.sno "` (verified with `cat -A`; the other two `-INCLUDE "line2.sno"` lines in the same file, lines 2 and 11, have no trailing space and succeed). `sbl -bf` trims it and includes the file cleanly; SCRIP looks for a file literally named `target.sno ` (with the space), which of course never exists, and refuses to compile. Narrow, mechanical, oracle-confirmed SCRIP lexer defect in `-INCLUDE` argument extraction.

**#8 link-only failure (RC1/ASM_FAIL), representative `setexit_label_pruned.sno`: a label reached only via `SETEXIT(.label)` — never by an explicit GOTO or fallthrough — has its own code emission pruned as unreachable, but mode-4's `__gva_names` address table still emits a reference to the pruned symbol, so `gcc -no-pie` linking fails (`undefined reference to LBL__eh35`).** Mode-3 (in-process binary) does not hit this — an m3≠m4 divergence, worth flagging against CLAUDE.md's "m3 ≡ m4 output is a design invariant." Ablated from `setexit7.sno` (which independently reproduces the identical failure at all three of its handler labels: `eh35`, `eh19`, `eh24`). ⚠️ **Reproduction is more specific than "any SETEXIT-only-reached label": during ablation, a same-shape handler whose body does NOT read `&LASTNO` linked cleanly (rc=0) — only a body that reads `&LASTNO` reproduces the dangling reference.** The witness preserves the exact working shape rather than the simplified version that stopped reproducing; the precise mechanism (why `&LASTNO` specifically is load-bearing) was not traced past the optimizer/emit boundary and is a fair starting point for whoever picks up the cure row. `sbl -bf` has no link stage to compare against; it accepts the `SETEXIT`/`.label` construct without complaint (the ERROR 037 it reports is from the witness's own deliberately-artificial `:(CONTINUE)`-with-nothing-to-continue-from, unrelated to the label question).
