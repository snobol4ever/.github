## The cure: a second-character guard closes a hole in an existing idiom
Line-level `callgrind_annotate` on `by_name_dispatch.c` (not just function totals) found the exact shape of `80a01c63`'s "bind the call, fold the name" pattern already partially applied here — `bid_bake` (hq_P s262) already resolves `bid_of()`/`strlen()` at SCRIP-emit time via the `bidlen` parameter, so `_fnlen`/`_bid` inside `try_call_builtin_by_name_bl` are cheap ternaries, not runtime hashing, for any baked call site. What line-level annotation found was NOT that pattern being absent, but a narrower, adjacent bug: `rt_call_arr_impl`'s existing "first-character guard" (itself a prior instance of this same idiom, hq_P s262, `by_name_dispatch.c:4658`) reads:

```c
if (fn[0] == 'S' && !strcmp(fn, "SNO$NOFAIL")) { ... }
```

`fn[0]=='S'` is true for `SIZE`, `SPAN`, `SORT`, `STRING`, `SUBSTR`, `SET`, `SUCCEED`, and every other ordinary 'S'-leading builtin — none of which can possibly equal `"SNO$NOFAIL"` past the second byte, yet all of them paid a full `__strcmp_avx2` PLT hop to find that out. Measured: 21,000 `SIZE` calls in string_manip alone cost 651,000 Ir (1.27% of the kernel) confirming a name the guard's own comment already said was knowable more cheaply. Since `strcmp(fn,"SNO$NOFAIL")==0` implies `fn[1]=='N'` (every internal `SNO$xxx` name — `SNO$NAME`, `SNO$NRET`, `SNO$KWSET`, etc. — shares that two-byte prefix, but no ordinary builtin does), adding `fn[1]=='N'` is a **strictly narrower pre-filter**: it can only skip `strcmp` calls that were already guaranteed to fail, never change the answer for `SNO$NOFAIL` itself or its `SNO$xxx` siblings (which still correctly fall through to `strcmp`). One-line change, `by_name_dispatch.c:4662`.

## Why the cure stopped there — two structural pieces remain, both correctly out of this session's scope
Line-level annotation of `try_call_builtin_by_name_bl`'s own body (5,166,515 Ir self-cost) breaks down almost entirely into machinery that exists to validate, on **every** call, that OPSYN/DEFINE hasn't rebound the name since the dtax cache entry was written — `_bid`/`_fnlen` derivation (already cheap, baked), a branch selecting array-index vs. hash lookup (966,046 Ir, 1.89%), the cache-hit `memcmp` validation (798,011 self + 839,980 callee, ≈3.2%), and the indirect-call dispatch itself (755,982 Ir, 1.48%) plus prologue/epilogue (1,092,052 Ir, 2.13%). None of this is redundant *string* resolution (that part is already fixed) — it is OPSYN-correctness bookkeeping that cannot be removed without either:

1. **A genuinely new persistent cache cell** (per-call-site or an extended shared array) validated by a cheap generation check instead of a full lookup+memcmp, the true full extent of the `80a01c63` pattern (that commit's `alpha_slot` had an *existing* per-proc record to extend; by-name call sites have no equivalent yet) — **this requires a new global/persistent-state addition, which CLAUDE.md gates behind Lon's explicit in-chat permission that session.** Not asked for or assumed here. **Minted `perf-dispatch-callsite-cache`** (rank 1), STEP 1 of which is exactly that ask, with STEP 2 a permission-free investigation of whether widening the *existing* `g_dtax_bid` array gets most of the win without needing a new global at all.

2. **The GC safepoint call** `rt_gc_point_arr(args, nargs, (const char **)0)` at `by_name_dispatch.c:4656` — confirmed via line-level annotation to be the *entire* source of the 3.61% GC-safepoint cost seat04's LEDGER entry flagged as "plausibly eliminates with the same fix... verify when curing, don't assume it's free." Read the implementation before touching anything: the asm veneer (`rt_asm_helpers.S:100-122`) unconditionally parks all six callee-saved registers on *every* call, before the cheap `g_gc_pending`/`g_hp_top` check inside `rt_gc_point_arr_c` even runs — the comment describes this as letting "the collector's repairing scan" fix up stale pointers "across a collect," language that reads as keyed to coroutine/co-expression suspend-resume, not to an ordinary non-suspending builtin call. That reading is a **hypothesis, not a finding** — this same session's `.github` history (`FINDING-2026-08-24-seat07-tag-predicate-o0-call-tax-and-allocator-closure.md`, section 1) records `always_inline` being tried and reverted at s264 for the *same genus* of mistake (an assumption about what the conservative GC stack scanner can tolerate, wrong in a way that only surfaced as broken deferred-capture tests and a 4s→402s wall-time cliff, not a compile error). **Minted `perf-dispatch-gc-safepoint-necessity`** (rank 2), scoped to require proving the mechanism before any code moves, the same bar `setjmp-per-builtin-call` already sets for its own guard on this identical call chain.
