## ⭐⭐ Class C is the actual headline, and it is not a parser gap at all

Minimal repro, verified in `--run` (m3):
```snocone
i = 1;
while (LE(i, 3)) {
    OUTPUT = i;
    i = ADD(i, 1);
}
```
Output: `1`, then `** Error 5 in statement 0 / Undefined function or operation` — a **SNOBOL4-level runtime error**, not a Snocone parse failure. `--dump-ast` shows a perfectly correct `TT_WHILE` node (condition `LE(i,3)`, 2-statement body) — the parser is not at fault. **Ablated to a single-statement body** (`i = ADD(i, 1);` alone, no `OUTPUT`) — same error, zero output first, confirming the failure is in the loop-back/condition-recheck path itself, independent of body content. **`for` shares the identical signature** (`for (i = 1; LE(i, 3); i = ADD(i, 1)) { OUTPUT = i; }` → prints `1`, same Error 5) — one mechanism, not two, almost certainly in whatever `lower_snocone`/`lower_snobol4` machinery both constructs share for loop re-entry (Snocone's `while`/`for` most likely both lower to the same SNOBOL4-goto loop shape). **Every one of the 9 class-C files times out/errors after printing exactly one line's worth of output** — consistent, not intermittent.

This means **basic Snocone loops do not iterate** in the current tree. Not investigated further here (out of this row's scope — this FINDING is the mint, not the fix), but `lower_snobol4.c`'s WHILE/FOR lowering (likely a generated label or resume-point that is only valid for the first pass) is where the next session should start, ASM-diff-first between iteration 1 and the (never-reached) iteration 2.
