## ⭐⭐ THE FINDING: "the fast-path hit itself" is not one line's cost — it's a DWARF line-tracking artifact spanning TWO unrelated `if` statements

Every prior session's breakdown (seat12's mint, carried forward by seat01 and seat07) treats "protected-pattern guard" and "the fast-path hit itself" as two separate, independently-understood cost buckets on two different source lines. `callgrind_annotate`'s per-line view of `core.c` appears to confirm this split — but it doesn't, and the confirmation is an illusion of the same class seat07's own FINDING on this row already caught twice (the invisible `_var_find_cached` gap, the too-short hand-scan window). This is a **third instance**, on the same function, of a different failure shape: not a missing gap this time, but cost visibly printed against the **wrong line**.

`callgrind_annotate src/runtime/core/core.c` on this session's own fresh `cg.out` prints, unambiguously:
```
13,403,067 ( 3.76%)      if (g_protected_pat_vars_armed && name && is_protected_pat_lead(name[0]) && is_protected_pat_name(name)) {
         .               if (!name) return val;
         .               if (!g_call_fastpath_off && name[0] != '&') { NV_t *e = _var_find_cached(name); if (e) { if (e->is_gva) *e->cell = val; else e->val = val; if (g_comm_dbg != 0 || trace_set_n != 0 || monitor_fd >= 0) comm_var(name, val); return val; } }
```
The entire 13,403,067 Ir sits on the protected-pattern-guard line (`core.c:2371` today); the memo-based fast-path line (`core.c:2376`, the one every prior session's prose calls "the fast-path hit") shows **zero**. Read naively, this says the guard costs 13.4M Ir and the fast path costs nothing — which cannot be right (`is_protected_pat_name` is never even called, see below; a bare armed-check-then-fail can't cost 13M Ir on its own), and does not match the row's own long-standing prose describing 2376 as the expensive one.

**Verified against ground truth, not another display heuristic**: `objdump --dwarf=decodedline out/libscrip_rt.so`, filtered to the address range covering both statements (0x35d090–0x35d2e6), shows the compiler's own address→line table, not `callgrind_annotate`'s rendering:
```
core.c   2371   0x35d0ad  (armed-check, name-check, is_protected_pat_lead call-site glue)
core.c   2314   0x35d0de  (_var_find_cached's OWN inlined body -- correctly separate, matches seat07's gap-closure exactly)
...
core.c   2321   0x35d229
core.c   2371   0x35d230  <-- JUMPS BACK to 2371's marker, and stays there through:
core.c   2371   0x35d245  (the is_gva field check + *e->cell=val / e->val=val store)
core.c   2371   0x35d292  (the g_comm_dbg / trace_set_n / monitor_fd three-way guard)
core.c   2371   0x35d2b3  (the conditional comm_var call)
core.c   2371   0x35d2d3  (return-value staging)
core.c   2371   0x35d2e1  (end of this address run)
core.c   2372   0x35d2e6  (core_runtime_error(42,...) -- the NEXT statement, correctly its own line)
```
**Every single instruction implementing line 2376's actual logic — the `is_gva` dispatch and store, the three-way debug/trace/monitor guard, the conditional `comm_var` call, the return — is tagged by the compiler's own debug-info emitter with line 2371's number, not 2376's.** Only `_var_find_cached`'s own inlined body (2314–2321) gets its correct, separate line numbers; everything textually *around* that inlined call, on both sides, collapses onto whatever line number was "current" before the inline expansion. This is not a `callgrind_annotate` bug and not an artifact of `--separate-callers` — it is literally what GCC `-O0 -g` wrote into the object file's line-number program for this specific shape (two adjacent cascading-`if` statements, the second containing an `always_inline` call in its condition, with no statement between them that would force a fresh `.loc` emission). No further root-causing attempted at the GCC-internals level — the *effect* is what matters for this row, and it is now proven from the authoritative source, not inferred.

**What this means for item 3, concretely:** the 13,403,067 Ir figure genuinely is real, fully-accounted, and belongs to *both* statements combined (protected-guard wrapper + full fast-path body), not to either one alone as previously believed. There is no way to cite "the guard costs X, the fast path costs Y" as two separate numbers from this profile — the tooling cannot separate them here. Anyone wanting that split would need either a source-level restructuring that forces GCC to emit a fresh `.loc` between the two statements (e.g. inserting a no-op statement — not attempted, feels like curing the wrong problem for a diagnostic-only reason) or accept the combined figure as the unit of analysis, as this finding does.

## Where the real, reducible cost is: the three-way debug/trace/monitor guard — and why it's blocked, not cured

Within the combined 2371-attributed block, the one candidate for a safe, structural reduction is the guard `if (g_comm_dbg != 0 || trace_set_n != 0 || monitor_fd >= 0) comm_var(name, val);` (source line 2376). Disassembly of the built binary (`objdump -dS`) shows it as three separate global-variable loads plus up to two short-circuited compares plus a conditional call-skip — `g_comm_dbg` and `trace_set_n` are `static` (direct RIP-relative load, one instruction each) but `monitor_fd` is a non-`static` `extern int` (`core.h:300`), so its load costs an extra GOT-indirection instruction. All three genuinely must be re-checked on every call, not just once at startup — unlike a killswitch-style `getenv` memo (`repl_pl_off`, `dtax_off`, `_nv_memo_off_get`, all elsewhere in this codebase), these three can change **mid-program**: `TRACE()`/`UNTRACE()` increment/decrement `trace_set_n` from anywhere, and while `monitor_fd` and `g_comm_dbg` are effectively fixed after early init, `trace_set_n`'s dynamism means the guard cannot be hoisted or cached the way those other checks were.

**The only real lever — packing the three checks behind one cached OR-flag — requires a new global**, and RULES.md is explicit and absolute here: *"No new global variables anywhere without Lon's explicit in-chat permission that session... The ask itself must be a large ⛔ banner naming proposed global, type, owning file, purpose, and why registers/stack cannot carry it... A commit adding one without a cited grant is rejected."* This is a fully autonomous FLEET session with no live grant available. **Not attempted, not worked around** — checked first whether an existing combined flag already does this job (it doesn't: grepped for any prior `g_any_observer`/`comm_active`-shaped flag, zero hits) and whether the existing `g_protected_pat_vars_armed`-style "armed once" pattern transfers (it doesn't: that flag is set once at startup for a program-static property; `trace_set_n` is genuinely dynamic and can't be captured that way).

Purpose: cache `(g_comm_dbg != 0 || trace_set_n != 0 || monitor_fd >= 0)` so `NV_SET_fn`'s hot-path guard (and any other call site with the identical three-way check, if one exists — not surveyed by this finding) becomes one load+compare instead of three.
