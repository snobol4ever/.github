# FINDING: `n11_array_key`'s Error 235 was never a NUL-truncation bug — `CONVERT(table,'ARRAY')` built a flat 2-D array the subscript chain can't walk, and native `ARRAY(r,c)` was never the same code path

**Seat:** seat07 · **Date:** 2026-08-24 · **Row:** `nul-in-counted-strings-class-defect` (task baton, hq_C mint s264) · **Fix:** SCRIP `src/runtime/core/core.c`, `_CONVERT_`'s `"ARRAY"`/`"TABLE"` branches.

## The claim

The task's one remaining rung, `n11_array_key` (`CONVERT(t,'ARRAY')[1,1]` on a table with a `CHAR(0)`-bearing key → oracle `3`, scrip `Error 235`), is **not a member of the NUL-in-counted-strings class**. It reproduces byte-for-byte with an ordinary NUL-free key (`w = 'ab'`) — the class hypothesis was wrong on this one rung, and the corrected diagnosis is a different, more general defect: `CONVERT(table,'ARRAY')`'s result was never 2-index-subscriptable at all.

## The chain, measured

| step | evidence |
|---|---|
| ablate: `w = 'ab'` (zero NUL bytes), `t[w]=1`, `CONVERT(t,'ARRAY')[1,1]` | scrip `Error 235`, oracle `2` — **identical failure with no NUL present** |
| ablate: `arr = CONVERT(t,'ARRAY'); OUTPUT=DATATYPE(arr)` | prints `ARRAY` correctly — the returned descriptor's tag is right; the fault is in how `[1,1]` walks it |
| gdb (`break core_runtime_error`, `bt`) | `c_rt_subscript_var_container_only` (pattern_match.c:1287) raises 235 because its dereferenced base is `DT_S, slen=2, s="ab"` — **the raw key string**, not an array or table |
| gdb, full chain (`break c_rt_subscript_var{,_container_only}`, print `base`/`idx` at each hit) | link 1: `c_rt_subscript_var(base=DT_A, idx=1)` → DT_A arm (pattern_match.c:1238-1244) computes `off = i - a->lo = 0` and hands back `NAMETRAP(&a->data[0])`. link 2: derefs that cell → it holds the **key descriptor** (`array_set2(a,1,1,kd)` put it at flat slot 0) → not DT_A/DT_T → 235 |
| root construction | `_CONVERT_`'s old `"ARRAY"` branch (core.c) built the result with `array_new2d(1,n,1,2)` — a **flat** `ndim=2` `ARBLK_t` — then filled it directly via `array_set2`, bypassing SNOBOL4-level assignment entirely |

## The fix

`sort_fn` (pattern_match.c:493, `SORT()`'s table→array conversion) builds a **different, nested** shape for the exact same "table of pairs → array" job: an outer `ndim=1` array of `n` elements, each element itself a `DT_A` **2-element** `ndim=1` array holding `[key, val]`. Verified this nested shape *is* correctly `[i,j]`-subscriptable (`SORT(t)[1,1]` / `[1,2]` / `[2,1]` / `[2,2]` all match oracle). Rewrote `_CONVERT_`'s `"ARRAY"` branch to build the same nested shape (unsorted — plain `TBL_FOREACH` order, matching the original's semantics) instead of the flat block. Also updated the reverse direction, `_CONVERT_`'s `"TABLE"` branch, to accept the new nested shape (falling back to the old flat `array_get2` reading for anything still built flat, e.g. a hand-built `ARRAY('n,2')`) — the flat shape was the only thing that branch accepted before, so leaving it as CONVERT-ARRAY-only would have broken `CONVERT(CONVERT(t,'ARRAY'),'TABLE')` round-trips.

**Verified:** all 14 `corpus/probe/nul/` rungs green (mode-3, pristine build). `n11_array_key` matches oracle in **both** m3 and m4 (m3≡m4 held). `.s` codegen confirmed byte-identical against 3 committed artifacts that call `CONVERT` (`crosscheck/rung9/910_convert.s`, `crosscheck/rung11/1113_table.s`, `demo/json.s`) — this is a pure runtime-C-function-body fix, nothing in the emission/lowering path changed, so no `.s` regen sweep was needed. `scripts/test_corpus_snobol4.sh`: pre-rebase, 360/361 both modes, unchanged from the pre-fix tree (the one red, `demo_treebank`, is [hq_C's already-filed `(A,B)` selection defect](FINDING-2026-08-23-hq_C-treebank-is-really-the-comma-selection-expression.md), confirmed identical via `git stash` on the unmodified tree — not something this fix touches or introduces). Re-verified after `git pull --rebase` onto SCRIP HEAD (which landed both the `(A,B)` cure and an unrelated `rt_subscript_var`/`rt_assign_var` DT_T fast-path addition, neither touching the DT_A path this fix changes): pristine rebuild, **362/362 both modes, zero failures** — `demo_treebank` now passes too.

## ⭐ The open question this does NOT close

Native `ARRAY(r,c)` / `ARRAY('lo:hi,lo:hi')` 2-D arrays — built via the SNOBOL4-level call and then written with ordinary `a[i,j] = v` assignment — use the **exact same flat `array_new2d`, `ndim=2` construction** `_CONVERT_` used to. I tested these directly and robustly against the oracle: 1×2, 2×2, 3×2, 2×3, reads and writes, all cells — **every one matches**. So flat `ndim=2` arrays are not broken in general; only the CONVERT-built one was. I traced the CONVERT failure with certainty (table above), but I was not able to pin down, with the budget I had, *why* the identical flat `ARBLK_t` shape survives `[i,j]` correctly when built via SNOBOL4-level assignment but not when built by C-level `array_new2d`+`array_set2` alone (my own gdb attempts at the assignment-driven path gave call sequences I could not fully reconcile with `pattern_match.c`'s textual chain — `sx_subscript_lv`/`bb_subscript.cpp` show a plain N-index chain with no `ndim`-aware special case, yet the runtime behavior is correct). Whoever next touches array subscripting should treat this as unresolved, not assumed-safe: it's plausible there's a real ASM/JIT fast path or optimizer step I didn't find that legitimately handles it, or it's plausible native construction is *also* fragile and my four shapes didn't hit the trigger. A probe ladder over VARIED native 2-D shapes/access orders (not just literal indices in the same statement as construction) would settle it cheaply.

## Transferable

- ⭐ **A brief's class hypothesis can be wrong on the very rung it names, and the DONE-WHEN is still the right target.** The task said "expect a third funnel" of NUL-truncation; the actual defect had zero NUL involvement. Ablating toward a NUL-free minimal witness (RULES.md's own ASM-DIFF-FIRST step 1) is what caught it — one line changed (`CHAR(0)` → nothing) and the identical error persisted.
- ⭐ **Two functions solving the same problem (`sort_fn` vs `_CONVERT_`'s old ARRAY branch) had picked different internal representations, and only one was subscript-chain-safe.** When a fix needs a "how do I build this shape correctly" answer, grep for a sibling that already does the same transformation before inventing a new representation — `sort_fn` was sitting 600 lines above the code that needed it.
