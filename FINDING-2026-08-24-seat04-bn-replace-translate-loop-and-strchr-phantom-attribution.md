## Part 1 — `bn_replace`'s own body, characterized on ITS OWN kernel for the first time

Every prior citation for `bn_replace`'s internal shape (the `by_name_dispatch.c:5085` inline comment, hq_P s262) was measured on **a different program** (`roman.sno`, short strings, ~3-4 chars/call) and only ever quoted as a per-call average (480 Ir/call) with the conclusion **"ninety per cent of REPLACE was getting ready to translate five characters."** Nobody had run `callgrind_annotate` with source-line detail against `by_name_dispatch.c` for `string_manip.sno` itself — a **44-character** string — until this pass. Full recipe: `callgrind_annotate --threshold=99.9 sm.callgrind src/runtime/by_name_dispatch.c`.

The line-level self-cost breakdown of `bn_replace`'s body (sums to exactly 18,986,411 Ir, byte-identical to the flat-profile top-level citation both prior FINDINGs used — verified by direct arithmetic, not eyeballed):

| bn_replace self-cost component | Ir | % of bn_replace's own cost | % of WHOLE kernel |
|---|---|---|---|
| **`for (i...) buf[i] = map[sv[i]];` — the translate loop itself** | **14,553,000** | **76.6%** | **28.43%** |
| everything else in the function body (entry/frame, arg-count check, 3× `BN_PTRLEN` unpack, `fl!=tl` check, map-cache lookup logic minus its callees, alloc call site, result store, return) | 4,433,411 | 23.4% | 8.66% |

Plus cost incurred **inside things `bn_replace` calls out to** (a separate, non-overlapping bucket — self-cost vs. inclusive-cost verified by exact arithmetic: 18,986,411 self + 2,317,505 in-callees = 21,303,916 inclusive, matching the caller-side citation of `bn_replace (20,999x)` at ~21.29M to within 0.05%, negligible rounding):

| callee (invoked from bn_replace) | Ir | disposition |
|---|---|---|
| `rt_ws_alloc_c` (heap allocation for the result buffer) | 1,265,569 | not yet routed to any row |
| map-cache memcmp validation (2×/call) | 839,960 | **already `perf-replace-map-cache-revalidation`** |

**The headline correction: the old "90% ceremony" framing does NOT generalize.** It was true for roman.sno's ~3-4 char strings, where a near-fixed per-call overhead swamps a near-zero translate cost. On a 44-character workload, the relationship inverts: **the genuine O(length) translate work is 76.6% of the function's own cost and single-handedly the largest line-level cost bucket in the ENTIRE kernel (28.43%, bigger than the whole outer by-name-dispatch chain's 22.84%+).** Per-character cost: 14,553,000 Ir / (44 chars × 20,999 calls) = **15.75 Ir/character** for `buf[i] = map[(unsigned char)sv[i]]` — a two-load-one-store-plus-loop-control byte copy, which is roughly what an unvectorized `-O0` scalar loop costs (no SIMD, no unrolling, full per-byte loop overhead; this is expected at `-O0`, not a bug in the loop's C source).

**Row-factory action: `bn_replace`'s translate loop — 28.43% of the whole kernel, is unrowed and is now this session's mint.** See `perf-replace-translate-loop-scalar-byte-copy` below. `rt_ws_alloc_c`'s 2.80%/1,265,569 Ir is flagged in that same row's brief as a secondary, smaller, not-yet-separately-scoped item (whether a REPLACE call could reuse/pool its output buffer) rather than minted on its own — it is entangled with the same call site and not worth fragmenting a 2.8% item into its own row.

## Part 2 — the two open questions from the prior FINDING, both now resolved

### `__strchr_avx2` (635,418 Ir, 1.24%) is a Valgrind/glibc-ifunc measurement ARTIFACT, not REPLACE cost, and not any SCRIP cost at all

The prior FINDING's hypothesis — *"REPLACE's cset-membership scan for its FROM argument may be routing through the pattern-compilation (RX-slab) machinery"* — is **refuted by direct source inspection**: `bn_replace` (`by_name_dispatch.c:5094-5112`) and everything it calls (`BN_PTRLEN`, `repl_pl_off`) contain **zero `strchr` calls** — the translate map is built with two plain `for` loops over `fv`/`tv`, never a scan. `string_manip.sno` itself (read in full) has exactly one statement per iteration doing string work — `REPLACE`/`SIZE`/`LT` — none of which are cset operations.

Cross-checked empirically, not just by source-reading: the raw `.callgrind` file's call-graph record for `__strchr_avx2` (`fn=(1576) 0x0000000004b70e70` → `cfn=(1578)` = `__strchr_avx2`, `calls=21258`) shows its caller as an **unsymbolized address inside the ambient `libc.so.6` object**, not a named function — the same "anonymous, dynamically-addressed" signature the prior FINDING flagged. **Definitive resolution via `gdb`, not further guessing:**
- `break __strchr_avx2; run` (breakpoint resolved cleanly to a real address, `0x7ffff3b8ad60`, once the binary was stopped at `main` so all shared libraries were loaded) — **the breakpoint NEVER FIRES.** The program runs to completion and exits normally. Repeated twice, both clean.
- i.e., **in a plain, uninstrumented native execution of the exact same binary and workload, `__strchr_avx2`'s actual code is entered zero times** — yet `valgrind --tool=callgrind` on that same binary attributes 21,258 calls and 635,418 Ir to it.
- Supporting structural evidence for *why*: the unsymbolized caller address (`0x…e70`) sits exactly `0x30` bytes from a **second, independently-verified-real** unsymbolized caller at `0x…ea0` that the SAME technique confirms is the map-cache's two `memcmp()` calls (line-annotated call count 41,998 = 2 × 20,999, matching the source exactly). Two adjacent small unsymbolized code blocks in the same object, one demonstrably a real PLT/ifunc trampoline (memcmp) and the other demonstrably dead code in native execution (strchr) — consistent with a known class of Valgrind/glibc multi-arch-ifunc cost-attribution confusion between neighboring AVX2 string-function resolver stubs, not a SCRIP or REPLACE behavior.
- **Consequence, stated carefully:** this is a measurement-tooling artifact, out of this project's control (glibc/Valgrind interaction, not SCRIP code) — but it means **the 51,185,959 Ir kernel total used for every ratio in this row's chain is inflated by ~635K Ir (≈1.24%) of phantom cost that never executes.** Whether SPITBOL's own callgrind-measured Ir total carries an analogous artifact is **not investigated here** — flagged as an explicit open question for the ratio-precision-sensitive row, not assumed either way.

### `__strcmp_avx2` (438,889 Ir, 0.86%) via `is_protected_pat_name` — fully resolved, real but irrelevant to REPLACE

`gdb` breakpoint on `is_protected_pat_name` (real function, real hit, unlike strchr) gives an exact backtrace: `main → gva_register (rt.c:487) → gva_collect_var → gva_name_eligible → is_protected_pat_name`. **This is a one-time startup pass** (called from `main`, before the ZBL loop, once per declared variable name — `string_manip.sno` has 16) — GVA (global-variable-analysis) eligibility registration, structurally identical in kind to the already-known fixed one-time linker cost (`_dl_relocate_object` et al.), and **entirely unrelated to `REPLACE`, `bn_replace`, or any per-iteration cost.** No row needed; this closes the open question with a real, if uninteresting, answer.
