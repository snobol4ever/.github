## The fix

Replaced the `for family in crosscheck/patterns crosscheck/strings ... crosscheck/rungW01; do` enumeration with filesystem discovery: `find "$SUITES/crosscheck" -maxdepth 1 -name "*.sno" | sort`, each paired with its sibling `.ref` (same pattern the script's own top "Crosscheck corpus" loop already used against `$CORPUS/crosscheck`). Nothing is named, so nothing can be forgotten when a new suite pair lands.

Discovery alone cannot see a family that went *missing* — fewer names discovered looks identical to fewer names that exist, the same blindness a glob shares with a hand list read backwards. So a floor stands guard: `SUITE_FAMILY_FLOOR="${SUITE_FAMILY_FLOOR:-29}"`, counted directly off the tree this commit. A discovered count under the floor adds the shortfall to the script's existing `MISSING`/`MISSING_LIST` accounting, which already SHRINK-REFUSES (`exit 2`, "GATE REFUSES ... the board is SMALLER than it looks") rather than reporting a smaller total as green — no new refusal path was needed, the shrink rides the one that already exists for a stale hardcoded demo path.

This is a **floor**, not a pinned total: RULES.md's own FACT RULE says a probe must never assert a denominator (a probe that pins an exact total goes red on every legitimate corpus growth, which is pure bookkeeping noise). This is exactly what the old list required of an *addition*, now required only of a *removal* — the failure mode that bit s277 (someone adds files, forgets to register them) is gone by construction; the rarer, more deliberate failure mode (someone removes files) still gets caught, loudly.
