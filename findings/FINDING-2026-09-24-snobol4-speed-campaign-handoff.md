## 3. Regressions found, OPEN — in the order to attack them (each with its callgrind number)

1. **The by-name call path scans two name tables with strcmp on EVERY call — treebank's 71%.** callgrind on treebank (×1024, m4): 09-03 `380cc4162` 2.48 G Ir; today 20.7 G. `__strcmp_avx2` 8.53 G (41%), `sn4_is_system_fn` 4.59 G (22%, `snobol4_system_fns.h`: a linear scan of 157 system-function names, inlined; 322 M strcmp calls from it — about 275 per by-name call, i.e. two full scans), `icn_builtin_is_known` 1.58 G (7.6%, `by_name_dispatch.c`: an Icon builtin-name table scanned from a SNOBOL4 program, 1,173,519 calls from `rt_call_arr_impl`, 66 strcmps each). The sites: `rt_call_arr_impl` line ~5910 `if (sn4 && !sn4_is_system_fn(fn) && !rt_proc_is_registered(fn) && FNCEX_fn(fn) && icn_builtin_is_known(fn) && ...` and ~5915 `if (strict && !rt_proc_name_exists(fn) && !icn_builtin_is_known(fn) && icn_builtin_arity(fn) == ...)`, and `sn4_call_in_scope` (~5849) which tests `sn4_is_system_fn` BEFORE `rt_proc_is_registered`. Since: `sn4_is_system_fn` arrived 2026-08-23 (`24cb07175`, ERROR 248 on redefining a system function); the Icon-table test on the SNOBOL4 path 2026-09-12 (`597c9be53`, "delete every am-I-running-Icon test"). THE CURE, in this order: (a) test `rt_proc_is_registered(fn)` FIRST (a hash lookup) and short-circuit every scan for a registered user function; (b) make `sn4_is_system_fn` and `icn_builtin_is_known` O(1) (a hashed set built once, or the baked builtin id `bid_bake_of` the emitter already computes — a call site with a baked bid is a builtin, one without is not); (c) resolve statically: a call to a name DEFINE'd in the program with a resolved proc record emits a direct open/land, no name at run time. Expected: treebank from 20.7 G toward the old 2.5 G; porter, calculator, json and every call-heavy kernel move with it.
2. **The collector's 09-19/21 call contract** (`rt_call_open_by_name` `80e3a942e`, `rt_apply_open` `ed9f7a76e`, `rt_proc_call_prologue`, `rt_proc_save_count`, `rt_proc_epilogue_named`, `rt_name_save_push`/`rt_name_restore`): a runtime-made call opens in C and lands in emitted code — about 1,100 Ir per call against 695 on 09-03 (indirect_dispatch after item 1's trace fix: 2.21 G vs 1.39 G). ARCH-RT-CALL-PROTOCOL.md § 12 has the per-function split. Cure: a direct open/land fast path for a known DEFINE'd callee with a resolved proc record and the locals' save/restore as a fixed-offset block.
3. **The GC poll is mis-sited and mis-shaped**: emitted after EVERY runtime-call return, including calls that cannot allocate (`rt_coerce_num2_d`, `rt_cmp_d`), and it is a call inside a 7-instruction RTCC spill/reload where the design wants an inline `cmp [g_gc_pending],0 / jne slow`. ~8% of arith_loop's Ir this morning; classify runtime entry points allocating/non-allocating at the emitter. NOT a diagnostic (Lon asked): it is the collector's trigger; it does not go under a switch. The cfo reviews (collector lane).
4. **The statement marks' three GOT indirections per statement in mode 4** (`bb_stmt_mark.cpp`: g_stno and g_line stores through `[rip@got]`): +17% cycles on arith_loop against 09-03 (283 M vs 266 M Ir, 74 M vs 63 M cycles). SPITBOL pays two direct moves. A packed stno:line word in one direct store, or rip-relative stores in mode 3.
5. **String, table and array classes not yet profiled**: string_manip 0.09x vs 0.66x, table_access 0.20x vs 1.29x, roman 0.24x vs 0.78x, array_sum 0.14x vs 0.27x, table_variety, mixed_workload, name_indirection, eval_fixed. Same one-kernel method (§ 5). Suspects from the demo profiles: the by-name path (item 1) inside `*function()` pattern calls, `dat_field_get`, `gc_blk_of`/`gc_hins` on table stores (table_access moved 2.8x with a 64 MB arena: collections are part of it).
