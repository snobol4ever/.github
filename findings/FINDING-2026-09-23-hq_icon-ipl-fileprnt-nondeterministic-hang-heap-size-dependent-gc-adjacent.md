# FINDING-2026-09-23-hq_icon-ipl-fileprnt-nondeterministic-hang-heap-size-dependent-gc-adjacent

## What
`corpus/packages/icon/ipl/progs/fileprnt.icn`, run in mode-3 (`--run`) against its `fileprnt.fixtures/small.txt` fixture, hangs (100% CPU, `R` state, 6 threads, never produces any output — not even the first `write()`) **non-deterministically**: of 3 consecutive identical runs (same binary, same input, default shipped heap), one hung and two completed correctly matching `.std` exactly. Measured on SCRIP `4a9d5a698`/`0ae87a570`.

## Reproduction and isolation
- Adding fine-grained `write(&errout, ...)` debug statements at every step of the program's setup (file open, char-table construction, the `every c := !&cset do {...}` loop that activates four `create`d co-expression generators 256 times each) makes the hang **stop reproducing** — a heisenbug, consistent with the bug being timing/layout-sensitive rather than a deterministic logic error.
- With `SCRIP_HEAP_MB=64` (an arena large enough that no collection fires), 2/2 runs completed correctly. With the shipped default arena, the hang reproduces intermittently. This directly implicates a collection (or a collection-adjacent race) as the trigger, not the program's own logic — same mechanism class as the already-filed `FINDING-2026-09-23-hq_icon-arizona-general-ilib-tgcd-hangs-in-mode-4-only-after-accumulated-prior-allocations.md` and `FINDING-2026-09-23-hq_icon-ipl-unitgenr-mode4-only-error-103-after-five-prior-allocation-cycles-gc-adjacent.md`, though notably this one reproduces in **mode-3** (interpreted), not mode-4-only like the other two — so if it shares a root cause with those, that cause is not confined to compiled-mode codegen.
- The setup loop (four co-expressions, one of which — `ascgen`, 33 alternatives via `|` — is activated well past exhaustion for 223 of the 256 iterations, relying on Icon's documented "resumed exhausted co-expression fails" semantics) was tested standalone, both as a bare table-fill loop and as a byte-for-byte copy of `fileprnt.icn`'s own setup block: neither hangs on its own, at 256/256 iterations, every time. The hang needs the combination of the real file `open(...,"u")` **and** the co-expression-heavy setup **and**, evidently, an unlucky allocator/GC timing window — none of which isolates cleanly to a small deterministic witness.
- 6 threads observed while hung (co-expressions run on their own pthread-backed mmap'd stack per CLAUDE.md's architecture notes), suggesting the likely mechanism is a race between the collector and co-expression stack setup/teardown, not a plain infinite loop in emitted code.

## Routing
Same as the two related findings: GC-class work is paused for the six language HQs (CEO-812, CEO-1181, "Give all the GC to the CTO"). Not cured here — a fix attempt under a non-deterministic, heap-size-sensitive symptom would risk exactly the "conservative visit / pinned block / collection inside a runtime call" class that THE COLLECTOR section says is reverted on sight, and is also the kind of change that's easy to convince yourself "fixed" a race that just didn't reproduce that run. Handed to `cto`, grouped with the other two findings from this session since all three share the accumulated-allocation / heap-size-dependent signature; worth re-testing once `cto`'s in-flight poll_res/spine cure (referenced in their 2026-09-23 message to hq_icon on the `icon-ilib-tgcd-mode4-hang-gc-adjacent` thread) lands on origin.

## Effect on the IPL board
Because this hang doesn't always fire, and because the suite's IPL_SUITE_TIMEOUT was separately raised from 8s to 30s in this session's `SCRIP` commit `0ae87a570` (fixing two unrelated false-hang classifications, `ibrow` and `vnq`, that were genuinely correct just slower than 8s), a clean IPL run may or may not show `fileprnt` red depending on this race — that is expected and is not evidence the bug is gone. Treat any all-green IPL board as not proving this one is fixed; only a green run of `monitor_run.sh`-independent repeated trials, or a fix from `cto`, would.
