# FINDING 2026-09-13 (cto, CEO-617/650 lane: THE PROLOG ISO LADDER, rung 8) — the Prolog reader wrapped an unbounded integer literal to −1 while a bignum core sat unused three directories away

**Claim.** After SCRIP `9f6bb922f`, a Prolog integer literal wider than 64 bits is read as an unbounded integer. It writes back as its own digits, answers `integer/1`, unifies, sorts in the standard order, compares arithmetically, and carries through `+ - * // mod`, unary minus, `abs`, `sign`, `min`, `max`, `**`, the bitwise `and`/`or`/`xor` and `gcd`. `current_prolog_flag(bounded, B)` answers `false`, as ISO 7.11.1.1 requires of an implementation with unbounded integers. Logtalk `unbounded` 29 → **70 of 111 in both modes**, the largest single class in the cto's lane.

**How it was found.** CTO-38's NEXT left the control lane with seven small reds and named the unbounded-integer class as mine (MODE line 2). A per-group read put the weight beyond argument: seven control reds against **78 fails in one family**. The first probe was three lines — `X = 123456789012345678901234567890` read back as `-1`, `+1` gave `0`, `*3` gave `-3` — so the loss was at the READER, before any arithmetic ran, and every one of the 111 cases that starts from a literal was decided before it began.

**⭐ The part worth reading: the feature was already built.** `src/runtime/bignum.c` has a complete hand-rolled limb bignum — `DT_BIG` plus `rt_big_from_str`, `add`, `sub`, `mul`, `div`, `mod`, `pow`, `neg`, `and`, `or`, `xor`, `cmp`, `str` — and `arithmetic.c` already promotes an overflowing *string* operand into it through `big_str_operand`. That is how Icon and SNOBOL4 get bignums. **Prolog simply never reached it.** The ceo's Icon lane carries a `b_bignum` row (rank 0, hq_B, quiet under SEPTET) for the same capability; had I started from the test expectations rather than from the tree I would have written a second bignum beside the first, which is precisely what Lon ruled out on 2026-09-02 (*"No need to create a new BB that does exactly what one already does"*). **The measurement that mattered took four greps and came before any design.**

**Where it was, and it was six layers, not one.** (1) `prolog_lex.c` did `t.ival = (long)(unsigned long long)strtoull(buf, NULL, 10)` — `strtoull` sets `ERANGE`, returns `ULLONG_MAX`, and the cast to `long` is `-1`. The digits were still in the token's `text`; only the conversion threw them away. (2) `prolog_parse.c` stored that `-1` in a `TT_ILIT`. (3) `lower_prolog.c` lowered `TT_ILIT` to `IR_LIT_INTEGER`, whose payload is an `int64_t` — no IR kind can hold a bignum. (4) The Prolog term layer (`rt_pl_type_test_cell`, `pl_is_int`) tested `d->v == DT_I` exactly, so a big was not an integer. (5) The four term writers printed `_G%d` for any tag they did not know, so a big inside a compound printed as an unbound variable — while `arg/1` extracted it correctly, which is how the compound was proven innocent. (6) `dop_ax` and `pl_ax_eval` rejected any operand that was not `DT_I` or `DT_R`, so `BIG + 1` raised `type_error(evaluable, ?/0)`; and `pl_num_cmp` read `(double)a.i` on a big, which is the *pointer bits* as a double.

**The cure.** **No new IR kind and no new global.** Terms in this lowerer are already built by runtime calls in term position — `mkc_node` emits `IR_CALL "$mkc"` with an `IR_LIT_STRING` operand — so a big literal lowers the same way: the lexer flags `ERANGE` on a decimal literal (the radix form is deliberately untouched and named below), the parser emits `$pl_big(<digits>)`, and `term_e` and `lower_arith_val` emit `IR_CALL "$pl_big"` over the digit string to a one-line det leaf calling `rt_big_from_str`. The other five layers each learned `DT_BIG`: the type tests, the standard-order class and comparison, the writer, `pl_ax_eval`, and `dop_ax` (through two helpers — exact integer ops via the `rt_big_*` core, and every double-based op given a correct `ad`/`bd` via `strtod(rt_big_str(...))` instead of the garbage a reinterpreted pointer produced).

**Proof.** `scripts/test_gate_pl_iso_rung8_an_unbounded_integer_literal_reads_writes_and_computes.sh` (wired into `make test` and `gate_wiring.tsv`): a 13-line witness in both modes, every expectation agreed by swipl 9 — gprolog 1.4.5 is a *bounded* implementation and is explicitly not an oracle for this rung — plus the Logtalk `unbounded` floor, ratcheted to the measured 70.
