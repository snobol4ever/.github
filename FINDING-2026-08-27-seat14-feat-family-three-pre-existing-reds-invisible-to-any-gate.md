# FINDING: `tests/snobol4/feat/` carries 3 broken programs invisible to every mandatory gate

**Who/when:** seat14, 2026-08-27, discovered while executing task `tests-consolidate-snobol4-loose`
(convert loose `.sno` test families into corpus-suites-consolidation suite format).
**Owner:** hq_C (correctness) — these are wrong-answer/crash defects, not a suite-format question.

## Mechanism — why nothing caught this before

`corpus/tests/snobol4/feat/` (21 `.sno`/`.ref` pairs, feature-acceptance tests) is graded ONLY by
`scorecard_snobol4.sh`'s `MISC_DIRS` bucket (weight 3, blended with `parser`/`smoke`/`jvm_j3`/`linker`/
`packages/snobol4/{dotnet,aisnobol}`). `scorecard_snobol4.sh` is **not** part of `make test` or any
mandatory gate — it is a manually-invoked, long-running scorecard. `test_corpus_snobol4.sh` (the actual
`make test` gate) has never covered `feat/` at all. So these three have been red for an unknown period
with zero gate ever reporting it.

They surfaced now because `corpus_suite_harness.py convert`'s byte-equal-or-no-delete law requires the
**original** file to already be green before it will convert it (`convert_one`: "original file itself is
not green" → refuse, nothing written). The harness is doing exactly its job; it is not the source of
these bugs, and none of this task's changes (or any recent commit this seat is aware of) touch I/O
channels, `CODE()`, or `EVAL`.

## The three programs, reproduced individually on a fresh pristine build (SCRIP `264f8226`, RT_OPT=-O0)

**`f13_eval_code.sno`** — `EVAL('2 + 3')` then `CODE("CPASS OUTPUT = 'PASS' :(END)")` + `:< C >` (dynamic
compile-and-jump). **Prints the CORRECT output (`PASS`) and then SIGSEGVs on the way out** (rc=139,
"Segmentation fault", confirmed via direct `--run` outside the harness's capture too). This is a
crash-after-correct-output shape — looks like teardown/cleanup after a dynamically-`CODE()`-compiled
region, not a computation defect. Not investigated further (out of this task's scope — ASM-DIFF-FIRST
methodology per RULES.md would be the right next step: mint the smallest CODE()+dynamic-goto repro, diff
`--compile` output against a passing sibling). **Not entirely novel:** `test_gate_fc_no_residual_rbp.sh`
already lists `f13_eval_code.sno` in a `KNOWN_NOCODE` set with the comment `"direct-goto \":< C >\" parse
defect"` — a related, already-tracked limitation of the same construct, though that gate frames it as a
parse-time issue rather than the runtime SIGSEGV-after-correct-output seen here; worth reconciling whether
these are one defect or two when someone picks this up. **Incidental litter noted, not swept:** the `feat/`
directory also carries a stray `f13_eval_code.c` — committed content (`91e4465cc`), header `generated by
scrip-cc` (a retired frontend), but its actual body is shift/reduce/stack/counter-table code with **no
relation to `f13_eval_code.sno`'s content** — looks misplaced/mislabeled, same dead-backend-litter class
`corpus-suites-consolidation`'s ledger already documented elsewhere (`capture/*.asm.ref`, `rungW01`'s stray
`.c`). Flagged, not deleted — out of this task's scope to adjudicate.

**`f10_io_basic.sno`** — `OUTPUT('FOUT', 1, path)` write, `ENDFILE(1)`, `INPUT('FIN', 2, path)` read back,
`IDENT(LINE, 'test_line')`. Prints `FAIL` (expected `PASS`) — the named-I/O-channel round-trip does not
read back what was written. rc=0, no crash, just wrong answer.

**`f11_io_file.sno`** — same named-I/O-channel mechanism, multi-line write (`WR='line1'`/`WR='line2'`) +
`DETACH(RD)`. Also prints `FAIL`. Likely the same root cause as f10 (named channel read-back), not
independently diagnosed.

## What this task did about it

Did **not** attempt a fix (named-I/O-channel semantics and `CODE()`/dynamic-jump teardown are both
real runtime work, not a narrow one-line precedent like the `control_new` goto-merge or lexer fixes seen
elsewhere in the sibling `corpus-suites-consolidation` ledger). Converted the other 16 of `feat/`'s 19
pairable programs via `corpus_suite_harness.py convert --skip f10_io_basic,f11_io_file,f13_eval_code`
(loud, named, reasoned exclusion — mirrors the stdin-bearing-tests and Snocone-removed-syntax
precedents). The 3 red files, plus 2 more with no `.ref` at all (`f15_trace_dump.sno`,
`f18_error_handling.sno`, pre-existing gap, not investigated), stay as loose files in `feat/` — 5 loose
files remain there, not 0, and that is by design, not an oversight.
