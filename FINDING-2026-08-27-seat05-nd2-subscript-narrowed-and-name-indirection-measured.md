## Part A — defect (2): why the reverted `a[i,j]` fast path read zeroed operands, narrowed without a rebuild

The prior session's revert note blamed `IR_SUBSCRIPT`-specific hardcoding in the ζ-storage pipeline (`zd_nops`, `zd_wl_kind` in `src/emitter/emit.cpp`) and stopped without finding the actual cause. Re-reading the prior session's own saved diff (`attempted-fix-nd2.diff`) and its emitted `.s` output (`mini2.s`, both preserved this session at `/tmp/claude-1000/-home-claude05/e8373a3f-abef-45a4-8abc-b7777f0975f0/scratchpad/nd2-investigation/`) against current source ruled out four specific hypotheses with direct evidence:

1. **The `zd_nops`/`zd_wl_kind` patches are a red herring.** They feed `g_emit.op_zread[]`/`op_zread_xf[]`, consumed only by `ZOPQ`/`ZRES`-style addressing under `_.op_zres` (cell-storage mode). The new `bb_subscript2()` template has **no `op_zres` branch at all** — it only reads `_.op_a_slot`/`_.op_sa`/`_.op_sb` via `FRQ()`. Fixing a mechanism the template never consults cannot fix the symptom.
2. **"Wrong driver function" is false.** `emit_drive()` (`emit.cpp:1438`) is the single per-node driver for the *entire* graph, called once per node from the main emission loop (`emit.cpp:3098`). Its 3-operand `IR_SUBSCRIPT` branch (`emit.cpp:1780-1798` in current, reverted source) **already existed before this row**, as the mechanism for `bb_section()` (3-operand slice syntax), and already computed `sa/sb/sc` via `drive_value_slot()` on all 3 operands generically.
3. **Template field-naming is consistent.** `emit_drive` sets `op_a_slot=slot(base)`, `op_sa=slot(idx1)`, `op_sb=slot(idx2)`; `bb_subscript2()` reads exactly those three, in that order, into rdi/rsi, rdx/rcx, r8/r9 — matching `c_rt_subscript_var2(base,idx1,idx2)`'s SysV ABI.
4. **`zls_grant_locals`'s call-kind "argv block" reservation does not apply to `IR_SUBSCRIPT`.** `ir_is_call_kind()` (`src/ir/IR.h:169`) is a fixed opcode allowlist that does not include `IR_SUBSCRIPT`; it falls to `zls_grant_locals`'s `default: return 0`, getting exactly one slot like any plain value-producer, independent of `n_operands`.

**What was proven instead**, via direct inspection of the prior session's saved `.s` (no rebuild needed — RULES.md's ASM-DIFF-FIRST): for `A[1,1]=11`, the emitted subscript box read its three operands from `[rsp+96]`/`[rsp+112]`/`[rsp+128]`. Manually reconstructing the correct addresses from the *same* `.s` file (each producer box — the `A` var-ref, and the two integer-literal index boxes — does its own unconditional `sub rsp,16`, a FORTH-style per-box push confirmed against `ARCH-ICON.md`'s register contract) shows those three offsets are wrong. The naive "reset to 0 at the start of this statement" computation (which would predict 48/32/16) is *itself* invalid, though: `zls_build()` (`src/ir/zeta_storage.c:336`) assigns slot offsets via a single **flat, monotonically-increasing counter across the whole graph** — confirmed by the emitted code's own explicit `add rsp,32` teardown at the end of statement 1, which resets the *dynamic* stack but not `zls_build`'s *static* counter (also confirmed: `IR_CALL`-kind nodes such as `ARRAY(...)` consume `1 + n_operands` slots via `zls_grant_locals`'s call-kind branch, not 1, so a hand count has to track every such node precisely). Two hand-recomputation attempts, accounting for this, landed within one 16-byte slot of 96/112/128 but not exactly on them — meaning one more contributing detail remains unaccounted for by hand arithmetic alone.

**Recommended next step** (should take well under the multi-hour dig the first attempt spent): add one `fprintf` inside `zls_grant()` (`zeta_storage.c:209`, right after `zls_entry(nd,scope_id,off)`) printing the node's op name and `off`, rebuild once (genuinely `make pristine` — see the "fresh vs. incremental build" caution below), run `nd2-investigation/mini2.sno` with the diff reapplied (check `git apply --check` first; the `src/templates/*.cpp` → `src/templates/{bb,x86,xa}/` reorg landed since the diff was made), and diff the fprintf'd `off` for the three operand nodes against what `emit_drive`'s `sa/sb/sc` read back in the same run. Match ⇒ bug is on the dynamic (runtime `sub rsp`) side; mismatch ⇒ bug is in registration/reachability ordering. **Do not chase a "dedicated new opcode" design instead** (the prior session's other proposed option) — the bug is confirmed to live in opcode-*generic* slot-counting machinery, so a new opcode would hit the identical issue.

**Secondary, confirmed-real, smaller gap:** `bb_subscript2()` is missing the `_.op_zres`/`ZOPQ`-branch its sibling `bb_subscript()` has, so the new box is incomplete under non-default `ZC_STORAGE` selectors even after the primary bug is fixed.

**Caution for whoever resumes this:** this same investigation independently re-confirmed (via a *different* mechanism than session 1's own re-discovery) that a `handoff_status.sh`-triggered `make pristine` racing a live build is real and separate from this row (see the `stop-hook-background-build-collision` project memory, updated 2026-08-27 from an unrelated hq_C answer) — always verify a build is genuinely fresh and uncontended before trusting a correctness result from it, exactly as session 1's own Error-235 discovery did.

## Part B — defect (3): `.NAME` (`DT_N`) string-representation cost, measured

The row's brief flagged `DT_N`'s `slen==0` string representation (`descr.h`'s `DESCR_t`, `NAMEVAL` macro at `src/runtime/core/core.h:25`) as unmeasured, and required measuring before proposing any change (a semantics question, not a pure perf one, per the brief).

**What triggers it:** `--dump-ir-verbose` on a two-line probe (`x=5`; `nm='x'`; `$nm=$nm+1`) shows `$nm` (indirect reference through a runtime string) lowers to `IR_CALL "SNO$NAME"` — i.e. **every** `$expr` indirection, not only the explicit `NAME()` builtin, routes through the same builtin-call mechanism that constructs a `DT_N`/`slen==0` value and then resolves it.

**Method:** two SNOBOL4 probes, `name_indirect.sno` (loop of `$nm = $nm + 1`, `nm` holding the string `'x'`) and `name_direct.sno` (identical loop shape, `x = x + 1` directly — the brief's "empty-loop/baseline-subtracted, one dedicated loop per shape" discipline, here using the direct-access kernel as the control since it is the same arithmetic/loop shape with indirection as the sole variable). Both preserved at `.../nd2-investigation/../name-cost/` (session scratchpad). Profiled with the project's own discovery-measurement tool, `scripts/profile_box_histogram.sh` (`SIMS=0`, callgrind `Ir` — deterministic instruction counts, not wall-clock, so the alignment-noise caution in the row's "MEASUREMENT DISCIPLINE FROM s249" does not apply to this pass; that discipline governs wall-clock `TIME()` claims, which this FINDING does not make) — 5000-iteration short-budget copies, matching the brief's own precedent methodology for defect (1)'s original discovery.

**Result:** both profiles carry an identical ~2.14M-Ir fixed one-time cost (`_dl_relocate_object`/`do_lookup_x`/`_dl_lookup_symbol_x` — dynamic-linker/PLT-resolution startup work, confirmed identical in absolute `Ir` count between the two runs, hence unrelated to the loop body and excluded from the ratio below). Back-computing each run's total `Ir` from that shared fixed cost's reported percentage: indirect-kernel total ≈ 14.89M Ir, direct-kernel total ≈ 5.02M Ir, for the same 5000 iterations — **≈2.97x total Ir, ≈4.43x Ir on the loop body alone** (fixed startup cost subtracted from both sides first). Axis: `indirect / direct`, both same instrument (callgrind Ir, `SIMS=0`), same `RT_OPT=-O0`, same iteration count, same mode (m3 default `--run`); this is an internal A/B between two of our own kernels, not a SPITBOL comparison, so RULES.md's `reference/ours`-on-the-faster-axis convention does not apply here — reported directly as "indirect costs Nx direct's instructions."

**Where the extra instructions go** (indirect-kernel-only or indirect-delta functions, top contributors): `rt:try_call_builtin_by_name_bl` (2.06M Ir) is the single largest named contributor — **larger than the string/hash machinery the brief specifically asked about.** `$` indirection's *own* implementation is dispatched through a generic "call a builtin by its string name" path (`try_call_builtin_by_name_bl` → `rt_call_arr_impl`/`rt_call_arr_bl`, another ≈1.57M Ir, the argument-marshaling layer for that same by-name call) before the `.NAME` resolution work even begins. *Then* the mechanism the brief named: `rt_sno_indirect_name` (630K) + `bn_sno_name` (500K) + `NV_GET_fn`/`NV_SET_fn` (385K + 671K) + `_var_hash`/`_var_bucket_find` (292K + 290K) + `VARVAL_d_fn` (370K) ≈ 3.1M Ir — real and substantial (≈36% of the ≈8.6M Ir attributable to indirection), but smaller than the by-name call-dispatch layer sitting in front of it (≈3.6M Ir, ≈42%). A single-run wall-clock sanity check (0.058s indirect vs. 0.013s direct for 200K iterations, unpadded/no noise-floor control, not to be quoted as a precise figure) is directionally consistent.

That row's sibling `perf-nv-set-capture-pump` is explicitly framed as a **caller-side cure: "stop calling it by name."** This FINDING's single largest contributor, `try_call_builtin_by_name_bl` (`$`-indirection's own dispatch to its `SNO$NAME` implementation, ≈2.06M Ir, larger than the name-hash layer itself), is structurally the identical disease — a runtime mechanism reached through a generic *string-keyed* call-dispatch rather than a direct/cached reference — just a different call site.
