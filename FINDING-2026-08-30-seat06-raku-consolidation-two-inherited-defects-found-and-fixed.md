## DEFECT 1 — THE COLLAPSE GUARD COMPARES THE WRONG UNIT (reported to hq_P, not fixed here — theirs)

`util_build_master_suite.py`'s new guard (`len(pairs) * 4 < len(base_entries)` → refuse as a "collapse") compares a **pair count** to an **entry count** — different units. It's correct for SNOBOL4's mostly-one-entry-per-pair shape (the incident it was built to prevent: a rebuild collapsing 1576 entries to 2). It is a **false positive** for any language using the banner-block format, where one pair legitimately holds dozens of entries: raku's 15 pairs → 97 entries (15×4=60 < 97) refused as a "collapse" when it was a perfect, verified 1:1 correspondence. Worse: it also refuses the **intended end state** — once every pair is legitimately absorbed and deleted, the next run sees 0 pairs against N entries and refuses again, meaning a fully-consolidated language can never be idly re-verified by the normal tool path again.

hq_P independently reproduced this, swept all six non-SNOBOL4 languages, and confirmed: **raku and snocone hit this wall; icon, pascal, rebus currently don't (enough pairs relative to entries); prolog doesn't either but for an unrelated reason (zero pairs takes an earlier, unaffected exit path).** Fix routed to hq_B (the guard's owner): compare `len(all_entries)` (already computed pre-write) to `len(base_entries)`, not pair count to entry count.

**Workaround used here, not a fix:** independent standalone verification (re-reading each source pair fresh via `corpus_suite_harness.py`'s own `read_block_suite`, comparing every field the real tool's verification loop compares) before a plain `git rm`. Per ceo's same-night Law 2 amendment (scratch/independent verification before any deletion on a cut-over-shaped tree, never delete-in-place through an unverified path), this is the sanctioned shape, not an exception to it.

## DEFECT 2 — 14 KNOWN-COMPILER-GAP ENTRIES WERE MIS-DECLARED `xfail=0` (found and fixed in this row)

The 14 individual fixture files (`class_and_main`, `class_basic`, `class_fields`, `class_method_param`, `class_multi_method`, `class_twigil`, `elsif_basic`, `for_range_ex`, `gather_in_assign`, `gather_multi_take`, `gather_take_lit`, `gather_take_var`, `raku_new`, `take_in_loop`) test Raku OOP (`class`) and `gather`/`take` generator syntax the compiler does not fully support yet — this was already documented (`FINDING-2026-08-27-seat05-tests-consolidate-raku-scope-complete-verified-not-assumed.md`, and the older `tests-consolidate-raku` task's own ledger) as a **known, bounded, coherent cluster of compiler gaps**, not drift.

They were absorbed into the master with `xfail=0` (should-pass) instead of `xfail=1` (known-red). Root cause: `util_build_master_suite.py`'s bannerless "plain program" absorption path (used for any non-SNOBOL4 pair whose source file carries no banner — exactly this shape) **never computes or sets xfail at all**; its own comment admits this ("auto-XFAIL-by-source-verdict is NOT applied on this path yet ... a named follow-up rather than a silent difference"). This is not something my session introduced — it's inherited from whoever originally absorbed these 14 (hq_B's master build) via a documented, known-incomplete code path.

**Measured, not assumed:** graded the full master with every entry's own CSV-declared mode (ast for parser families, m3/m4 for the rest) before touching anything — `ast: PASS=83 FAIL=14`, and the 14 failing names matched the 14 known-gap stems exactly (confirmed by cross-referencing origins, not by name pattern). Fixed by setting `xfail=1` on those 14 rows in `ALL.csv` **and** adding the `XFAIL` marker to their banner lines in both `ALL.raku` and `ALL.ref` (the harness reads xfail status from the banner text, not the CSV — editing only the CSV would have desynced the two). Re-graded clean: `ast: PASS=83 FAIL=0 XFAIL=14 XPASS=0`.
