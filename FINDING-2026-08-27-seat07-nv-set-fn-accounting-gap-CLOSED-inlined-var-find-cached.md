## METHOD: a purpose-built raw `cg.out` parser, not `callgrind_annotate`'s rendered view

`callgrind_annotate`'s per-file source view prints `core.c` top-to-bottom exactly once, inserting whatever cost lands on each line number — it has no inline-frame awareness and gives no visual signal when a displayed number's true call-graph context (`fn=`) differs from the function whose text physically surrounds it on screen. That is a display limitation, not a data problem: the raw `cg.out` file is unambiguous. Per the Callgrind Format Spec (grammar confirmed against the installed doc, not recalled from memory):
- `positions: line` ⇒ every cost line is exactly `<subpos> <cost>` (one event, Ir).
- A `SubPosition` is an absolute number, `+N`/`-N` (relative to the **last cost line's** subposition), or `*` (same as last) — **one continuous running counter**, shared by plain self-cost lines and by the mandatory cost line following a `calls=` record.
- `calls=<count> <target-position>` — "After a calls= line there MUST be a cost line" (exactly one) — and that line's cost is the **inclusive cost of the callee**, not the caller's self cost. A script must exclude it from self-cost sums or it double-counts (this bit me on the first parser draft: raw total came out to 62,265,696 until the call-cost line was correctly excluded from the `fn=NV_SET_fn` self-cost sum, after which it matched 50,492,413 exactly).
- `fi=`/`fe=` switch the *current* file mid-function (inlined code from another file) without changing `fn=`.

Script: `parse_nvset.py` (kept in scratch, not committed — reproducible from this document; ~120 lines). It tracks the compressed `fl=`/`fn=`/`fi=`/`fe=` id tables, walks every cost line, and for every line whose **current `fn=` context** resolves to `NV_SET_fn` (any of the 5 caller-split names), records `(resolved file, resolved absolute line, cost)`. **Total summed: 50,492,413 — exact match to the independently-known flat total.** That match is the parser's own proof of correctness; everything below follows from the same run.

### Mechanism 1 (the real gap, 14,321,183 Ir): `_var_find_cached` is `always_inline`, and callgrind's line-based costing has no inline-frame awareness

`core.c:2312`: `static inline __attribute__((always_inline)) NV_t *_var_find_cached(const char *name) { ... }` (body: lines 2313–2320) — the SAME s258 memo-cache helper the row's own GOAL text credits with curing the write-side hash+strcmp cost, shared with the read side (`NV_GET_fn`). Per the standing s262 doctrine already written at its sibling site (the `rt_protected.h` comment on `is_protected_pat_lead`, one guard below in the same file): *"under the s262 NO -O2 fact rule, -O0 honours neither `inline` nor its own cost model: a plain `static inline` helper is a REAL CALL with a real prologue... always_inline is honoured at -O0 and is the only way to get inlining back."* GCC does inline it — the instructions genuinely execute as part of `NV_SET_fn`'s machine code, with no call/return, which is exactly why the flat table correctly buckets 100% of this cost under the `fn=NV_SET_fn` call-graph context. But the DWARF line-table entries for those inlined instructions still carry `_var_find_cached`'s **own** source lines (2313–2320), not the call site inside `NV_SET_fn` — so `callgrind_annotate`'s per-line view displays the cost next to `_var_find_cached`'s definition, ~40 lines before `NV_SET_fn`'s own `{`.

This is the *identical* effect already known and separately bucketed for `is_protected_pat_lead` — the difference is purely cosmetic: `is_protected_pat_lead` lives in a *different file* (`rt_protected.h`), so `callgrind_annotate --auto` gives it an obviously-separate "Auto-annotated source" section a reader can't miss. `_var_find_cached` lives in the *same file* (`core.c`), so its cost silently blends into the single continuous top-to-bottom core.c listing at a line number a human scanning "`NV_SET_fn`'s body" has no reason to also read. Same mechanism, one visible instance and one invisible instance — that asymmetry, not a tooling defect, is why this took three sessions.
