## 2. CWD-fidelity bug found and fixed (harness, not compiler)

The harness ran every graded program with `SCRIP/` (or wherever the harness itself was invoked from) as CWD, never the suite directory. Upstream's `Test-icon` is always run **from within** the test directory, so any program using a relative path resolves against `general/`. Two real Arizona programs depend on this: `fncs1.icn` (`open("gc1.icn")`, a relative read of a sibling test file) and `io.icn` (opens/writes `./tmp1`, `./tmp2`, `foo.baz`). Confirmed directly: `fncs1.icn` run with the correct CWD flips its `open("gc1.icn")` line from `none` to a real file object — this was a **harness fidelity bug making SCRIP look wrong for something it wasn't responsible for**, not a compiler defect.

**Fixed**: both the m3 (`--run`) and m4 (compiled-binary) execution steps now run as `(cd "$SUITE" && timeout ...)`. `fncs1.icn` still does not reach a full byte-exact PASS (it has at least one more independent issue, unexamined beyond the CWD confound — worth a fresh look now that this confound is removed). `io.icn` is unaffected by this fix — its own failure is unrelated to CWD (see §4.4).

**Side effect found and fixed in the same commit**: CWD fidelity means those relative writes now really happen, littering real files (`foo.baz`, `tmp3`) into the tracked `corpus` tree on every run — which would also have permanently tripped `util_score_row.py`'s own new dirty-tree refusal (CEO-174: "a dirty-tree number describes no checkable tree"). Fixed by snapshotting each suite subdirectory's file listing **before** grading and removing (by exact name) anything new **after** — deliberately **not** `git clean`, which is repo-wide-destructive by nature and unnecessary when the harness already knows precisely which files it just caused to exist.

### 4.1 Bignum/overflow — now 6 witnesses, not 2

`checkfpc ck large overflow` join the already-known `radix lgint`: all six show raw-integer-wraparound or wrong-promotion on arithmetic/parse overflow (`INT64_MAX+INT64_MAX` → `-2` instead of promoting; `integer("3e500")` wraps instead of clamping/erroring; `real("7r4")` radix-literal parsing → `none`). This is arbitrary-precision-integer promotion, a genuine feature gap needing a real design pass, not a class-cure — consistent with every prior session's judgment on `radix`/`lgint` alone, now confirmed to be a larger cluster. **Mint**: `icon-arizona-class-bignum-not-implemented` (named since session 3, never formally minted until now) with all 6 witnesses.

### 4.2 The lvalue-producer-as-operand family has (at least) two more witnesses

Both confirmed by gdb, not inferred:

- **`errors.icn`** aborts via `emit.cpp`'s own self-diagnosing `IR_ASSIGN` guard: `nameless N-operand assign ... s[i:j] section — LOWER's TT_ASSIGN terminal arm minted a placeholder; not a missing template.` Read the guard's own comment and confirmed against the source (`errors.icn:79`, `(a[1:3] := a) | monitor(&line)`): this is **not an emitter template gap**, it's LOWER routing a substring-section assignment target (`s[i:j] :=`) through the generic named-variable `IR_ASSIGN` node instead of a dedicated lvalue-producer node, because there's no such node for this shape yet.
- **`evalx.icn`** aborts with `FATAL emit_drive: IR op=122 has no template` — a **misleading message**: op=122 is `IR_SWAP`, which plainly has a case (`emit.cpp:1881`). The FATAL sink is reused as that case's own internal guard (confirmed via `bt`: frame `emit_drive (emit.cpp:1886)`, not the generic dispatch default). Root cause: `IR_SWAP`'s handler assumes both operands are simple named variables (`bb_varslot_peek(IR_LIT(operand).sval)`); `evalx.icn` chains swaps (`x :=: y :=: z`, parsed as `x :=: (y :=: z)`), so the outer swap's right operand is itself an `IR_SWAP` node, not a named variable, and the peek fails.

Both are the **same architecture** already named by the two existing do-not-touch rows `icon-arizona-class-reverse-assign-to-global-not-emitted` (assign, missing global branch) and `icon-arizona-class-swap-list-slot-record-field-fails` (swap, missing mixed-operand-kind branch): **SCRIP's reversible-assignment IR model assumes its target/operand is always a simple named slot, and has no general mechanism for the target being itself the result of another lvalue-producing sub-expression.** That family is now known to span at least 5 witnesses across 4 rows (`ilib mega spellnum` · `struct` · `errors` · `evalx`), not 3 across 2. **Recommendation, not action taken**: whoever eventually does the ARCH-LANGUAGES.md + GOAL-TEMPLATE-REVAMP-RULES-DRAFT.md design pass this family is gated behind should treat all four rows as one design problem, not four independent template gaps — the leverage of fixing it once is much higher than previously visible. **Minted** `errors.icn` and `evalx.icn` as their own small rows (matching how the two existing rows are already split by specific construct, not merged), each cross-referencing this finding and the two existing rows, each marked do-not-attempt-without-the-same-prerequisite-reading.

### 4.3 Silent-SIGSEGV family — gdb'd all 4 known witnesses myself; found a real cross-witness clue, not a fix

- **`gc2`**: crashes inside `snprintf`'s libc internals (`__vsnprintf_internal` → `__printf_buffer_init`), called from `rt_fire_buildplan_tweak`'s `"%s__TWEAK"` format (`by_name_dispatch.c:662`) via `dat_construct("nonterm", ...)`. Matches the existing row `icon-arizona-segv-buildplan-tweak-nonterm-gc2` exactly.
- **`tracer`**: crashes **inside the same libc snprintf internals**, but a **different call site**: `subscript_get`'s integer-to-string coercion (`pattern_match.c:238`, `snprintf(ibuf,32,"%lld",...)` for Icon's `n[1]`-subscripts-an-integer idiom). Matches `icon-arizona-segv-int-subscript-snprintf-tracer-others` exactly.
- **`others`**: two *separate* bugs already correctly split by the existing rows (`icon-arizona-segv-int-subscript-snprintf-tracer-others` for n≥20, `icon-arizona-segv-find-uncoerced-integer-arg-others` for n≤12) — not re-investigated further, existing diagnosis stands.
- **`iobig`**: crashes in glibc's malloc/arena code during `&lcase` cset registration at startup (`kw_cset_grow`/`kw_cset_prime`) — a different character entirely from the other three. Matches `icon-arizona-segv-cset-register-coexpr-iobig` exactly; not re-investigated (its own task already has a working hypothesis re: the recent co-expression/pthread-stack change).

**New, not yet in any task file**: `gc2` and `tracer` crash in the **same underlying libc function** (`__vsnprintf_internal`/`__printf_buffer_init`) from two different call sites. That is either coincidence (two unrelated call sites both happening to hit a real glibc bug/edge case) or a shared cause upstream of both call sites (e.g. a stack-alignment violation at the C-ABI boundary when JIT-compiled Icon code calls into *any* runtime helper that itself calls snprintf) — **not confirmed either way this session**, flagged as the single most promising lead for whoever picks up either of the two existing rows next, since resolving it might fix both at once. I did not attempt the alignment theory's own verification (would need RSP-mod-16 tracking at the actual call instruction, not several frames deep where intermediate pushes already obscure it).

**New candidate 5th witness, NOT yet confirmed**: `misc.icn` (from the fresh 27) is also a silent SIGSEGV (only "2" printed first, then crash, zero further stderr) — flagged by the fork, not yet gdb'd by me. Whoever owns the silent-segv family should check it before assuming it shares any of the four existing causes.

### 4.4 `io.icn` — precisely isolated, not just "open() fails"

Confirmed `open("/dev/null","w")` works correctly standalone (minimal repro: `n := open("/dev/null","w"); write(image(n))` → `file(/dev/null)`, correct). The failure requires the **exact combination** present in `io.icn`'s own line: an assignment-with-alternation (`n := open(...) | stop(...)`) as a **non-first element of a multi-element list constructor** (`[&input, &output, &errout, n := open(...) | stop(...)]`). Isolated by elimination — each of these three sub-shapes passes alone: (a) `n := open(...) | stop(...)` outside any list; (b) `L := [n := open(...)]` (list+assign, no alternation); (c) `L := [open(...) | stop(...)]` (list+alternation, no assignment). Only the full combination reproduces. **Not root-caused further** (would need to see what LOWER/emit does differently for a list element that is itself an assign-with-alternation vs. the same expression in isolation) — but this narrows the search space enormously for whoever picks it up next. **Minted** as its own row.

**Correction to the fork's proposed grouping**: the fork paired `fncs1`+`io` as a "file-io open() family, plausible pair." They are **not** the same bug — `fncs1`'s was the CWD-fidelity harness artifact (§2, now fixed at the harness level; its remaining failure, if any, is unexamined) and `io`'s is the list-constructor issue above, which is CWD-independent (`/dev/null` is an absolute path). Un-grouping them here so the correction is visible next to the original claim.
