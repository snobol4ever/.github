## What was found and fixed

`rt_jmp_frame_lexprep2` (`src/runtime/rt/rt.c`) was a complete no-op (`{ (void)fb; (void)suffix_off; (void)region_bytes; }`), called from every multi-clause/generator predicate's frame prologue (`xa_flat_zframe_prologue_str`, `src/templates/xa_flat.cpp:281-294`, the `g_flat_dc_np < 0` branch). Two separate defects in that path, both now fixed:

**(1) The frame was never zeroed, and pending retry state was never installed.** The sibling branch (`g_flat_dc_np >= 0`, ordinary det calls) zeroes the frame then calls `rt_icn_zframe_args_install`; this branch did neither. The runtime already had a complete, working "staging" mechanism for retry state — `rt_pl_zf_resume_set(cursor, tm_lo, tm_hi, tm_off, cursor_off)` (`rt.c:1725`, called from `bb_call_proc_staged.cpp`'s `pl_zf_resume` arm, PL-FR-4) stashes the retained resume-continuation pointer and two trail-mark longs into globals (`g_pl_zf_pending_cursor` etc.) right before jumping back into the callee's α entry — but nothing ever consumed them. Fixed:

```c
void rt_jmp_frame_lexprep2(void *fb, long suffix_off, long region_bytes)
{
    (void)suffix_off;
    memset(fb, 0, (size_t)region_bytes);
    if (g_pl_zf_pending_cursor) {
        *(void **)((char *)fb + g_pl_zf_pending_cursor_off) = g_pl_zf_pending_cursor;
        *(long  *)((char *)fb + g_pl_zf_pending_tm_off)     = g_pl_zf_pending_tm_lo;
        *(long  *)((char *)fb + g_pl_zf_pending_tm_off + 8) = g_pl_zf_pending_tm_hi;
        g_pl_zf_pending_cursor = (void *)0;
    }
}
```
Verified by breakpointing `rt_jmp_frame_lexprep2` for a genuine resume call and reading the frame back afterward: the cursor and both trail-mark longs land at exactly `fb+cursor_off` / `fb+tm_off` as expected (gdb session, see below).

**(2) The generator branch's args-install call re-zeroed what (1) had just written.** My first cut added a call to `rt_icn_zframe_args_install(fb, np, nl)` right after lexprep2, mirroring the det branch, to install the caller's staged arguments (`g_call_args[]`) — needed because a 1-param call like `foo(X)` was reading `X` back as an all-zero `DESCR_t`, corrupting downstream dispatch (root-caused via `gdb`: `r13`/`r14` reading 0 at the crash, `rt_icn_zframe_args_install` breakpoint showing `nparams=0` for the wrong call — see full trace in this row's LEDGER discussion). But `rt_icn_zframe_args_install`'s locals-zero loop assumes locals sit immediately after params (`base+(np+j+1)*16`); in the generator-frame layout that's false — `zeta_storage.c` reserves `resume_off` (and `zeta_mark_off` where applicable) *between* params and named locals (`zeta_storage.c:447-466`, computed strictly after the main per-node slot-granting loop). Passing the real `nlocals` re-zeroed the resume/trail-mark slots (1) had just restored. Fixed by passing `nlocals=0` always — the locals region is already correctly zeroed by lexprep2's `memset`; the args-install call now exists purely for its param-copy loop, which *is* offset-compatible (params always occupy `[16, base)` in both layouts).

**Verified, mode-4 (`--compile`), non-retry case** — `foo(1). foo(2). main :- foo(X), write(X), nl.` now correctly prints `1` (was: SIGSEGV nondeterministically, or silent empty output — matching the parent finding's description exactly). No `Term`/heap involvement, no new globals; consistent with Lon's s273 design ruling.

## What's still broken

- `rt_jmp_frame_lexprep2` (fixed per (1)) correctly writes that cursor and both trail-mark longs into the new frame at the right offsets — verified by reading the memory back with gdb immediately after the call returns.

In the one retry this test exercises, that fixed label and the retained cursor happened to be identical, so this coincidence masked whether it's a real conflict. **Whether this unconditional write is intentional (e.g. establishing "where to resume if this activation itself suspends," a different concept from "which clause to try next") or a second instance of the same defect class is not determined.** Mode-4 fails with SIGILL/SIGSEGV (varies by which of my two fixes is in place) inside `__libc_start_call_main`'s return path — the CPU jumps to a stack address holding raw uninitialized bytes, with a plausible real code address (`0x402f96`) sitting unused in `rax` at the fault. ## ADDENDUM (same session, continued after a "quit filing side reports, keep working" redirect) — two more real fixes landed, (A) ruled out as the RTCC-veneer theory, (B) narrowed to a concrete offset mismatch

**(A) is NOT the RTCC-veneer-clobbers-rcx theory** — that theory was wrong, ruled out by direct test, not just argued away. `x86("call", sym, ptr)` routes through `x86_rtcc_call`, whose BINARY-medium reload half (`x86_rtcc_rl_bin`, `x86_asm.h:385`) uses `rcx` as a scratch pointer into `rtccb` (`movabs rtccb,%rcx; mov r8,[rcx+40]; ...`), while the write-back half (`x86_rtcc_wb_bin`) deliberately uses `rax` instead — avoiding a stomp on the callee's fresh return value at the cost of clobbering whatever the caller had in `rcx`. Since neither `rt_jmp_frame_lexprep2` nor `rt_icn_zframe_args_install` touches r8-r11, wrapping them in this veneer at all is pure waste, so both were switched to `call_bare` (no veneer, `x86_call_ro`, SCRIP `63a752f3`). **This is a real, independently-justified fix — but it did not change bug (A) at all.** Re-tested immediately after: mode-3 crash on the minimal non-retry repro is byte-identical in shape (`mov r12,[rcx*2−0x7bf01b7b]`, `rcx=&rtccb`, same displacement) at a shifted address. So `rcx=&rtccb` at that fault is real but its cause is something else entirely — not chased further; (A) is still open.

**(B) is narrowed a lot, and the resume mechanism is now fully understood** — pulled the *complete* disassembly of `fact$2F1` (mode-4, `objdump -d -M intel`, real symbols) instead of incremental breakpoints, per this file's own prior recommendation, and it paid off immediately. Every `SUSPEND` node in a multi-clause predicate's clause chain (`n4_suspend`, `n9_suspend`, one per clause boundary) shares the *same* `resume_off` slot as "where do I jump if re-entered", AND shares a *second*, fixed pair at `[fb+0]`/`[fb+8]`: the first time any suspend node fires, it copies the current trail-mark value there (self-clearing — the α-port's very next instruction on a nonzero read is `mov [fb],0`) as an implicit "have I already suspended in this activation" signal, separate from the resume cursor itself. `rt_jmp_frame_lexprep2` restored the cursor and the trail-mark slot but never touched `[fb+0]`/`[fb+8]` — so a resumed call looked exactly like a fresh one to the body's own dispatch, and it would silently re-run clause 1 instead of honoring the retained cursor. Fixed by mirroring the same copy the body's own first-time path makes (SCRIP `63a752f3`).

**A concrete, unresolved lead for the next session, verified numerically, not guessed:** `fact/1`'s `resume_off` (the `cursor_off` argument to `rt_pl_zf_resume_set`) is **448** when computed from *inside* `fact`'s own body (`n4_suspend_α`'s internal `rt_pl_cp_push3` call, confirmed live via a `rt_pl_zf_resume_set` breakpoint) — but the compiled call site in `main` (`n82_call_proc_staged_β`, static disassembly, `objdump`) hardcodes **480** (`mov r8d,0x1e0`) for the *identical* by-name lookup (`zls_g_resume_by_name("fact/1")`), same predicate, same conceptual slot. `zls_build` is idempotent per `IR_graph_t*` (early-returns if already processed) and there is exactly one graph-creation call site that could plausibly register a second `fact/1` entry (`lower_pl_register_all_preds`, guarded by `resolve_bb_lookup` against duplicates) — so a naive "two graph objects with the same name" theory doesn't have an obvious mechanism *found yet*, but wasn't fully eliminated either. **If the caller writes the resume cursor at offset 480 into a callee frame whose real data region is only 480 bytes (`region_bytes` measured as exactly 480 for this predicate), that write lands one qword past the end of the zeroed region — directly into the wiring header holding the γ/ω continuation addresses**, which would produce precisely the "garbage jump target" crash class both (A) and (B) share. **What's actually happening, nailed via a full chronological trace of every `rt_pl_cp_push3`/`pop3`/`rt_pl_zf_resume_set`/`rt_jmp_frame_lexprep2` call (gdb `commands`/`continue`, one clean run, addresses resolved with `info symbol`):**
```
OPEN_DET idx=1                                            ; main opens $disj0/1
LEXPREP2 fb=0xdd38 region_bytes=528 pending_cursor=nil     ; $disj0 fresh entry
OPEN_DET idx=0                                             ; $disj0's body opens fact/1
LEXPREP2 fb=0xdb20 region_bytes=480 pending_cursor=nil     ; fact/1 fresh entry (clause a)
PUSH3 cont=n4_suspend_β top_before=0                       ; clause a succeeds, offers clause b
POP3_CALL top_before=3                                     ; write(a),nl,fail -> retry fact
RESUME_SET cursor=n4_suspend_β cursor_off=448              ; correctly staged: fact's OWN cursor/offset
OPEN_DET idx=0                                              ; re-opens fact/1 for the retry
LEXPREP2 fb=0xdb30 region_bytes=480 pending_cursor=n4_suspend_β pending_off=448   ; correctly installed
PUSH3 cont=n52_suspend_β top_before=0                      ; <-- WRONG: n52_suspend_β belongs to $disj0/1, not fact/1
[SIGSEGV shortly after, rip=0x11]
```
Everything through the `LEXPREP2 ... pending_cursor=n4_suspend_β` line is **correct**: the retry is opened, the cursor and offset are exactly right, and `g_pl_zf_pending_cursor`/`g_pl_zf_pending_cursor_off` hold `fact/1`'s own values. The very next thing that should happen is `fact$2F1`'s own clause-1 SUSPEND dispatch (label `n4_suspend_α`, IR node 4@) reading `[fb+0]` (the self-clearing "was I resumed" flag ADDENDUM-1's fix installs), seeing it non-zero, and jumping to `[fb+448]` — which should hold `n4_suspend_β`, landing in clause 2's own logic (`n5...`, ending at its own SUSPEND, `n9_suspend_α`/IR node 11@, which if reached fresh would correctly push `n9_suspend_β`). **Instead the push is `n52_suspend_β` — a label physically inside `FN__$disj0$2F1` (confirmed: its address falls between the `FN__$disj0$2F1:` and `$disj0$2F1_res:` labels in the `.s` text), not inside `FN__fact$2F1` at all.**

**Root mechanism, confirmed with a hardware watchpoint on `*(long*)fb` for the retry frame (`fb=0xdb30`):** `rt_jmp_frame_lexprep2` correctly writes the retained flag (`0 -> 3`, matching the staged `tm_lo`). The **very next write to that same address** happens **inside the emitted code for IR node 0** (`n0_call_builtin_prolog_α`, `fact/1`'s own leading builtin — a `$trail_mark`-shaped call, unrelated to the resume flag), which stores `0` there. The write after **that** happens **inside IR node 3** (`n3_call_builtin_prolog_α`, the clause's own `unify(X,"a")` call), which stores an unrelated tagged value (`0x100000028`) there. **`fact$2F1`'s clause-1 SUSPEND check (`n4_suspend_α`) only runs *after* nodes 0 and 3, so by the time it reads `[fb+0]` to decide fresh-vs-resumed, the retained flag has already been overwritten twice by ordinary node output that has nothing to do with resumption.** A non-zero garbage/leftover value there reads as "resumed" regardless of whether it actually is, and the code then jumps through whatever currently sits at `[fb+448]` — on this run that happens to be stale/adjacent stack content resolving to `$disj0`'s own `n52_suspend_β` (plausible given `fact/1`'s successive activations sit only 16 bytes apart on the stack, `0xdb20` vs `0xdb30`, well inside noise distance of nearby frames' own writes), producing exactly the "PC=0x11-class bogus jump target" signature every finding in this row has independently observed.

**Why `[fb+0]`/`[fb+8]` isn't protected:** `zls_build` (`zeta_storage.c`) *does* reserve `[0,16)` from its own `base`-relative per-node grant loop whenever `s0` is set (`nparams>0 || resumable_callable`, true for `fact/1`) — `base = 16 + nparams*16 = 32` for `fact/1`, so the ordinary `base+k*16` slot loop never emits anything below offset 32. That reservation is *not* what nodes 0 and 3 are hitting. The likely mechanism (structurally the only offset-granting logic in this file that does not route through `base`/`k`) is the **FCC ("value chain") pass at the top of `zls_build`** (`fc_vlit_register`/`fc_vbinop_register`/`fc_vwpop_register`/`fc_call_register`, lines ~338-391): it computes its own slot addresses from a **local depth counter `d`**, independent of `base`, via `fc_vwpop_register(x, (long)d*16)` — and `d` starts at `0`. **This is a plausible, structurally-motivated hypothesis, not yet pinned with a breakpoint on the `fc_v*` registration functions themselves for these two specific nodes** — that is the concrete, cheap next step (breakpoint `fc_vlit_register`/`fc_vwpop_register`/`fc_call_register`, confirm which one registers IR node 0 or node 3 at `d=0`, and confirm it is graph-blind to Prolog's `[fb+0]`/`[fb+8]` convention).

**This retires ADDENDUM 1's "concrete offset mismatch" lead (448 vs 480) — both were correct all along** — and adds a *third* concrete mechanism to the two already filed today (see the numbering note above). All three are different in their specifics — a fixed `rsp`-relative γ-port read drifting after unbounded intervening stack growth (the *other* seat07 pass); a single global pending-cursor mailbox shared across nested frames with no per-frame ownership (seat01); ordinary per-node output landing on the self-clearing resume flag's own bytes because that flag isn't an exclusively-reserved slot (this pass) — but **all three are symptoms of the same root shape**: multi-clause/resumable Prolog predicates keep retry/resume state at fixed offsets or in shared globals that assume nothing else can touch them across a γ-suspend↔β-resume window, and nothing in `zls_build`'s layout or the runtime's pending-state plumbing actually enforces that assumption. That is exactly the gap the **BB FRAME-PLACEMENT CRITERION** (RSP is only safe when every consumer reaches a slot at a fixed offset on *every* path; unbounded γ→β growth forces ζ-ACTIVATION-FRAME instead) and **PZ-4/PZ-5** (`GOAL-PROLOG-100.md`) already exist to close. This is almost certainly why every rung13/14/15 program — all of which backtrack through non-trivial, nested clause bodies — is still red: not one offset bug, but this whole class, appearing at a different spot depending on which program you throw at it.
